# 模式表声明的 fps 可以整条都是假的，而它恰好被下游原样转发

> 发现于：2026-11-11
> 位置：`docs/hardware/radxa-cubie-a7a/vin-references/imx219.c:877-899`（`sensor_win_sizes[]` 满分辨率条目）、`sensor_helper.c:892-927`（`sensor_g_parm` / `sensor_s_parm`）
> 影响：丢帧率里 38.15% 是纯计算假象；`S_PARM` 是空操作，改帧率永远不生效；所有「本该收到 N 帧」的分母都不可信

## 现象

`V4l2FrameSource` 在产品路径上稳定报 38.15% 丢帧，长稳 10 分钟不漂移：

```text
received=11152 expected=18030 (loss_expected=38.15%)
REAL_FPS=18.56  BANDWIDTH=53.9 MiB/s
```

`G_PARM` 一直回报 `1/30`，`S_PARM(1/30)` 返回 `rc=0`，但实测帧间隔稳定在 53.87ms。
最容易被带偏的是这个组合：**命令全都成功、日志没有一行报错、丢帧率恰好恒定**。
恒定最像「链路稳定丢了固定比例的帧」，于是第一反应是去查带宽、DMA、ISP 时钟。

全部扑空：

- 1640×1232 与 3280×2464 的帧率**完全相同**（都是 18.56），带宽差 4 倍；
- 帧间隔分布是**单箱**：120 个样本全落在 52.5~55.0ms，其余箱全零；
- ISP 时钟实测 **704 MHz**，远高于 `sensor_get_clk()` 算出的 275 MHz 需求；
- TDM 的 offline TX 反压整段被 `#if VIN_FALSE` 编译掉了，根本不存在。

## 成因

### 第一层：`S_PARM` 是空操作，`G_PARM` 返回的是常数

`sensor_helper.c:911` 的 `sensor_s_parm()` 只做三件事，**没有一件会改时序**：

```c
info->capture_mode = cp->capturemode;
info->tpf = cp->timeperframe;          // 存起来，之后再没人读
info->use_current_win = cp->reserved[0];
info->isp_wdr_mode   = cp->reserved[1];
info->large_image    = cp->reserved[2];
return 0;
```

而 `sensor_g_parm()`（`sensor_helper.c:892`）压根不看 `tpf`：

```c
if (info->current_wins && info->current_wins->fps_fixed)
    cp->timeperframe.denominator = info->current_wins->fps_fixed;   // 模式表常数
else
    cp->timeperframe.denominator = info->tpf.denominator;           // 永远走不到
```

`current_wins->fps_fixed` 是 `sensor_win_sizes[]` 里的写死值。所以：

- `S_PARM(1/30)` → `rc=0`，什么都没改；
- `G_PARM` → 永远返回 `1/30`，因为模式表写的是 30。

`v4l2_frame_source.cpp:1018` 的回填逻辑 `if (actual != s.cfg.fps)` 因此**永远不会触发**——
回填的前提是「驱动说了实话」，而驱动在这里说的是模式表里的常数。

### 第二层：模式表的 `fps_fixed` 和 `pclk` 两个声明互相矛盾

满分辨率条目（`imx219.c:877`）写着：

```c
.hts = 3444,
.vts = 2700,
.pclk = (278 * 1000 * 1000),
.fps_fixed = 30,
```

`hts × vts = 3444 × 2700 = 9,298,800`，要跑 30fps 需要 `9.2988e6 × 30 = 279 MHz`。
所以 `.pclk = 278 MHz` 和 `.fps_fixed = 30` **在算术上自洽**——这正是它骗过所有人的原因。
两个数一起错、错得刚好配平，读代码时无论如何发现不了。

真相在寄存器表里。IMX219 的像素时钟由 PLL 决定：

```text
VTPXCK = INCK × MPY / VTPXCK_DIV
OPXCK  = VTPXCK / 5                    (CSI-2 10bit 输出)
```

`sensor_hxga_regs`（`imx219.c:70-135`）写的是 `0x0305 = 0x03`（div=3）、`0x0307 = 0x36`（MPY=54）：

```text
OPXCK = 24MHz × 54 / 3 / 5 = 172.8 MHz     ← 不是 278 MHz
```

代入实测寄存器值（`VTS=2700, HTS=3448`）：

```text
3448 × 2700 / 172.8e6 = 53.875 ms = 18.56 fps
```

**与实测 53.87ms / 18.56fps 吻到小数点后两位。**

### 第三层：为什么四个模式里只有这一个是假的

同样的公式套其余三个模式，结果全部正常：

| 模式 | 表声明 pclk | 真实 pixel rate（按 PLL 算） | 真实 fps | 表声明 fps |
| --- | --- | --- | --- | --- |
| hxga 3280×2464 | 278 MHz | **172.8 MHz** | **18.56** | 30 ❌ |
| sxga 1280×960 | 278 MHz | 278.4 MHz | 30.00 | 30 ✅ |
| 1080p 1920×1080 | 278 MHz | 182.4 MHz | 29.99 | 30 ✅ |
| 720p 1280×720 | 200 MHz | 192.0 MHz | 57.56 | 30 ⚠️ |

`278 MHz` 是 **SXGA 那个模式的真实值**（MPY=87），被复制到了满分辨率条目上，
而满分辨率的寄存器表只配到 MPY=54。典型的「复制一条模式、改了分辨率、忘了改 PLL」。

还有一条被忽略的自证：`imx219.c:65` 的 `sensor_default_regs` 注释写着
**`3280 x 2464_20fps 4lanes 720Mbps/lane`**——BSP 作者自己标的是 **20fps / 4 lane**，
而 `sensor_win_sizes[]` 写成 `fps_fixed = 30`、`sensor_g_mbus_config()` 硬编码 2 lane。
20fps 与 18.56 的差距可以解释为那条注释也是估的，但方向明确：**从来不是 30**。

### 为什么不能靠「下游丢帧」解释

MIPI CSI-2 的 HS 链路是**单向**的，接收端无法对传感器施加反压。传感器照自己的
pixel rate 往外推数据，下游接不住只能丢。但丢帧一定伴随：

- 帧间隔分布出现多箱或拍频（丢一帧 → 两个 53.87 = 107.7ms 的间隔）；
- 或 `vb2` 序号出现跳变。

实测两者都没有：`min=53.70 / p50=53.88 / p95=54.02 / max=54.09`，
**±0.4% 抖动、单箱、`seq_gaps=0`**。间隔如此规整只有一种解释——
每帧都是被传感器按时序**产生**的，没有任何一帧被中途丢掉。

## 修法

**不要在应用层修。** 这是 BSP 模式表的错误声明，正确修法是让模式表与寄存器表对齐。
本仓库不改内核，所以落到产品侧的是「不要相信驱动报的 fps」：

1. **`V4l2FrameSource` 的 fps 来源必须可标定**，不能只信 `G_PARM`。
   现有回填逻辑（`v4l2_frame_source.cpp:1018`）在 `fps_fixed` 模式下永不触发，
   需要一条「用实测帧间隔反推 fps」的路径，或允许显式指定校准值。
2. **归因时必须扣除这个基线。** 38.15% 不是链路劣化，是分母错了。
   任何「丢帧率 > 阈值」判据在扣除基线前都没有意义。
3. 若要彻底修好，改 `imx219.c:887-888`：把满分辨率条目的 `.pclk` 改成 `172800000`、
   `.fps_fixed` 改成 `18`（或把 `.vts` 调到 `1766` 换取 30fps，但那会裁掉垂直视野）。

### 已落地的实现（2026-11-11）

第 1 条已在 `V4l2FrameSource` 里实现为**一次性基线校准**
（`V4l2CaptureConfig::fps_calibration_windows`，默认 3；`fps_calibration_max_spread_percent`，默认 15）：

| 设计点 | 取值 | 理由 |
| --- | --- | --- |
| 校准次数 | **一次**，成功后 `calibration_done` 永久置位 | 每窗口重算会把真实丢帧吸收进分母（见下方「边界」） |
| 样本精度 | **微秒**（`window_gaps_us`），不复用取整后的 `gaps` | 53.87ms 截成 54ms 会让反推偏高 2.4%，且这个偏差会被一次性校准**永久固化** |
| 汇总方式 | 中位数 | 首帧 / AE 收敛造成的偶发长间隔会把均值拉偏 |
| 准入判据 | 样本 ≥ 10 帧，且 p05/p95 相对中位数偏离 ≤ 15% | 不稳的窗口说明采集本身有问题，拿它当基线会把异常固化成正常 |
| 取整方向 | **向下取整** | 18.56→18 让丢帧率略偏高；四舍五入到 19 会少报丢帧。本项目纪律是「少报比多报危险」 |
| 失败处理 | 维持原 `fps`，原因写进 `describe()` 的 `[fps: ...]` | 静默维持原值会让运维误以为校准生效了 |

**关键反例（已用变异测试钉住）**：如果改成「每窗口用实测帧间隔反推 fps」，
会形成闭环「丢帧 → 收到更少帧 → 实测帧率变低 → expected 同步变小 → 丢帧率归零」。
实测在 `buffer_count=2` 的真实丢帧场景下，吸收型实现把 50% 丢帧洗成 3%
（`expected=31 received=30`）。守这条的测试是
`V4l2LiveTest.FpsCalibrationDoesNotAbsorbRealFrameLoss`。

## 边界

- **这条只对 `bin_factor=1` 的那个模式成立。** 其余三个模式算出来是 30.00/29.99，
  说明公式与寄存器解读正确，它们的问题不在 fps 声明上（720p 是零帧，另一回事）。
- **`G_PARM` 在别的驱动上可能是诚实的。** 本条的教训不是「G_PARM 都不可信」，
  而是「`G_PARM` 可能只是把模式表常数搬出来」，验证方法是
  **对比实测帧间隔与它声称的周期**，不是读它的返回值。
- 用实测帧间隔反推 fps 也有边界：若下游真的在丢帧，反推值会偏低，
  于是「用实测值当分母」会把真实丢帧吸收掉。所以这一步只能用于
  **建立基线**，不能用于持续测量——两者必须分开。

### 一次性校准的边界（实现之后补记）

- **校准只覆盖「稳定偏置」，不覆盖「漂移」。** 本板 18.56fps 是 PLL 决定的固定值，
  所以一次校准即可。若某天传感器因温度/供电出现真实帧率漂移，一次性校准会
  一直用旧基线——此时丢帧率会**如实反映**漂移（偏高），这是可接受的降级：
  它退化成「基线与现实不符」，而不是「掩盖问题」。
- **校准样本太少时会被跳过，而不是放宽门槛。** 默认要求 ≥10 帧且离散度 ≤15%。
  用短窗口（如 500ms×低帧率）或极小 buffer 时，样本天然不足，校准会拒绝执行
  并在 `describe()` 写明原因。这是**有意为之**：校准错误比不校准危险。
- **`fps_calibration_windows=0` 会完全关闭校准**，此时若驱动撒谎，
  每次重启后前 N 个窗口仍会出现基线偏差。这与「不校准」的历史行为一致。
- **校准不修改 `v4l2_frame_source.hpp` 里 `fps` 的初值**，只改运行期 `cfg.fps`。
  重启后会重新校准一次。若某次启动恰好采样到异常段，基线会带偏一个开机周期——
  这是「一次性」换来的代价，已由准入判据尽量挡住。
- **测试侧的边界**：`FpsCalibrationReplacesLyingDriverValue` 必须用
  `set_frame_rate=false`，否则 `start()` 的「以驱动回报为准」回填会先把
  `cfg.fps` 改对，校准就无事可做。vivid 的 `G_PARM` 是诚实的（回报 60），
  构造不出「撒谎的驱动」，只能构造「配置值与实际不符」。

## 教训

**当两个错误声明在算术上互相配平时，读代码永远发现不了它。**

`.pclk = 278MHz` 和 `.fps_fixed = 30` 单独看都很正常，放在一起还能自圆其说，
于是它们同时存在了很久。唯一能戳穿的办法是**绕开声明、直接读硬件寄存器**，
再用物理公式正推一遍——本次正是靠 I2C 读回 `VTS=2700 / HTS=3448` 才推翻了
自己先前「VTS 被拉伸到 4349」的错误假设。

配套的一条：`rc=0` 只说明 ioctl 被接受，不说明它做了什么。
`S_PARM` 返回成功、`G_PARM` 返回 30、丢帧率恒定——三个「正常」信号叠在一起，
构成了本次最完整的假象。
