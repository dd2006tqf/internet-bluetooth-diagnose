# 帧间隔单箱分布是「下游没在丢帧」的决定性证据

> 发现于：2026-11-11
> 位置：板端实测（`/tmp/tsgap` 探针，一次性，未入库）；判据适用于任何 V4L2 采集链路
> 影响：不做这个检查，会把「传感器本身帧率低」误判成「下游带宽不足/丢帧」

## 现象

帧率只有 18.56fps（期望 30），丢帧率恒定 38.15%。第一反应几乎必然是
「下游接不住」：ISP 太慢、DMA 带宽不够、TDM 反压、MIPI 链路不够宽。

于是按这个假设做了一轮又一轮实验，全部落空：

| 实验 | 结果 | 对假设的含义 |
| --- | --- | --- |
| 1640x1232 → 3280x2464（像素量 ×4） | 帧率**完全相同** | 带宽不可能是瓶颈 |
| ISP 时钟实测 | **704 MHz**（`sensor_get_clk()` 只算到 275 MHz 需求） | 不是 ISP 时钟 |
| TDM offline TX 反压 | 整段被 `#if VIN_FALSE` 编译掉（`vin_tdm.c:735`） | 这条路径不存在 |
| 3200x2400（非模式表尺寸） | 同 53.87ms | 与分辨率无关 |

## 成因

### 帧间隔直方图给出了分水岭

在 6 秒采集窗口内统计**相邻帧的时间戳差**（`v4l2_buffer.timestamp`，
内核单调时钟），按 2.5ms 分箱：

```text
3280x2464, 120 samples:
  mean=53.87ms  min=53.70  p50=53.88  p95=54.02  max=54.09

  bin 52.5-55.0ms : #################### 120   ← 全部
  bin 50.0-52.5ms :                          0
  bin 55.0-57.5ms :                          0
  其余所有箱      :                          0
```

**120 个样本全落在同一个 2.5ms 宽的箱里，其余箱全零。**
3200x2400 独立复测 60 个样本，同样全在唯一一个箱里。

### 为什么这能排除下游丢帧

关键在于：**下游丢帧不会让周期保持不变，只会让周期变成周期的整数倍。**

若传感器以 30fps（33.3ms）产生帧、下游每 5 帧丢 2 帧，那么用户态看到的
相邻帧间隔会是 `33.3 × 2 = 66.7ms` 或 `33.3 × 3 = 100ms` —— 直方图会出现
**多个箱**，且各箱计数比反映丢帧模式。

若下游是「填满 buffer 就丢」的非规则丢帧，直方图会**变宽**（出现长尾）。

实测是**单箱、且箱宽只有 ±0.4%（53.70~54.09，相对 53.87）**。
这个规整度只有一种来源：**每一帧都是被传感器按自己的时序准时产生的**，
中间没有任何一帧被吞掉或延迟。`seq_gaps=0` 与此一致（序号连续）。

这条推论还有一条硬约束背书：**MIPI CSI-2 的 HS 链路是单向的**，
接收端无法对传感器施加反压。传感器照自己的 pixel rate 往外推数据，
接不住只能丢——而丢了一定会在间隔分布上留下痕迹。没有痕迹 = 没丢。

### 帧率被什么决定

既然下游没丢，那 18.56fps 就是传感器的真实输出率：

```text
HTS × VTS / pixel_rate = 3448 × 2700 / 172.8e6 = 53.875 ms = 18.56 fps
```

`172.8 MHz` 是 `sensor_hxga_regs` 里 PLL 寄存器（`MPY=54`）决定的真实值，
不是 `sensor_win_sizes[]` 声明的 `278 MHz`。完整推导见
[sensor-mode-table-fps-lie.md](sensor-mode-table-fps-lie.md)。

## 修法

**把「帧间隔直方图」作为排查帧率问题的第一个测量，不是最后一个。**

判读规则：

| 直方图形状 | 结论 |
| --- | --- |
| **单箱，窄（±1% 内）** | 传感器就是这帧率，下游没问题 → 去查模式表/PLL |
| 多个离散箱，间隔为基周期的整数倍 | 下游规则丢帧 → 查 buffer 数量与消费速度 |
| 单箱但很宽（长尾） | 下游不规则丢帧或反压 → 查 DMA/ISP 负载 |
| 多箱且箱位无整数倍关系 | 存在两个时钟源在竞争 → 查同步 |

探针本身很简单：连续 `DQBUF`，对相邻 `timestamp` 求差，分箱计数。
**注意必须在同一次 `STREAMON` 会话内连续取帧**，不要两次调用之间 sleep
（那会人为制造大间隔，见 `window-span-vs-elapsed-time.md`）。

## 边界

- **单箱只证明「下游没丢这一层的帧」，不证明「整条链路没丢帧」。** 若丢帧发生在
  统计窗口**之前**（比如 STREAMON 后的前几帧被跳过），直方图看不到。
  所以仍需配合 `seq_gaps`（但这只在序号连续时才可靠）。
- **单箱 + 低帧率也可能是「传感器被正确配置成低帧率」。** 判据是「帧率是否符合
  该模式的时序」，不是「帧率是否低」。本次的错在于模式表声明 30 而实际 18.56，
  不在于 18.56 本身。
- 直方图分箱宽度要小于「单帧周期/2」，否则整数倍丢帧会落进同一个箱里看不出来。
  本次 33.3ms 基周期用 2.5ms 箱，足够分辨 1×/2×/3× 倍周期。
- 帧间隔抖动本身有正常来源（AE 调整曝光会改 `frame_length`，见
  `imx219.c:343`）。看到抖动前先确认曝光是否在动。

## 教训

**「慢」和「丢」是两件不同的事，必须用不同的判据分开。**

本次一开始把两者混成一件：帧率低 → 以为在丢帧 → 去查会丢帧的地方（带宽/DMA/反压），
而实际上一个帧都没丢，只是产生得慢。

区分方法简单到只需一张直方图：**丢帧改变的是间隔的形状，慢改变的是间隔的中心。**
形状规整而中心偏移 → 是慢，不是丢。
