# `/proc/<pid>/stat` 按空白切分取字段：comm 含空格时整体错位，判据静默失效

> 发现于：2026-11-15
> 位置：`tools/weaknet-health-guard.cpp` 的 `CountDThreads()`
> 影响：D 状态判据恒通过（漏报），看门狗「看起来在保护，实际已失效」

## 现象

健康看门狗的第四条判据是「进程内没有长期处于 `D` 状态的线程」，实现最初是：

```c
awk '{print $3}' /proc/<pid>/task/*/stat 2>/dev/null | grep -c '^D$'
```

构造一行真实存在的 stat 内容：

```
1234 (my service name) D 1 1 0 -1 4194560 0 0 0 0 0 100 50
```

取第 3 字段的结果是 **`service`**，不是 `D`。

```
$ awk '{print $3}' /tmp/stat_test.txt
D
service          ← 这一行本该也是 D
$ awk '{print $3}' /tmp/stat_test.txt | grep -c '^D$'
1                ← 实际两个线程都在 D，只数出 1 个
```

进程里只要有线程的 comm 含空格，它的 D 状态就**永远数不出来**。

## 成因

`/proc/<pid>/stat` 的字段 2 是 `(comm)`，即**用括号包起来的、内容不受约束的字符串**。
comm 可以含空格、括号、任意可打印字符（`prctl(PR_SET_NAME)` 允许，
fork 时继承自可执行文件名时也可能带入）。因此「按空白切分 → 取第 N 段」
从根上就是错的：空白不再等于字段边界。

正确做法只有一个：**定位最后一个 `)`**，它之后才是字段 3 的起点。

```c
char* rp = strrchr(buf, ')');       /* 最后一个 ')':可含括号的 comm 也能定位 */
/* rp+1 == ' ', rp+2 起是字段 3 */
```

同一个文件里的 CPU 判据（`ReadProcCpuTicks`）用的就是这个正确写法。
**同一个数据格式在同一文件里有两套解析器，其中一套是错的** —— 这类不一致
本身就是信号：说明写第二套时没回头确认第一套怎么解。

## 第二个失效方向：退出码被丢弃

同一处的另一个问题：`popen` + `pclose` 的退出码没有检查。

扫描失败时（目录打不开、权限不足、被 `hidepid` 拦），`grep -c` 的输入为空，
**输出 `0` 并且退出码非零**。调用方只看输出，于是「扫描失败」与
「确实没有 D 线程」在结果上完全不可区分，两者都判**通过**。

```c
char* buf = RunCommand(cmd, 128, &rc);
int n = static_cast<int>(strtol(buf, nullptr, 10));   /* rc 被彻底忽略 */
```

修法是不要经过 shell：`opendir` + 逐 tid `ReadFile`，打不开就返回 `-1`，
由调用方按「判据无法评估」处理（`CheckDState` 里 `d_count < 0` → 返回 `false`，
即停止喂狗）。让「读不到」走「不健康」分支，而不是「健康」分支。

## 修法

`tools/weaknet-health-guard.cpp:459` `CountDThreads()`：

- 改 `opendir` + `ReadFile`，逐 tid 读 stat；
- 用 `strrchr(')')` 定位状态字段，与同文件 `ReadProcCpuTicks` 统一；
- 线程数超过 `kDStateMaxTasks` 返回 `-1`（异常情况不静默当 0）；
- 单个 tid 读取失败视为正常竞态（线程已退出）跳过，但目录打开失败返回 `-1`。

回归测试见 `tools/test_weaknet_health_guard.py` 的 `TestDThreadCounting`，
其中同时断言「正确实现数得出」和「旧的空白切分实现数不出」——
后者是为了让这个 bug 的具体形态留在测试里，而不只是「现在是对的」。

## 边界

- comm 里含**换行**不可能（内核会截断），所以按行读是安全的。
- `strrchr` 取最后一个 `)` 的前提是 comm 之后确实还有 `)`。若 stat 被截断
  （读到一半），`rp` 之后可能不足 2 字节，必须显式检查 `rp[1] == ' '`
  与 `rp[2] != '\0'`，否则会读到越界或误判。
- 这个修法只解决「数得出」。判据是否**该**因某个线程 D 了 8 秒而复位，
  是另一个问题（见 `docs/ideas/喂狗条件检查-系统健康看门狗.md`）。

## 教训

> `/proc/*/stat` 的 comm 字段不受约束，**任何按空白切分取字段的写法都是错的**。
> 更普遍地说：解析「人可读格式」时，如果格式里有一个不受约束的可变长字段，
> 就应该找**定界符**而不是**分隔符**。

第二层教训是这个 bug 的发现路径：x86 g++ 编译零告警、78 项测试全绿，
它是在**换 ARM64 clang 编译**时，由一条看似无关的
`-Wunused-const-variable`（`kDStateMaxTasks` 定义了没用）告警牵出来的。
顺着「为什么这个常量没用」查下去，才发现数线程那段压根没走目录遍历。
**告警本身不是问题，告警指向的那处代码没被认真写过才是问题。**
