# 用浮点算「本该收到多少帧」，截断会少算一帧

> 发现于：2026-11-09
> 位置：`server/src/synthetic_frame_source.cpp:41` 与 `server/src/v4l2_frame_source.cpp:1326`
> 影响：丢帧率系统性偏移，且偏移方向是「显得更健康」

## 现象

最自然的写法是：

```cpp
const uint64_t frames = static_cast<uint64_t>(window_ms / 1000.0 * fps);
```

看起来毫无问题。但实测：

```
1000.0 / (1000.0 / 30) = 29.999999999999996
int() 截断             = 29
```

**期望 30 帧，算出 29 帧。** 丢帧率的分子 `expected - received` 就凭空多了 1，
或者说，因为分母少 1，算出的比率会偏。

方向很重要：`expected` 偏小 → 丢帧率偏大。这一条是偏保守的方向，比反过来安全。
但问题不在这，在于**它会让「完美」永远达不到**——即便一帧没丢，
`framesLost()` 也是 1。

## 成因

IEEE-754 双精度无法精确表示 1/30。`1000.0/30` 得到一个略大于 33.3333 的值，
再做 `1000.0 / x` 时舍入误差落到 30 的下方一点点，`static_cast` 直接砍掉小数，
就掉到了 29。

这类误差的量级是 1e-15 左右，但 `static_cast` 是**截断**而不是四舍五入，
所以只要结果落在 29.9999...9 就必然变成 29，误差被放大成了完整的一帧。

写完这篇时验证了一个反直觉的点：**常见配置下这个 bug 不出现**。

```
ms=1000 fps=30: float=30.0    trunc=30  round=30  → 无差异
ms=1000 fps=25: float=25.0    trunc=25  round=25  → 无差异
ms=500  fps=30: float=15.0    trunc=15  round=15  → 无差异
ms=1000 fps=60: float=60.0    trunc=60  round=60  → 无差异
ms=333  fps=30: float=9.99    trunc=9   round=10  → 差 1
```

也就是说，1000ms 与 500ms 这些「整」窗口恰好落得干净，**只有窗口时长不是
帧周期整数倍时才会暴露**。这解释了为什么它容易被漏掉：默认配置下测不出来。

一旦有人把窗口改成 333ms，或者 fps 调成 25 配 400ms 窗口，偏差就出现了，
而且表现为「丢帧率永远不是 0」——很难归因到算术上。

## 修法

用整数算术，带四舍五入：

```cpp
const uint64_t expected = (span_ms * s.cfg.fps + 500u) / 1000u;
```

`+500u` 是整数域的四舍五入（除以 1000 前加半个除数）。这样：

- `ms=333, fps=30` → `(9990 + 500)/1000 = 10`，与数学期望一致；
- 全程整数，没有浮点舍入，结果完全确定。

两个帧源（合成源与 V4L2 源）用**同一套算术**，这不是巧合而是要求：
两路实现的 `frames_expected` 若算法不同，同一组输入会给出不同的丢帧率，
而这两个源本来就是为了互相验证而存在的。

## 边界

整数算术的精度边界是 `span_ms * fps` 不能溢出 `uint64_t`。以 `span_ms` 最大
一小时（3,600,000）与 `fps` 最大 240 计，乘积约 8.6e8，远小于 2^64，
所以当前不构成风险。

另一个细节：`+500u` 做的是四舍五入，意味着当小数部分恰好是 0.5 时向上取。
对「本该收到多少帧」这个语义，四舍五入比截断更合理——但要注意它与
「向下取整」在边界上会差 1。若要严格保守，可以改用向下取整，
代价是系统性低估一帧（丢帧率略偏高）。当前选四舍五入。

## 教训

**凡是「时间 × 频率」的换算，都用整数算术。**

浮点在这类计算里没有任何好处——参与运算的都是整数，结果也是整数，
中间引入浮点只是给自己埋一个精度陷阱，而这个陷阱只在特定参数下暴露，
测试很容易覆盖不到。

更进一步：**`static_cast` 截断与浮点误差叠加，会把 1e-15 的误差放大成 1 个单位。**
凡是「浮点算出结果再转整数」的地方，都要问一句：这个结果会不会落在
`x.9999...` 上。

同类问题在别处也出现过：`percentile95` 的索引计算用
`ceil(0.95 * n) - 1`，若用 `static_cast<size_t>(0.95 * n)` 就会在某些 n 上取错位置。
两者都是「浮点转整数」的同一种病。
