# 跨窗口比较帧序号，会稳定产生一次假丢帧

> 发现于：2026-11-09
> 位置：`server/src/v4l2_frame_source.cpp:1247` 附近（`seq_gap_count` 判定）
> 影响：每个统计窗口恒定多记一次 `seq_gap`，看起来像持续性轻微丢帧

## 现象

真机联调时，明明画面完全正常、没有丢帧，但 `seq_gap_count` **每个窗口恒为 1**。
不是偶发，是稳定复现，且与真实丢帧无关。

这个现象很容易被误读成「链路有轻微但不间断的丢帧」——恰恰是最难排查的那类
结论，因为它看起来既不像故障也不像正常。

## 成因

`seq_gap_count` 的逻辑是「当前序号 != 上次序号 + 1 就记一次跳变」。

若 `last_seq` 跨 `snapshotAndReset()` 保留，那么**每个窗口的首帧**都会和上一个
窗口的末帧比较。这看起来没问题：

```
窗口 A 末帧 seq = 29
窗口 B 首帧 seq = 30      ← 连续，没问题
```

但真实调用中，两个窗口之间必然存在间隔（快照本身的耗时、循环的其它工作），
这段时间里驱动仍在出帧：

```
窗口 A 末帧 seq = 29
   ...间隔期间驱动又出了 3 帧（30, 31, 32）...
窗口 B 首帧 seq = 33      ← 29 + 1 = 30 ≠ 33，误记一次 gap
```

**关键点：这段间隔里的帧本来就该被丢弃**，因为它们是上一个窗口之后、下一个
窗口之前产生的，从未属于任何统计窗口。把它们算作「丢帧」是概念错误。

`snapshotAndReset()` 的语义是「取走并清零」，清零的必须包括跨窗口的比较基准。
否则窗口边界会变成一个稳定的假信号源。

## 修法

`resetWindow()` 里清掉 `has_last_seq`：

```cpp
seq_gap_count = 0;
has_last_seq  = false;   // ← 本窗口首帧不参与比较
```

判定处相应改为：

```cpp
if (s.has_last_seq && buf.sequence != s.last_seq + 1) {
    ...
}
s.last_seq = buf.sequence;
s.has_last_seq = true;
```

## 边界

清掉比较基准的代价是：**真实的跨窗口丢帧不会被发现**。

若摄像头在窗口边界处掉线，下一个窗口的首帧序号跳了一大截，此时
`has_last_seq == false`，这次跳变不会被记为 gap。

这是有意的取舍——跨窗口丢帧会体现为那个窗口的 `frames_received` 偏少
（因为 `frames_expected` 是按 `window_ms` 固定的），从而反映在丢帧率上。
用 `seq_gap_count` 去捕捉它，反而会因为窗口间隔而持续误报。

## 教训

**「取走并清零」的语义要求把比较基准一起清掉，不只是清计数器。**

任何带状态的差值计算，都要问一句：这个状态跨越了清零点之后还有意义吗？
窗口边界、批处理边界、重连边界，都是这类假信号的常见来源。

同类问题还出现在序号回绕上：`sequence` 是 32 位无符号，30fps 下约 4.97 年
回绕一次，真回绕时序号突然变小。但**不能把任何变小都当回绕**——正常重排的
差值很小，真回绕的差值极大。代码里的判据是「变小且差值 > 2^31」，
两者都不记 gap，因为那是驱动行为，不是丢帧。
