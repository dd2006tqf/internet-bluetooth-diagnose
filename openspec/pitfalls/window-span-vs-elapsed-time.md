# 窗口跨度用实际耗时算，会把「睡眠」误算成「健康」

> 发现于：2026-11-09
> 位置：`server/src/v4l2_frame_source.cpp:1326` 附近（`frames_expected` 推导）
> 影响：丢帧率被系统性低估，摄像头掉线也能报出「画面完美」

## 现象

真机联调时抓到三个假象，都指向同一个根因：

1. 调用方故意多睡 1 秒再取快照，丢帧率不升反降；
2. 驱动因缓冲区填满而丢掉的帧完全不进 `frames_received`；
3. 睡眠越久，统计结果越「健康」——劣化被伪装成优化。

第 3 条最危险，因为它把「采集端跟不上」这个真问题藏了起来。

## 成因

`FrameStats` 里 `frames_expected` 是丢帧率的分母，它的推导方式决定了一切。

写错的版本是：

```cpp
const auto elapsed = now() - window_start;      // 实际流逝时间
const uint64_t expected = elapsed_ms * fps / 1000;
```

看起来天经地义：算这段时间里本该来多少帧。问题在于**实际流逝时间里包含
了调用方自己的延迟**。那段延迟期间，驱动侧因为用户态没及时 DQBUF，
缓冲区填满后开始丢帧——这些帧既不在 `frames_received` 里，也不该被算作
「本该收到」。

于是分子分母都被拉大，比率反而下降。多睡一秒，账面更漂亮。

更隐蔽的一层：如果调用方因为系统负载而延迟进入，我们看到的不是
「网络/链路劣化」，而是「我们自己的采集节奏乱了」。用实际耗时算，
这两件事会被混成一件，而这恰恰是本项目最不能接受的——观测者的状态
污染被观测对象的结论。

## 修法

固定用**窗口设计跨度** `cfg.window_ms`，不用实际耗时：

```cpp
const auto span_ms = static_cast<uint64_t>(s.cfg.window_ms);
const uint64_t expected = (span_ms * s.cfg.fps + 500u) / 1000u;
```

同时把口径写进注释，避免后人「顺手优化」回去。

代价是：调用方延迟进入时，实际只 drain 到较少帧，`frameLossRatio()`
会偏高。这是**如实**反映「本窗口没取够帧」，不是误报。

选这个方向的理由：**少报比多报危险**。少报会让运维错过真实故障，
多报最多是虚惊一场。

顺带修掉一个同类问题：`sampled_at` 用实际结束时刻而不是 `window_end`，
因为窗口早已过期时 `window_end` 落在未来，会让下游以为这份数据来自未来。

## 边界

这个修法假设调用方**基本按节奏**取快照。若调用方长期严重滞后，丢帧率会
持续偏高，此时应当暴露的是「采集循环有问题」，而不是通过调节分母把数字
修好看——但目前的 `FrameStats` 没有字段能区分「链路丢帧」与「采集滞后」，
这是已知的表达力缺口。

## 教训

**推导「本该发生多少」时，分母必须是契约约定的量，不能是实际观测到的量。**

凡是出现「用实际值去算预期值」的地方，都要警惕它会把偏差吸收掉。
正确的做法是让偏差显现出来，而不是让比率看起来正常。

同一类错误还出现在浮点截断里：`1000.0 / (1000.0/30)` 得到
29.999999999999996，截断成 29 会让丢帧率整体偏移。所以这里用整数
`(span_ms * fps + 500u) / 1000u`，与合成源保持同一套算术。
