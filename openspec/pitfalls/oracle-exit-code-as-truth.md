# 拿工具进程的退出码当 ground truth，会把健康解析器判成故障

> 发现于：2026-09-12
> 位置：`docs/网络体验评价体系.md:717`（结论撤回记录）、`tools/dns_oracle.py`（正确做法）
> 影响：一次真实的 DNS POOR 判定被错误地"确认为正确检出"，还连带改坏了验收门禁

## 现象

开发板上 DNS SLE 持续判 POOR，目标指向网关解析器 `192.168.137.1`。

为了确认这是"体系抓到了真故障"还是"体系误报"，跑了一条外部命令做对照：

```bash
host -W 2 www.baidu.com 192.168.137.1
echo $?      # → 1
```

`exit=1`，于是结论写成：**网关解析器确实故障，DNS 判 POOR 是正确的检出。**

这个结论当时看起来很扎实：评价体系给出告警，独立工具也给出失败，两者一致。
基于这个"已确认的故障"，验收脚本的判定门禁还被改了一处（`GT_OK1` 条件），
让阶段 1/3/4 的真实断言在健康网络上被跳过。

## 成因

`host` 在**不指定 `-t`** 时，会依次查询 A、AAAA、MX 等多种 RR 类型。

网关对 A 记录是正常的（`www.baidu.com` 有 A 记录答案），
但它不支持（或空）AAAA / MX 查询，那些查询返回 NXDOMAIN。
`host` 只要有任何一个子查询失败就整体 `exit=1`。

所以 `exit=1` 的真实含义是：

> **"这个域名在某几种 RR 类型上没查到记录"**

而我们**想知道的**是：

> **"这个解析器能不能正常回答 A 查询"**

这两句话在 A 记录健康的解析器上会给出相反答案。把前者的输出当后者的
ground truth，等于用一个测了别的东西的量具去校准另一件量具。

这类错误的危险在于**它不像错误**：命令真的跑了，退出码真的是 1，
推理链条（工具失败 → 解析器故障 → 我们的告警正确）在逻辑上是自洽的。
唯一的问题是起点那个测量本身不成立。

## 修法

自己构造 DNS 查询报文，显式指定 QTYPE，直接解析响应里的
RCODE / ANCOUNT / 答案记录（`tools/dns_oracle.py`）。
不走任何 CLI，也就不会被"工具顺手多查了几种类型"干扰。

重测结果（A / AAAA / MX / NXDOMAIN 分别测）：

```text
192.168.137.1 :  A=NOERROR(2 answers)  AAAA=NOERROR  MX=NOERROR  NXDOMAIN=正确
223.5.5.5     :  A=NOERROR(3 answers)  AAAA=NOERROR  MX=NOERROR  NXDOMAIN=正确
```

网关解析器与公共解析器行为**完全一致**，此前判定的"故障"不存在。

这里有个值得注意的细节：`host` 报告的失败在**它自己的语义下是真的**
（那几种 RR 确实查不到），错的是我们给它强行赋予了"A 查询是否正常"的含义。
换成 `host -t A` 也能修正，但那依然是依赖 CLI 的语义理解——
自己发包能同时拿到 RCODE、ANCOUNT 和往返时延，这些是 `host` 的退出码
无论如何都表达不了的。

**连带修复**：那条基于错误 oracle 改的验收门禁必须回退。
它的触发前提不成立，留着就会让健康网络上的真实验证被永久跳过——
这比误报更难发现，因为它表现为"一直绿灯"。

## 边界

"自己发包"并不能消除 oracle 自身的风险，只是把风险搬到了可审查的地方。

`dns_oracle.py` 同样是代码，也可能有 bug。区别在于它的每一条判定
（RCODE 是什么、ANCOUNT 是多少）都能被逐行核对，而 `host` 的 `exit=1`
是一个**多因一果的压缩结果**，看不出是哪个类型失败导致的。

另一点：oracle 只回答"这个解析器对这类查询怎么响应"，
它不回答"这个响应是不是用户真实体验到的"。两者的差距
（缓存、TTL、CDN 就近节点、IPv6 优先）不在 oracle 的覆盖范围内，
看到 oracle GOOD 而 SLE 判 POOR 时，仍要先回头查采集侧。本案的
`tracker_q=45 vs tracker_r=324` 就是这样被发现的。

## 教训

**oracle 本身必须先被独立验证，否则测量缺陷会被记成被测对象的问题。**

在用一个对照结果去"确认"自己的判断之前，先问三句：

1. 这个工具输出的到底是不是我想测的那个量？
2. 它失败时，我能从输出里区分是**哪一种**失败吗？
3. 如果它的结论和我的判断一致，会不会只是因为**我们都错了**？

第 3 条最难，因为"两个独立来源结论一致"给人一种交叉验证的错觉——
但如果两边的输入是同一个错误前提（都假设 `exit=1` 等于 A 查询失败），
那它们根本不是独立来源。

这与本项目的一条基本原则是同构的：**禁止把观测器故障嫁祸给业务**。
只不过这次故障发生在测量链的更上游——不是采集器坏了，
而是我们用来校准采集器的那把尺子刻度不对。
