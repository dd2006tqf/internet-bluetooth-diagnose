# 控制框架回读的值，可能和硬件寄存器毫无关系

> 发现于：2026-11-11
> 位置：V4L2 control framework（`VIDIOC_G_CTRL`）与 IMX219 实际寄存器 `0x015a/0x015b`
> 影响：用 `--get-ctrl exposure` 当曝光证据，会得出「AE 在长曝光」的错误结论，进而误判帧率被曝光拉低

## 现象

排查帧率偏低时，怀疑是 AE 自动拉长曝光导致 `frame_length` 超过 VTS
（`imx219.c:343`：`if (shutter > vts - 4) frame_length = shutter + 4`）。

于是读控制框架：

```bash
$ v4l2-ctl -d /dev/video0 --get-ctrl exposure
exposure: 4036
```

按驱动换算 `exp_val >>= 4`，4036 对应 **252 行**。看起来远小于 `vts-4=2696`，
于是判定「曝光不是元凶」——这个结论**碰巧是对的，但推理是错的**。

等一下，手算核对：`1000 << 4 = 16000`，而 4036 与 16000 差了近 4 倍。
说明 `4036` 这个数**不是从当前快门寄存器算出来的**。

用 I2C 直接读传感器寄存器（绕过所有框架）：

```text
/dev/i2c-3 addr=0x10  VTS=2700  HTS=3448
shutter = 0x03e8 = 1000
```

**真实快门是 1000，控制框架报的是 4036。** 两者不成任何整数倍关系。

## 成因

`exposure` 是一个 V4L2 control，它的读取路径是
`v4l2-ctrl: v4l2_g_ctrl()` → 驱动注册的 `.g_volatile_ctrl` / `.g_ctrl` 回调。
它返回的是**驱动内部维护的状态变量**，不是寄存器的实时值。

问题在于这个状态变量可能：

1. **由 AE 算法异步更新**，而 AE 运行在 ISP 固件或内核线程里，更新时机与
   `G_CTRL` 的调用时机没有同步关系；
2. **存的是另一种单位**（本驱动里曝光有「行数」与「寄存器值 `<<4`」两种表示，
   `sensor_get_exp()` 里 `info->exp/16*hts/(pclk/1e6)` 说明 `info->exp` 是
   `<<4` 后的值）；
3. **在 `s_parm`/`s_fmt` 后被重置或未重新同步**。

三者叠加的结果：`G_CTRL` 返回一个**内部状态快照**，它与硬件此刻在做什么
没有可验证的对应关系。而它看起来太像一个可靠的测量——有单位、有量程、
`rc=0`、单位也对——于是很容易被直接采信。

这与 `subdev-parm-to-devnode-parm.md` 是同一个病的两面：
那边是**写**不生效但返回成功，这边是**读**不可信但返回成功。

## 修法

**需要硬件真值时，只能直接读寄存器，不能用控制框架回读。**

```bash
# 裸 I2C 读 IMX219 快门/VTS/HTS（16 位寄存器，大端）
# 0x015a/0x015b = shutter, 0x0160/0x0161 = VTS, 0x0162/0x0163 = HTS
```

本仓库在 `docs/hardware/radxa-cubie-a7a/vin-references/imx219.c:316-350`
有完整的曝光寄存器写路径（`sensor_s_exp_gain`），可据此反推寄存器与
`info->exp` 的换算关系。

判断控制值是否可信的自检方法：**`set` 一个已知值，立刻 `get` 回来，再读寄存器对照。**
三者一致才可信，任何一个不闭合就说明这条路径不能当证据。

## 边界

- **不是所有 control 都不可信。** 有的驱动把 `.g_ctrl` 实现成「真的读寄存器」，
  那种就是准的。判别方法是上面那条自检，不是按 control 名字猜。
- 本条只证明了**曝光**这一个 control 在本驱动上不可信，没有逐个验证其余 control。
  不要推广成「所有 V4L2 control 都是假的」，但也不要默认其余的是真的——
  在拿它当证据之前，同样自检一遍。
- 更隐蔽的一层：即使 `G_CTRL` 完全准确，**AE 在 fluctl 运行期间本来就会改曝光**，
  两次读取之间值会变。这不是 bug，是自动控制的正常行为。所以「读一次当定论」
  本身就不成立，无论路径可不可信。

## 教训

**「有个数」不等于「这个数测的是你以为的那件事」。**

`exposure: 4036` 有单位、有格式、命令成功、数值在合理量程内——所有
「像证据」的特征都具备。唯一的问题是它和寄存器差着 4 倍，而且**不会报错**。

推论：任何跨越抽象层（控制框架 → 驱动状态 → 硬件寄存器）读取的值，
都要至少在一个点上做**跨层对照**。对不上就说明这层抽象在撒谎，
而它平时不会告诉你。

同类记录：`oracle-exit-code-as-truth.md`（退出码）、
`subdev-parm-to-devnode-parm.md`（ioctl 返回值）、
`gst-v4l2src-fps-artifact.md`（工具输出）——
本目录里已经有一整族「判据本身没被验证」的问题。
