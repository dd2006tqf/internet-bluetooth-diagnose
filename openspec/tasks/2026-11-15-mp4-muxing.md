# 视频留证：裸 H.264 → MP4 容器封装

> 日期：2026-11-15
> 分类：工作流外实施
> 结果：**代码完成、双编译通过、云端 31 项测试绿、板端部署并转正**
> （二进制 MD5 与本地构建产物逐字节一致，生产日志已输出 `mux_failures`）。
> **板端真机端到端未完成**：卡在摄像头采集零帧（`tdm0 rx0 frame error!
> width is 0`，中枢 `pub=0` 从未配置），封装器连一次执行机会都没有。
> 这是**上游断流**，与本次改动无关；采集侧需另开一条线排查。

## 构思

### 这一步要解决什么问题

留证链路的最后一段交付形态是错的。传上去的是**裸 Annex-B H.264**，
而它没有容器、没有时间轴、没有帧率，后果不是「画质差一点」：

- 浏览器 `<video>` 不收 `.h264` 文件，远程查看直接失效；
- 播放器只能从头线性播，**不能拖进度条**——而事故回看的核心用法
  恰恰是「跳到出事那一刻」；
- 云端拿不到时长，运营列表里只能显示字节数。

代码侧的根因很清楚：`VideoClipRecorder` 把编码器吐出的 NAL 单元
按字节拼起来就交给上传器，中间没有任何容器化步骤。这件事从链路
跑通那天就在，只是当时的目标是「通道打通」，形态问题被排到后面。

### 备选方案与取舍

| 方案 | 结论 |
| --- | --- |
| 板端自写 fMP4 muxer（约 500 行 C++） | 不选。无第三方依赖最干净，但要自己处理 `stbl` / `stsc` / `stts` / `stss` 全套 box，且**写错了文件仍能打开**（只是时长/帧率错），属于「错了不报错」的高风险自研 |
| `gst mp4mux` | **实测不可用**。硬性要求输入 buffer 带 PTS（`Buffer has no PTS`），而硬件编码器吐的是裸 Annex-B。加 `framerate` caps → `not-negotiated (-4)`；`do-timestamp=true` 仍然无 PTS；`videoparse` 链不上 `h264parse` |
| `gst avmux_mp4` | **实测产出坏文件**。能收裸 H.264，但 616 帧全部压到同一个时间戳，`ffprobe` 报 `duration=0.006s`。文件能打开、内容全错，比失败更糟 |
| 板端装 ffmpeg 调命令行 | **采用**。不重编码，只搬字节写容器 |
| 链接 `libavformat` | 不选。需要 sysroot 补整套精确版本开发包 + glibc 2.31 硬约束 + 构建体系分叉，代价与前一项完全不同 |

### 为什么上一次评估推翻了 ffmpeg

`docs/ideas/视频流产品化-远程查看与事件留证.md` 原写着「引入 ffmpeg 的成本：
sysroot 补全部依赖、glibc 2.31 硬约束、构建体系分叉，在 mp4mux 能用的情况下
没有收益」。

这句话把**链接库**的代价当成了**调命令行**的代价——两者完全不同：

- 链接：多一个构建依赖、多一条 ABI 约束、二进制体积涨；
- 调命令行：**零**构建依赖、零 sysroot 改动、二进制不链接任何 `libav*`。

板端因已装 `gstreamer1.0-libav`，全部 `libav*` 运行时库本来就在，装 `ffmpeg`
实际只多两个包。也就是说，原评估里唯一成立的前提（「mp4mux 能用」）
被实测推翻了，而它列的成本项在新方案下大部分不存在。已在原文档补订正。

### 为什么不走 OpenSpec change

沿用用户对 v4l2/video 这条线的一贯指示：不进 change。本次是**交付形态修补**
——录制、上传、云端契约的输入输出都没变（清单字段一个没动），只在上传线程
内部多了一步字节变换，不新增产品表面。

### 关键决策一：封装放在上传线程，不放在编码线程

实测单次封装约 0.26 s（570 帧 / 90 KB）。放在编码线程里，这 0.26 s 内
帧中枢租约会堆积、采集帧被丢弃；而编码线程的纪律是「绝不被下游拖住」
（`enqueue()` 已为同一理由把上传移到独立线程）。上传线程本来就在等网络，
0.26 s 本地 CPU 对它没有影响。

副作用是**必须重算** `total_bytes` 与 `content_sha256`：它们在分片前用于云端
幂等（同 `clip_id` 异内容 = 409）。若封装后仍按原始码流算，云端会判冲突，
而本地日志只显示「清单上传失败 409」，完全看不出是字节换了。

### 关键决策二：封装失败不丢证据

缺 ffmpeg 或码流不合规时，**改传裸 H.264** 并计入 `mux_failures`：

- 云端历史片段本来就是裸码流，播放路径已能处理；
- 放弃上传等于让一次真实事故的现场永久消失，代价远大于「这次没有容器」；
- `mux_failures` **不**并入 `clips_dropped`：前者说明缺依赖或编码器异常，
  后者才是留证真丢了，两者处置方向相反。

### 关键决策三：帧率用有理数，且必须来自实测

`VideoClipMeta::fps` 原来固定 25，`grep -n "fps"` 在 `video_clip_exporter.cpp`
里只有序列化那一处——**没有任何地方按实测填过它**。而采集侧是变速的
（板端实测 18.5 fps 上下浮动），用名义 25 会让 Container 时间轴按
`25/18.5 ≈ 1.35` 倍拉长，「事发那一刻在第几秒」系统性偏掉，且不报错。

修法两处：

1. `poll()` 里用 `frames_.size() - start` 与 `newest_mono_ms_ - frames_[start].mono_ms`
   算实测帧率，纯整数四舍五入（先乘后除加半个除数），填入 `meta.fps`；
   同时新增 `meta.frame_count`——容器里没有「帧率」这个独立的量，
   它是由「帧数 ÷ 时长」反推的，少了帧数就只能硬编。
2. 传给 ffmpeg 的 `-framerate` 写成 `N/D`（`N = 帧数×1000`，`D = 跨度ms`），
   使容器时长 `= 帧数 × D / N = D/1000` 秒，**与真实跨度逐毫秒相等**。
   用小数（如 18.56）会引入恒定相对误差：570 帧实测从 30.711 s 漂到
   30.712 s——小，但没理由白吃。

退化条件（帧数 < 2 或跨度为 0）回落 `25/1`，成功时容器照样可用。

### 关键决策四：memfd 而非临时文件，也非管道

板端实测三种输出目标的行为：

| 目标 | 结果 |
| --- | --- |
| `pipe:1` | **失败**：`muxer does not support non seekable output`（`moov` 要回填偏移） |
| `/tmp` 临时文件 | 可行，但要管清理、占闪存、多一次落盘 |
| memfd | **可行且最好**：可 seek、不落盘、无残骸 |

输入同理走 `/proc/self/fd/0`。这条路径有一个**不显然的前置条件**：输出文件名
没有扩展名，ffmpeg 无法据此推断格式，必须显式 `-f mp4`，否则报
`Unable to find a suitable output format`（实测踩到）。

另外三条实测出来的约束：
- fd 编号必须 ≥ 3（`dup2` 到 0/1/2 才安全）；
- `fork` 后子进程只能用异步信号安全函数（`dup2`/`execv`/`_exit`），
  `argv` 必须在 fork **之前**组装好；
- 用 memfd 做 stderr 而不是管道：管道写满会**阻塞子进程**，
  而父进程正在等它退出——经典死锁。memfd 是有 inode 的普通文件，不会满。

### 关键决策五：产物校验按字节，不信退出码

`avmux_mp4` 演示了「退出码 0 但产物不是 MP4」是真实存在的形态。所以
`looksLikeMp4()` 检查 `[4, 8)` 是否为 `ftyp`——ISO/IEC 14496-12 规定 box 类型
落在这个位置，而 Annex-B 起始码在最前 4 字节内，两者不可能混淆。

云端下载端点用**同一个判据**决定 `Content-Type`。为什么不让清单声明容器类型：
容器是码流自身的事实，再在清单里声明一份就等于允许两者不一致，而不一致时
以谁为准没有答案；何况历史片段全是裸码流，两者会长期共存。

### 关键决策六：测试必须在没装 ffmpeg 的机器上也全绿

本机（CI 所在的那类环境）`which ffmpeg` 返回 1。若所有用例都依赖它，
测试会随环境飘红，然后所有人学会忽略它——那比没有测试更糟。

所以 9 项里 6 项**永远跑**（嗅探、空输入、缺可执行文件、空路径、
坏码流、以及一条「缺 ffmpeg 必须报没装」），3 项用 `GTEST_SKIP`
只在有 ffmpeg 处跑，真机回归补那一段覆盖。

其中「缺 ffmpeg 必须报没装」是最重要的一条：生产里 ffmpeg 是**运行时**依赖，
缺它时服务照常启动、录制照常进行，只有真出事故要封装那一刻才失败。而
`execv` 失败（127）与「码流不合规」在日志上极易混淆，处置方向完全相反
（补依赖 vs 查编码器），所以必须用测试钉住报错文案。

### 关键决策七：观察工具必须跟着载荷形态分叉

`weaknet-incident-forge --watch` 原先把载荷核对写死成 Annex-B：找起始码、
数 SPS/PPS/IDR，缺一个就 `return 5`。封装上线后这变成了一个**必然误报**——
MP4 里没有 Annex-B 起始码，`describe_nal_layout` 会数出 0 个单元，
于是「链路完全成功」被判成「载荷核对未通过」。

这类缺陷比崩溃更麻烦：它只在真机端到端时才暴露，而真机端到端本来就跑得少。
修法是先嗅 `ftyp` 分叉：

- MP4 → 列顶层 box，要求 `ftyp`/`moov`/`mdat` 三者齐备；
- 否则 → 走原来的 Annex-B 校验。

为什么 MP4 这一支要查 `moov` 而不只看 `ftyp`：封装被截断时会留下
`ftyp`+`mdat` 的半截文件，播放器打不开，而 sha256 依然与清单一致
——校验和只证明「云端存的字节就是板端发的字节」，不证明那串字节可用。

四个边界用例已本地验证：真实 Annex-B 起始码不会被误判成 MP4；
最小 MP4 三 box 通过；**截断 MP4（缺 `moov`）必须判为不可解码**；
短 buffer 不崩。

### 真机卡点：摄像头采集零帧（与本次改动无关）

事故开得很干净：

```
[forge] 事故已开出：sitinc_radxa_cubie_a7a_..._1794733306767
[forge]   受影响设备 3 台，状态 ONGOING
```

但留证片段一个都没有。逐层取证后定位在**采集侧**，不在封装侧：

| 证据 | 读数 | 含义 |
| --- | --- | --- |
| 中枢停止统计 | `hub:none(unconfigured) pub=0 acq=0 rel=0` | 一帧都没回调，中枢从未配置 |
| 内核首次 open | `tdm0 rx0 frame error! width is 0, height is 1936` | 零帧形态（宽度恒 0 = 没收像素） |
| `v4l2-ctl --stream-mmap=3 --stream-count=30`（首次） | `select timeout` | 设备当刻确实零帧，**不是服务代码的问题** |

已按 memory `capture-first-open-zero-frames` 做过完整对照实验：重启板子 → 服务自动启动
（第 1 次 open，零帧）→ 重启服务（第 2 次 open）→ **仍然零帧**。那条记录的判据
是「第一次必挂、第二次起必好」（样本 4/4），本次**第二次也挂**。

> **订正**：排查过程中我第二次用 `v4l2-ctl --stream-mmap` 做探针，之后内核出现
> `vinc0 cannot write and read the right addr to register, y 0x0, cb 0x0, cr 0x0`
> 以及 `__vin_set_fmt device busy`。我一度把它当成「DMA 未映射的驱动程序故障」，
> **这是错的**——`v4l2-ctl` 跑完不释放设备，内核留下
> `imx219 is not used, video0 cannot be close!`，后续 open 必然 `device busy`，
> vinc0 那条报错是**探针搞脏设备的后果，不是根因**。该结论已记入 memory。

**结论**：真机端到端被采集侧零帧挡住，而封装器连一次执行机会都没有——
这是**上游断流**，与本次改动无关。采集侧剩余的不确定性（第二次 open 为何仍零帧）
需要另开一条线、用**不污染设备**的手段排查，不该在这条线上继续消耗。

### 遗留问题

1. **摄像头采集故障（阻塞真机验证）**。`vinc0 cannot write and read the
   right addr to register, y 0x0, cb 0x0, cr 0x0` —— 三个平面地址全 0，
   `sunxi-vin` 没有把 DMA 地址写进寄存器，随后 `__vin_set_fmt device busy`。
   已经做过完整对照（重启板子 → 第 1 次 open 零帧 → 重启服务第 2 次 open
   仍零帧），排除了已知的「首次 open 竞态」。**这条独立于 MP4 改动**，
   但也独立于它存在——所有视频下行能力都被它挡住了。需要单开一条线排查。
2. **板端真机未复跑**。上面所有「完成」都不包含「这段代码在板子上真的
   产出了可播放 MP4」。按仓库纪律，这不构成交付完成。
3. **恒定帧率是近似**。真实采集变速，`-framerate` 只能给一个恒定值。
   用整段平均帧率，误差在毫秒级，对「事发在第几秒」够用；要精确到
   每帧需要写 PTS，那得自己实现 muxer（回到备选方案一）。
4. **ffmpeg 缺失只在部署时告警**。若板端后来被清理掉 ffmpeg，
   要等 `mux_failures` 涨才会发现。这个计数目前在停止日志里，
   没有周期上报。

### 是否值得升格为 OpenSpec change

不建议。没有新增产品表面：清单字段一个未加（`frame_count` 只在板端内部
流转，不进入上传报文），云端契约不变，唯一对外可见的变化是下载端点的
`Content-Type` 在字节确实是 MP4 时变成 `video/mp4`——那是对既有一行
header 的修正，不是新能力。

如果将来要把「实时查看」做成 WebRTC/HLS，那才是需要规划的部分。
