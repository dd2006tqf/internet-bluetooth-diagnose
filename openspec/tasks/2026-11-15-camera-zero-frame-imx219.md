# IMX219 采集零帧：一份错误结论的撤回与方法论纠正

> 日期：2026-11-15
> 分类：工作流外实施（**排查结论撤回**）
> 状态：**方法论部分成立；「采集正常、无缺陷待修」这一结局判断已被
> 同日 13:0x 的复现推翻，见文末「复发」。** 本记录的作用是撤回同日上午
> 那份「CSI-2 数据从未到达 SoC、根因在物理层、需重插 FPC」的错误结论，
> 并固定住导致那个错误的方法论缺陷。

## 构思

### 先给结论

摄像头**曾经工作正常**，但**这个结论在同日晚些时候被复现推翻**。
12:39~12:42 那段时间确实是健康的：

```
frame stats: window_ms=15038 expected=271 received=268 corrupt=0 lost=3
             bytes=816195072 seq_gap=0 max_gap_ms=161 p95_gap_ms=54
frame stats: window_ms=15045 expected=271 received=271 corrupt=0 lost=0
             bytes=825331584 seq_gap=0
frame stats: window_ms=15043 expected=271 received=272 corrupt=0 lost=0
             bytes=828377088 seq_gap=0
```

连续 8 个窗口稳定出帧，`hub configured=1`，`tdm0 rx0` 错误 **0** 次。

但 13:03 那次重启之后，同样的板子、同样的二进制，**再也没有出过帧**。
详见文末「复发」。所以本记录只能主张「它有过一段健康期」，
不能主张「它已经正常了」。

### 为什么本记录必须存在

同日上午我写下了一份 226 行的排查记录，结论是：

> **CSI-2 数据从未到达 SoC。** 依据是四个中断计数在整场流式传输期间
> 全 8 核恒为 0。……根因指向物理层，需重插 FPC。

这个结论**是错的**。它把一个「偶发的、可自愈的启动期解析异常」，
误判成了「硬件接触不良」。如果留着不改，下一个人会去拆机器重插排线，
而问题本来会自己好。

### 用户的一句话点破了它

> 「不可能啊，我们之前不是完整跑过一次链路了吗，怎么会突然不行呢？」

这句质疑是对的，而且它指向的正是我漏掉的那条推理：**能工作的东西不会
无缘无故坏掉**。之前完整跑通过，那么"硬件坏了"就是一个应当被高度怀疑、
而不是被优先接受的假设。我没有做这一步反证。

## 实现方式（错误是怎么一步步产生的）

三个错误叠加，每一个单独看都不显眼。

### 错误一：用 `dmesg` 判断历史

我执行 `sudo dmesg | grep -c "tdm0 rx0"` 得到 **0**，据此判断「TDM 一次都没被触发」。

`dmesg` 读的是**环形缓冲区**，在开机运行 40 多分钟后早已被冲掉。
改用 `journalctl -b 0` 查同一台机器同一次 boot：

```
$ sudo journalctl -b 0 | grep -c "tdm0 rx0"
149
```

**149 次，不是 0 次。** 而且形态正是 `width is 0, height is 1138`、
`hblank short! min is 11` 这种解析失败——说明数据到了，TDM 在解析，
只是解析得不正确。

### 错误二：读中断计数器时选错了时刻

我几次采样 `/proc/interrupts` 都看到 `5908000.tdm` 全 0，于是认定
「自开机从未有过中断」。

但 **TDM 复位会清零它的计数值**。日志里满屏都是：

```
__sunxi_tdm_reset_v2_handle:workqueue tdm_rx0 reset!!!, isp frame count is 0
```

所以「此刻读到 0」完全可能是「刚被复位清掉」，而不是「从来没有过」。
12:20 再读时，同一行已经是：

```
443: 0 0 0 0 0 0 756 0  wakeupgen 134 Level  5908000.tdm
```

CPU6 上 756 且在增长。

### 错误三（根本性的）：把「当时没有」当成「从未有过」

前两个是取证手段的错误，第三个是推理错误。我拿一个**瞬时采样**
去否定一段**历史**，而这两者在逻辑上不等价。

正确做法应该是：要么用累积量（`journalctl -b` 的日志计数，
它不会被环形缓冲区之外的复位影响），要么多次采样看趋势，
绝不能单次采样就下「从未」这种全时段断言。

### 转折点：断网后重新连上，采集已经正常

排查过程中板子断网重启（见文末「操作事故」）。重连后第一件事是看帧统计，
结果直接就是正常的 `received=268 / expected=271`。

再往前追，断网前 12:19:50 那一轮其实已经是 `received=58` 了——
说明**在我宣布"CSI-2 从未到达"的同一时段，它已经开始出帧了**。

真实的失败形态是：数据到了，但 TDM 反复解析失败并复位
（`hblank short` / `width is 0`），要过一段时间才收敛到稳定出帧。
这是**启动期收敛问题**，不是硬件故障。

## 结果

### 已确认为真的部分（可保留）

排查中逐层核对的那批事实本身是有效的，它们是：

| 层 | 证据 | 结论 |
| --- | --- | --- |
| 器件在位 | I2C chip id `0x0219` | ✅ |
| 供电 | `axp8191-bldo1` 5/5 enabled，1800 mV | ✅ |
| MCLK | `csi-mclk` 26 MHz enabled | ✅ |
| 寄存器已配 | VTS `0x0A8C` / HTS `0x0D78` / PLL / crop 与 BSP 模式表一致 | ✅ |
| 驱动流式 | `sensor_s_stream on = 1` 成功 | ✅ |
| 拓扑 | 7 跳全 ENABLED，`SRGGB10_1X10/3280x2464` 对齐 | ✅ |
| CSI/ISP 时钟 | 704 MHz enabled | ✅ |
| lane 数 | 寄存器 `0x0114` 与 `sensor_g_mbus_config` 都是 2 lane | ✅ |

顺带一个**有效的排除**：dmesg 里 `get csi mipi clk fail` /
`Get isp bus clk failed!` 看着像根因，但读 `vin.c` 可确认不是——
拿不到句柄就置 NULL 并继续，真正的时钟使能走
`csic_ccu_mcsi_combo_clk_en()` 的 CCU 寄存器门控，不依赖这些句柄。
clk_summary 也证实 `csi` / `isp` / `csi-mclk` 实际 enabled。

### 已撤回的部分

| 原结论 | 状态 |
| --- | --- |
| CSI-2 数据从未到达 SoC | **撤回**（中断计数非零，日志有 149 次 TDM 错误） |
| 根因在物理层 / FPC 接触不良 | **撤回**（无证据支持） |
| 需要断电重插排线 | **撤回**（不必要的物理干预建议） |
| 「软件侧可查项已全部查完」 | **撤回**（其实没查完，是取证手段本身错了） |
| `0x0122 = 0x00` 是最可能根因 | **撤回**（未定性，且不成立） |

### 真实的失败模式（留作后续观察）

如果是**冷启动后的一段时间内** TDM 解析不稳定、随后收敛，那么它可能
会在每次重启后重现。当前样本：

- 12:24 重启后首次 open → **直接正常**，连续 8 窗口稳定；
- 更早的 12:11 重启服务 → 持续零帧（当时未等到收敛）。

样本不足，**不能**据此断言「重启后必须等 N 分钟」。这一点如实留作
待观察项，不写进任何结论。

### 一次操作事故（如实记录）

排查中板子断网重启（`up 0 min`）。判定依据：

- `/var/lib/weaknet/health-guard-last-failure.json` **为空**；
- `weaknet-health-guard` 的 journal **无条目**。

即**不是**看门狗复位。但也没有其它证据指向具体原因——
我最后一次操作是在跑 `sudo lsof /dev/video*`，紧接着 SSH 就断了。
`lsof` 遍历 `/proc` 时触碰了某个不该碰的节点，是一个合理怀疑，
但**未证实**。如实记录为「原因未定」。

## 遗留

1. **`ZERO_FRAME` 归因改进保留**（`server/src/video_qoe_attribution.cpp`）。
   它不依赖本次排查的结论：无论根因是什么，「期望 N 帧收到 0 帧」
   与「收到一部分帧」在排障方向上都相反，这个拆分本身是对的。
   4 项新单测 + RED 验证（改回只报 `FRAME_LOSS` 时恰好只有新测试变红）。
2. **`server.cpp` 的 `frame stats` 原始数值日志保留**。本次事件正是它的
   价值证明：如果只有 `frames_bad=yes/no`，我连「received=0」都看不到。
3. **方法论教训**（已写入 `openspec/pitfalls/` 候选）：
   - 判断「历史上有没有发生过 X」不能用 `dmesg`，要用 `journalctl -b`；
   - 判断「计数器是否一直在涨」不能用单次采样，因为被监控对象可能自己清零；
   - **已知曾经工作过的系统突然不工作，优先怀疑状态而非硬件**。
4. **冷启动收敛问题待观察**，样本不足，不建结论。

## 复发：13:03 重启后彻底零帧（本记录写作时尚在发生）

写完上面那份「采集正常」的结论之后，板子在 13:03 重启，**摄像头再也没出过帧**。
这一节记录的是什么被推翻、什么仍然成立。

### 实测事实（连续采样，非单次）

| 观测项 | 值 | 采样方式 |
| --- | --- | --- |
| `received` | 持续为 0，`expected≈451/窗口` | 连续 8 个 15s 窗口，全部 0 |
| `bytes` | 0 | 同上 |
| `video frame hub configured` | 本 boot **0 次** | 全时段 journal grep |
| `5908000.tdm` 中断 | 3（开机时那 3 条错误） | 间隔 3s×3、10s 各采样一次，**不动** |
| `5900000.isp` 中断 | 0 | 同上，**不动** |
| `5830000.vinc` 中断 | 0 | 同上，**不动** |
| 本 boot `tdm0 rx0` 错误 | 3 条，全部集中在开机后 96s | `journalctl -b 0` |
| 驱动侧 `sensor_s_stream on` | = 1，成功 | dmesg |
| 驱动侧 `s_fmt` | 3280x2464，成功 | dmesg |
| media 拓扑 | 7 跳全 ENABLED | `media-ctl -p` |

`hub configured` 是应用层首帧回调（`server.cpp:1729`）打出的。它为 0 
等价于**一帧 PixelFrame 都没有到达过应用层**，与 `received=0` 自洽。

### 关键形态：这次连错误都不报

开机后 `tdm0 rx0` 的 3 条错误全部集中在 96~97s，之后**内核彻底安静**：

```
[  95.911549] tdm0 rx0 hblank short! min is 11, max is 65535
[  97.202320] tdm0 rx0 frame error! width is 16383, height is 0
[  97.211196] tdm0 rx0 hblank short! min is 15, max is 16
[  97.328005] __sunxi_tdm_reset_v2_handle: tdm_rx0 reset!!!, isp frame count is 0
```

之后 13:10 重启服务触发**第二次 open**（`sensor_s_stream on = 1` 又一次成功），
**依然一条报错都没有**，但也依然一帧没有。

这与记忆里 `capture-first-open-zero-frames` 记的形态都不同：

| 已知形态 | 特征 |
| --- | --- |
| 首次 open 失败（已记录） | `width is 0`，`height` 在 2255~2420 随机跳 |
| `bin_factor=2` 坏模式 | 稳定 `width is 1869` |
| **本次** | 一次复位之后**完全无报错**，TDM/ISP/VINC 中断全静止 |

也就是说：**「重开一次就好」这次没有成立**。记忆里那条 2026-11-15 补充
观察（第二次 open 跑满 90 秒仍无 `hub configured`，且无 `width is 0`）
与本次形态一致，说明这是**同一个未解变体**，不是偶发。

### 已排除 / 未排除

已排除（本 boot 内实测）：

- 驱动没起来 —— `sensor_s_stream on = 1`、`s_fmt` 都成功；
- 拓扑断开 —— 7 跳全 ENABLED；
- 时钟没使能 —— 沿用上文那节的排除（`clk_summary` 实测 enabled）；
- 设备被别的东西占用 —— 只有 `weaknet-dbus-server` 持有 `/dev/video0`。

未排除（本次没有证据，列出来供下一步）：

- sensor 侧上电/复位时序在冷启动时偶发不完整；
- CSI-2 lane 训练偶尔失败后不重试，驱动侧却仍报 stream on；
- 上游 **`openspec/tasks/2026-11-15-kmod-refcnt-regression-reopen.md`** 里
  记录的模块引用计数损坏，是否影响了 sensor 子设备的 `.s_stream` 实际生效
  （驱动 `rc=0` 但硬件未动作）——**这条与本次现象在形态上吻合，值得优先查**。

### 取证受限（如实记录）

- `v4l2-ctl -d /dev/video0` 全部返回 `Device or resource busy`（服务占用），
  无法读 `--get-fmt-video`；按既有教训**不要**用 `--stream-mmap` 探针，
  它会把设备弄脏。
- 想对照「历史上出过帧那次 boot 的启动日志」，但**已经取不到了**：
  `journalctl -b -1` 只有 289 行（12:13~12:42），而 boot 列表把 12:36 的
  记录划给了 boot 0。时钟在开机后被校时跳变，journald 的 boot 边界被写乱。
  **这是一个新的取证陷阱**：`journalctl -b N` 在时钟跳变过的机器上，
  boot 归属不完全可信。逐 boot 统计 `hub configured` 时，boot -2 的 2 次
  命中的其实是 `sudo` 命令行里的字符串，不是应用日志——grep 也要防自匹配。

### 结论

**摄像头零帧问题仍然开放，根因未定。** 本记录早上那份「采集正常、
无缺陷待修」的结局判断**不成立**，只有「它有过一段健康期」这一点成立。
方法论部分（`dmesg` 不是历史、单次采样不能否定全时段、优先怀疑状态）
不受影响，仍然有效。
