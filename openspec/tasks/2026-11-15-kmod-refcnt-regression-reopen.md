# kmod vma 引用计数下溢：修补未闭合，问题重开

> 日期：2026-11-15
> 分类：工作流外实施（缺陷重开 + 根因待定）
> 状态：**未修复**。本记录的作用是撤回一条错误的「已验证闭合」结论，
> 并把已知事实固定下来，避免下一个人基于假前提继续。

## 构思

### 为什么要单独记一次「没修好」

`2026-11-15-kmod-vma-refcount-and-rtt-hotpath.md` 的第「一」节写着
**「kmod 修复已在真机验证闭合（计数可逆、rmmod 成功）」**。
这句话是错误的，而错误的验证结论比没有结论更危险：

- 没有结论 → 下一个人会去查；
- 有错误结论 → 下一个人会认为这块已经干净，转去查别处，
  于是每次都在同一个坑里绕。

所以本记录的第一目的是**撤回**，而不是新增。

### 错误是怎么产生的

先看清楚当时到底验了什么。原记录的证据链是：

1. `rmmod` 旧版（基线计数已为 0，所以这一步**本来就会成功**，不构成证据）；
2. `insmod` 新版；
3. 跑探针：`mmap → fork → 子进程退出 → munmap`，重复 3 轮，计数回到 0；
4. `rmmod` 成功，`/sys/module/<name>` 消失。

第 4 步被当成了闭合判据。问题在于它是一个**单次**观察，而且是在计数器
从未进入下溢状态的前提下做的。真正的闭合判据应该是：

> 在多轮真实使用（含 fork 继承映射、多段 munmap 拆分）之后，
> 计数仍能与首次映射前对齐，并且 `rmmod` 仍然成功。

单次 `rc=0` 只能证明「这一次没坏」，不能证明「不会坏」。

### 复现事实

同日晚些时候，使用**同一份 .ko**（MD5 与构建产物逐字节一致，排除了
「部署了旧文件」这一可能）复测：

```
/sys/module/weaknet_cpu_stat/refcnt   → -1        （干净启动约 17 分钟后）
dmesg                                 → WARNING ... module_put
                                               lr : wn_vma_close+0x20/0x30
```

`refcnt` 是 `unsigned int`，`-1` 即 `UINT_MAX`，说明 put 次数仍多于 get 次数。
调用栈直接落在我们自己的 `wn_vma_close()` 上。

## 实现方式

**本次没有修改代码。** 原因：根因尚未定位到可验证的假设，而在
「不知道哪里多 put 了一次」的状态下改 `.open`/`.close`，只会把下溢
从 17 分钟推迟到另一个时长，然后再次被误判为已修复——这正是上一次
发生的错误。

已排除的方向：

| 假设 | 排除依据 |
| --- | --- |
| 部署了旧版 .ko | MD5 与构建产物逐字节一致 |
| 修正没生效（漏编译某个模块） | 两个模块均重新交叉编译，vermagic 校验通过 |
| `mmap` 内联 get/put 未删净 | 已复查源码，`wn_mmap()` 内无 get/put |

仍待验证的方向（未做，需单独排期）：

1. **`file_operations.mmap` 之外还有没有 put 路径**：例如错误返回分支上
   先 `wn_vma_open()` 后 `remap_vmalloc_range()` 失败，是否会留下一次
   无配对的 get，或反之；
2. **`vma->vm_ops` 被覆盖**：若有其它路径重设 `vm_ops`，我们注册的
   `.close` 可能被绕过而 `.open` 照常执行；
3. **`fork()` 之外还会复制 vma 的路径**：`mremap`、`vmsplice`、
   以及 `munmap` 把一段拆成多段时，`open`/`close` 的调用次数是否
   仍然严格 1:1。

### 为什么这一条必须用「多轮」判据

本案的关键教训不是「内核 vma 语义难」，而是**验证判据设计错了**。
下溢是累积型故障：它需要 put 次数超过 get 次数若干次才显现。
任何单次操作后的计数检查，都无法区分「配对正确」与
「每轮多 put 一次但还没减到 0」。

可用的判据形态（下次照此设计）：

- 让模块计数在**每一轮**结束时回到同一个基线值，而不是只看最后一轮；
- 至少覆盖 100 轮 `mmap → fork → 子进程退出 → munmap`；
- 判据是「每轮基线不变」+「全部结束后 `rmmod` 成功」，两者缺一不可。

## 结果

- **问题状态：开放。** `weaknet_cpu_stat` / `weaknet_softirq` 在干净启动后
  约 17 分钟内仍会进入 `refcnt=-1`，内核被 taint 成 `G O`，
  模块无法卸载。
- **原记录的闭合结论已撤回**，原文顶部加注失效声明并指向本记录。
- **生产影响有限但真实**：计数下溢本身不破坏数据面（共享快照页仍可读），
  代价是不能 `rmmod`（升级必须重启整机）+ 每次 `execve` 刷一条
  `WARNING` 污染内核日志。因此定级为「需修但不紧急」，
  优先级低于当前正在排查的摄像头无帧。
- **运维规避**（当下可用）：需要换模块时直接重启板子，不要依赖 `rmmod`。

## 遗留

1. 三个待验证方向均未做，需要单独排期；定位前不要再动
   `.open`/`.close` 的配对逻辑。
2. `2026-11-15-kmod-vma-refcount-and-rtt-hotpath.md` 里那张
   「计数构成已逐项核对」的表（`open()` +2 / `mmap()` +1 / `munmap()` −1 /
   `close(fd)` −2）与跨进程复验数据，在**单轮**意义上是自洽的；
   但正因为它自洽，才掩盖了累积偏差。引用它时要注明「单轮，不足以证明闭合」。
