# 事故构造工具与留证上行接线缺陷修复

> 日期：2026-11-15
> 分类：工作流外实施
> 结果：已完成

## 构思

### 要解决的问题

区域事故的触发门槛是产品定义写死的：同一现场至少 2 台设备在关联窗口内同时
出现合格异常，且受影响比例不低于 30%。这是「一台设备坏了」与「这一片无线
环境出了问题」的分界线，不能为测试放低。

后果是单网关、周边设备稀少的现场永远凑不出一次真实事故。而留证链路
（事故 → 回溯预录 → 切片 → 签名分片上传 → 云端入库）的价值全在事故真的
发生那一刻。没有事故，那条链路在单测之外从未被完整走过，第一次运行就是真
出事那次，等于从未拥有过这个能力。

### 备选方案与取舍

方案一，调低生产阈值做测试。直接否决：改判据等于改产品定义，测试通过之后
现场还是拼不出事故，问题只是被藏起来。

方案二，往关联器对象里注入一个 SiteIncident。否决。理由是这个做法绕过了
「什么算事故」的全部判定——QualifyingAnomalyPolicy::qualify()、双门槛、
活跃分母，验完仍然不知道生产代码会不会自己开出一场事故。它证明的是注入
成功，不是判定正确。

方案三，写一个命令行工具，往事实表写合格异常，再让生产代码自己去判定。
采用。工具不含任何判定逻辑，它只往 device_events 写事实；判定、聚合、
持久化、触发留证每一步都走生产代码。

### 不走 OpenSpec change 的理由

没有新的产品表面：工具是开发期验证器，不进入部署产物、不改变任何现有接口与
运行时行为。生产改动只有一处缺陷修复，且缺陷本身已由运行态证据锁定，不存在
需求歧义。按仓库约定，这类工作走工作流外实施并留本记录。

### 三条必须守住的边界

不伪造已有事故：只写 device_events，绝不写 site_incidents 或
site_incident_events。事故行只能由关联器自己产出。

不改生产阈值：不读也不写 incident_min_devices 等配置。门槛不够就多造几台
设备，绝不放松判定标准。

事件可甄别：构造事件带 forge 事件号前缀与 INCIDENT_FORGE 来源标记，任何人
查库都能一眼分清哪些是构造的、哪些是真实采集。

## 实现方式

### 新增：tools/weaknet-incident-forge

单文件 Python，无第三方依赖，板端 python3 3.9 即可运行。

机制分四步：写 N 条合格异常到 device_events → 经 D-Bus 重启 bt_events 插件
→ 插件启动时的 recoverFromStore() 按生产逻辑回放事件、用 observeLocked()
重新推导事故 → 巡检线程发现活跃事故后触发录制与上传。

关键决策：

- 事件写成「现在减 8 秒」。recoverFromStore 只回放最近
  （关联窗口 + 静默窗口）内的事件，默认 120 秒。退 8 秒既远早于插件重启
  时刻，又远在窗口内部，两头都有余量。
- 写入前读该现场最近一次 resolved_at_ms 作为回放左边界。上一轮构造的事故
  结案后，任何早于它的新事件都会被静默跳过，表现为「写进去了但事故没出现」。
  撞上就拒绝执行并提示还要等多久，绝不硬写一版注定被忽略的数据。
- 设备地址用 02:00:00:00:00:XX（本地管理地址段）。真实厂商设备永不使用这
  一段，因此即便有人把构造数据误当真实采集，地址段本身就是提示。
- 事件类型与原因码混合 LINK_DISCONNECTED/CONNECTION_TIMEOUT 与
  LINK_DEGRADED/OTHER，覆盖 qualify() 的两条分支；地址类型交替 BREDR 与
  LE_PUBLIC，覆盖复合设备键。
- 报文用 repr() 内联进远端源码，不走 argv 也不走 stdin 第二条流。前者会被
  远端 shell 二次解释，后者不存在——python3 接 - 时 stdin 整条都是源码。
- 观察点放在**云端**而不是板端。板端没有 video_clips 表，片段记录只在云端
  落库。初版在板端查表，把每一次成功上传都报成了「未观察到留证片段」。
- --watch 不只报状态，还下载已拼装码流核对 sha256 与 NAL 结构。sha256 一致
  只证明字节没被改，不证明那些字节是可解码的视频；缺 SPS/PPS/IDR 的码流能
  完美通过校验和却解不出画面。

写库与清理必须提权：库是 WAL 方言，写事务要同时拿到 -wal 与 -shm 的写权限，
而这两个文件属主是 root（服务以 root 运行）。以普通用户写入在第一次写事务就
被拒，报的却是 attempt to write a readonly database——文件本身可写，是配套
文件不可写，这句话极具误导性。

### 修复：server/src/server.cpp 与 server/include/server.hpp

真实缺陷：编码线程在启动时捕获了 ctx.video_clip_exporter.get()，而上行器要到
启动流程后半段才创建。捕获那一刻必然是 nullptr，于是每一段片段都落进
「上行器未启用」分支被静默丢弃。事故、录制、日志全都正常，只有上传永远不
发生，且日志里看不出这是接线问题。

修法：新增原子槽位 video_clip_exporter_slot，上行器 start() 成功之后发布、
stop() 之前撤下；编码线程通过槽位取当前实例。不用裸指针直读 unique_ptr，
是因为那是非原子写，与编码线程的读构成数据竞争。

只在 start() 成功之后发布也是刻意的：start() 失败时内部停止标志仍是未置位
状态，此时发布会让入队照常接收片段，而背后没有任何消费线程——队列涨到上限
再开始丢，比直接不接收更难归因。

同时把入队失败的日志按原因分开（队列已满 / 上行器未创建或已停止），并按
片段记录字节数。原先两种情况共用一个含糊措辞，正是这次缺陷没能被一眼看出的
原因之一。

### 顺带修正

tools/weaknet-incident-forge 的文档与帮助文本原写「sudo 运行本工具」。实测
在云端开发机上外层 sudo 会让 ssh 改用 root 的 known_hosts 与密钥，ssh board
别名随即失效，报 Host key verification failed——看起来像板子掉线，实际是
身份被换了。已改为：需要提权的三步由工具在远端自行 sudo -n，调用方保持普通
用户。

### 验证手段

- x86 编译通过；test_video_clip_exporter_gtest 26 项全过。
- ARM64 交叉编译通过；tools/ci.sh 部署到开发板成功，板端测试通过。
- 板端二进制与本地 build-arm64-native 产物 md5 一致，确认部署的就是修好的
  那一份。
- 端到端一条命令跑通：事故开出 3 台受影响设备 → 检测到活跃事故并开始录制
  → 视频留证已入队 → 开始上传 → 上传完成 → 云端 state=COMPLETE。
- 云端取回载荷核对：95462 字节，sha256 与清单声明一致，NAL 单元 610 个，
  含 SPS/PPS，IDR 23 个，首个 NAL 是 SPS。

### 遗留问题

- 事故是「构造事实 → 生产判定」得来的，物理世界的真实异常（真实设备掉线
  造成的区域事故）仍未被观测到。
- 上传重试与队列背压两条路径没有被施加压力，目前只验证了单分片成功路径。
- 云端分片仍存在内存对象存储，排练服务重启即丢分片；元数据在数据库里存活。
  这是排练环境的已知边界，换成持久对象存储属于另一项工作。
- 片段是裸 Annex-B H.264 码流，没有封装成 MP4。这是链路现状的事实，不是本次
  缺陷；容器化与网页播放器仍是未做的部分。

### 是否值得升格为 OpenSpec change

不建议。工具是开发期验证器，不进部署产物；缺陷修复已由运行态证据闭环，没有
新的产品表面需要规划。若将来要做「真实异常自动触发 + 重试与背压压力验证」，
那才涉及新的判定与可靠性设计，届时应走正式流程。
