# Kickoff: 新功能与新工作全景技术立项

当用户提出想实现一个新功能、新增监控器、扩展 eBPF 探针、重构架构或开启任何一项新工作时，调用此技能。

<HARD-GATE>
**严禁直接写代码或立即创建分支**。
此技能的核心目标是：**先建立全局技术视界与现状事实，再输出结构化构思方案，等待用户评估决策**。
</HARD-GATE>

---

## 阶段一：定向探索与上下文建立

不要仅凭记忆猜测代码，必须主动使用 `Grep`、`Read`、`Bash` 定向阅读真实源码，梳理与新需求交织的上下游调用链路。

需重点扫描：
1. **现有功能实现**：仓库中是否已有类似、同名、或同探针的数据流？
2. **生命周期中枢**：`server/src/server.cpp`、`MonitorManager`、`ServerContext`、`IMonitorPlugin` 如何托管该类能力？
3. **数据流通道**：指标是否进入 `MetricsRegistry`？是否经由 `EventManager`、`DbusService`、`libweaknet.so`？
4. **测试与模拟**：已有测试用例（`server/test/unit/`）是如何针对同类模块编写 mock/fixture 的？

---

## 阶段二：标准化全景输出（必须涵盖以下四大板块）

Agent 必须严格按照以下结构输出自然语言技术立项报告：

### 1. 业务与系统背景定位（Project Context & Motivation）
- **核心定位**：该新工作在整个弱网监控与诊断系统（eBPF + D-Bus + Assurance + Web SPA + AI RAG）中属于哪一层？
- **业务价值**：解决什么真实物理环境/协议层网络痛点？（例如：内核丢包归因、无线干扰、传输延迟抖动、进程网络归属等）。
- **与既有体系的关系**：是独立扩展、对旧链路的升级，还是填补未监控空白？

### 2. 关联代码文件与具体实现现状（Codebase Audit & Ground Truth）
逐个列出与新工作直接相关、潜在耦合或需要适配修改的代码文件，**格式统一**：
- **`文件路径:行号范围`**（必须可点击跳转）：
  - **当前职责**：该文件当前实现什么逻辑、持有谁的指针、注册了什么线程或结构体。
  - **具体接口与关键符号**：列出具体的 class、struct、方法名、枚举值。
  - **耦合与影响分析**：若在此处接入新工作，是否存在锁竞争（如 `iface_mutex_`）、生命周期陷阱、内存开销或跨架构约束。
- **关联测试资产**：列出涉及的单元测试文件与目前验证覆盖情况。

### 3. 新工作技术构思与落地思考（Technical Conceiving & Design）
- **架构方案设计**：
  - 若涉及 eBPF：挂点选择（kprobe / fentry / tracepoint）、CO-RE 兼容性、BPF map 类型（Hash / RingBuf / Array）。
  - 若涉及核心服务：数据如何注入时序仓（`MetricsRegistry`）、是否定义新的无状态评估器（SLE Evaluator）或归入已有 Evaluator。
  - 若涉及 IPC/对外暴露：D-Bus 方法签名（方法名/参数/返回类型）、信号 payload 格式或 CLI 命令集成。
  - 若涉及 Web 前端：图表形式（时序图/雷达图/卡片指标）、API 适配层。
- **关键权衡（Trade-offs）与边界考量**：
  - 至少列出 2 种可能的实现路径，并对比性能损耗、代码侵入度、维护成本。
  - 指出不可踩的雷区（如 ARM64 交叉编译差异、D-Bus 线程安全、vmlinux.h BTF 依赖）。

### 4. 推荐实施路径与里程碑建议（Next Actionable Steps）
- **第 1 阶段（底层数据源/eBPF/采集）**：最小闭环验证步骤。
- **第 2 阶段（服务端集成与生命周期）**：插件注册与时序注入。
- **第 3 阶段（对外接口与展示）**：D-Bus 适配、CLI 及前端联动。
- **第 4 阶段（自动化测试）**：x86 Google Test、ARM64 容器编译、开发板真机验证。

## 质量铁律（Guidelines）

1. **事实优先**：严禁“幻觉引用”不存在的文件或函数。所有列出的符号必须真实存在于代码库中。
2. **遵守 Harness 约束**：新工作若为大型核心变更，提醒用户是否需要通过 OpenSpec 变更管理或 TDD（RED-GREEN-REFACTOR）流程实施。
3. **架构一致性**：新模块设计必须遵循本项目的黄金原则——优先复用、最小可验证闭环、明确单一真值来源。
