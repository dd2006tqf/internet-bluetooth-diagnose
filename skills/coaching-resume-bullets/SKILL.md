# Coaching Resume Bullets: 简历分点面试辩护准备

## 这是什么

把一句简历分点，先还原成一份**与听众无关的技术知识骨架**，再投影成两种面试现场的表达，最后用压力测试验证它经不经得起追问。

用户的目标是掌握**知识架构**与**项目全景**，不是背代码。因此本技能**不做逐行代码讲解**——那是 `code-explainer` 的职责。

核心信条：**两种面试官不是两套知识，是同一份骨架的两次投影。** 准备两份稿子的人，交叉追问时事实会对不上。

## 输入

用户在技能名之后跟一句简历分点原文。一次只处理一个分点。

可选开关：

| 写法 | 行为 |
| :--- | :--- |
| 默认 | 输出第 0~6 段，然后停在第一问，进入交互式 drill |
| `--offline` | 第 7 段改为一次性输出题集，答案后置 |

---

## 前置：证据核对（必做，不得跳过）

在输出任何内容前：

1. 读 `弱网项目简历知识库.md` 中与该分点对应的条目。
2. 断言涉及具体实现时，用 `Grep` / `Read` 核对代码事实。
3. 找不到证据的断言，**必须**标注为「不可主张」并写明缺什么证据。

**不得凭记忆编造项目事实。** 也不得把行业通用知识伪装成本项目做过的事。

---

## 输出结构（固定八段）

### 第 0 段：断言拆解

简历句子几乎总含有 1~2 个经不起追问的词。先拆成原子断言。

| 断言 | 判定 | 依据 | 现场怎么说 |
| :--- | :--- | :--- | :--- |

判定三档：

- **可主张** —— 有证据，原样讲。
- **需限定** —— 有证据但范围被夸大，必须补条件才讲。
- **不可主张** —— 无证据，换措辞或干脆不提。

判定为「需限定」的，本段必须给出**限定后的完整句子**，让用户直接可用。

### 第 1 段：知识骨架

输出一张文字版依赖图，至少三层。**这一段的产物是「侃侃而谈」的真正来源**：用户随时知道自己在图上的哪个位置。

要求：

- 节点用**领域通用概念**命名，不是项目里的类名、函数名。
- 每个节点后给一句「这个节点被问到时，核心答案是什么」。
- 项目只做锚点标注：`↳ 本项目落在 …`，一句话即可。
- 必须标出节点之间的**依赖关系**（谁决定谁），这是追问会走的路径。

### 第 2 段：主线叙事

两个长度，都按**决策链**组织，不按功能列表罗列。

- **90 秒版**：5 步，每步一句。结构是「为什么需要 → 怎么解决 → 关键取舍 → 怎么保证 → 结果边界」。
- **30 秒版**：3 句。开场结论、一个取舍、一个边界。

禁止写成「我做了 A，还做了 B，还做了 C」。

### 第 3 段：双视角渲染

**外行版**（面试官不了解这个项目，甚至不熟这个技术领域）：

- 开场一句：从**收益**说，不从技术名词说。
- 三个要点，每点一句，允许用类比。
- 收尾一句：落回「所以它能解决什么问题」。
- 禁忌：术语堆砌、报未验证的数字。

**行家版**（面试官技术栈对口）：

- 开场一句：直接给结论 + 选型。
- 取舍 2~3 个：每个都是「为什么是 X 不是 Y」。
- 边界一句：主动交出一个不成立的条件。
- 收尾一句：指向证据或验证方式。

两版的事实必须完全一致，只是投影角度不同。写法规则、反例与自检清单见 `references/rendering-guide.md`。

### 第 4 段：追问树

三条轴，每条轴三层。每条轴一张表：

| 层 | 面试官会问 | 你答（≤3 句） |
| :--- | :--- | :--- |

要求：

- 每一层的答案必须**能独立成句**——面试官可能只问一层就跳走。
- 第三层通常是「你怎么证明」或「换个极端条件还成立吗」。
- 轴的选取与升级规则见 `references/depth-axis.md`。

### 第 5 段：红线清单

这个分点上**不能说的话**。性价比最高的一段。

| 不能说 | 为什么 | 改成 |
| :--- | :--- | :--- |

红线优先收录：绝对化表述、未实测的数字、把通用能力说成本项目成果、把边界说没有。

### 第 6 段：速记卡

考前五分钟看的一页纸。只保留：

- 骨架图顶层四个节点名
- 每条轴一行（该轴的第三层问题）
- 三条红线

不得重复前几段的完整内容。

### 第 7 段：drill（压力测试）

**默认交互式。** 输出完第 0~6 段后立刻进入面试官角色，只问第 1 问，然后停。

规则：

1. **一次一问。** 问完必须停，等用户回答。禁止自问自答。
2. **不纠正、不鼓励、不解释。** 用户答完，直接给下一问。
3. **按回答质量分支：**

   | 用户回答 | 动作 |
   | :--- | :--- |
   | 答在点上 | 升一层，问该轴的下一层 |
   | 含糊、用术语糊弄 | 抓回来，要求给具体例子或定义 |
   | 像背书 | 换条件，问变体 |
   | 答错 | 不纠正，继续施压，让矛盾自己暴露 |
   | 说「不会」「不清楚」 | 记下，跳到下一条轴 |

4. **三层到顶就换轴。** 三轴走完结束。
5. **全程不泄露答案。** 用户答错也不给正确答案——那是第 4 段的事。泄露一次，这次 drill 就废了。

**结束后的复盘表：**

| 轴 | 层 | 判定 | 问题 | 修法 |
| :--- | :--- | :--- | :--- | :--- |

判定只有三档：**过 / 险 / 翻车**。只指出会翻车的地方，不做鼓励式点评。最后给一句总评：这套答案在第几层会崩。

**`--offline` 变体：** 先列全部问题（8~12 问，按轴分组，只有问题没有答案），再给一条明确的分割线与警告，最后才列答案与判定标准。

## 硬规则

1. **不报没测过的数字。** 没有实测就说「没做过量化」，并给出「该怎么测」。编数字是唯一不可修复的错误。
2. **每条断言必须可回溯。** 指不到知识库条目或代码事实的，降级措辞或标为不可主张。
3. **不出现代码行号、函数名、源码片段。** 除非该符号本身就是锚点，且只出现一次。
4. **每层答案独立成句。** 任何一段被单独拿走都能听懂。
5. **主动交边界。** 行家面前，先说「这在 X 情况下不成立」，比被问出来强十倍。
6. **两版事实一致。** 外行版和行家版不得出现互相矛盾的陈述。
7. **默认中文。** 用户说明有英文面试时，只在第 3 段补英文开场句，不重写全文。
8. **纯 Markdown 正文。** 不出现 HTML 实体转义（`&gt;` `&lt;`），不把整段答案包进代码块。

## 反模式

| 反模式 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 按功能列表罗列 | 听起来像流水账，无法应对取舍追问 | 按决策链组织 |
| 把知识库原文抄进输出 | 用户背不下来，且抓不到结构 | 只输出骨架与投影 |
| 讲解代码实现 | 违背用户目标，且面试不考这个 | 项目只作锚点 |
| drill 时心软给提示 | 压力测试失效 | 一次一问，不给答案 |
| 追问树写成问答百科 | 用户误以为自己会了 | 三层封顶，每层一句话 |
| 虚构实测数据 | 面试现场被追穿，无法挽回 | 明说没量化并给测法 |

## 与其它技能的分工

- `code-explainer`：逐行代码教学。本技能不碰代码细节。
- `kickoff`：新功能立项。本技能不做设计推导。
- `brainstorming`：需求探索。本技能只处理已成文的简历分点。
