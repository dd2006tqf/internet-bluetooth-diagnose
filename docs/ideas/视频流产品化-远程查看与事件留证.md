# 视频流产品化：远程查看与事件留证

> 状态：孵化中（2026-11-12 记录）
> 定位：**产品功能**设想的孵化，不是诊断能力的一部分

## 一句话摘要

把边缘网关采集到的画面编码后传到云端，让远端运维能实时查看现场、并在事故发生时回看录像。

## 动机/痛点

当前产品的视频能力只做到「采集 + 归因」：`V4l2FrameSource` 采帧，
`VideoQoeAttribution` 判断画面好坏。但**画面本身没有出口**——
远端运维只能看到「画面卡了」这个结论，看不到「卡成什么样」。

`docs/产品定位-工业无线诊断网关.md` 第三节之二已经写：

> 远端 Web 看到的是汇总趋势，现场人员看到的是"画面卡了"这一手事实

**如果画面能传到远端，这个闭环才真正闭合。** 目前只有现场人员能看到，
远端只能读数字。

这个设想回答的是一个产品问题：**网关除了告诉运维"哪里出了问题"，
能不能也让他"亲眼看到问题"？**

## 初步技术方案

### 分层：先把「测网络」和「传视频」彻底分开

这两件事常被混为一谈，但它们的需求相反：

| 目标 | 推荐做法 | 为什么 |
| --- | --- | --- |
| 判断网络质量 | eBPF 合成流量 | 视频编码引入的 CPU 抖动、关键帧突变会**污染**网络测量 |
| 传输视频 | 编码 + 封装 | 目标是把画面送到对端，与测量无关 |

**测网络不需要视频栈。** 现有的 `kmod/flow_rate.bpf.c`
（`kprobe/ip_queue_xmit` / `kprobe/udp_sendmsg` + `kprobe/tcp_retransmit_skb`）
已经能给出「这个进程发了多少、重传了多少」。

### 传输路径：绕过云安全组的入方向限制

2026-11-12 实测结论（**这条是关键约束**）：

| 板端 → 服务器公网端口 | 结果 |
| --- | --- |
| `81.71.76.133:22` | ✅ OPEN（反向隧道在用） |
| `81.71.76.133:4000` | ✅ OPEN（防火墙显式放行） |
| `81.71.76.133:18999` | ❌ **超时** |

宿主机 iptables 的 `INPUT` 策略是 `ACCEPT`，且没有任何 18999 规则，
所以拦截来自**云厂商安全组入方向**。这意味着：

**不能假设「板端主动推流到服务器某个端口」是可行的**——除非先在
云控制台开放端口，或复用已有出站通道。

> **2026-11-14 更新**：已在云控制台放行 `8000`，板端直连
> `81.71.76.133:8000` 实测可达（未签名请求返回 401 而非超时），留证上行走的
> 就是这条路。所以方式 1 已落地，方式 2/3 不再需要。
>
> **2026-11-15 订正（重要）**：上面这条当时只是「探针可达」的结论，
> **生产配置并没有跟着改**。`edge.url` 一直写着 `http://127.0.0.1:8000/...`，
> 而板端 8000 上**没有任何常驻监听**——`weaknet-tunnel.service` 只做
> `-R 22222`，从不转发 8000（2026-11-10 事故后刻意移除，见该 unit 注释）。
> 于是遥测、无线事件、留证三条上行在生产上**全部必然失败**，症状是
> `Couldn't connect to server http=0`，且因为设备侧一切正常而极难定位。
>
> 已于 2026-11-15 改为直连公网并显式开 `allow_insecure_http: true`
> （非回环明文 HTTP 会被 `weaknet_config.cpp:538-563` 拒绝加载）。
> 云端 uvicorn access log 实测持续收到 `POST /edge/telemetry`、
> `POST /edge/wireless-events` 均 `200 OK`。详见
> `openspec/tasks/2026-11-15-edge-url-cloud-direct-and-capture-race.md`。
>
> 代价是**明文过公网**：Ed25519 签名保证完整性，不保证机密性。要收紧应上
> TLS 反代，而不是继续加开关。

可行的三条路：

| 方式 | 做法 | 代价 |
| --- | --- | --- |
| 1. 开放端口 | 云控制台放行一段端口区间 | 需人工操作；暴露新攻击面 |
| 2. 复用出站 HTTPS | 视频 chunk 走已有的 `EdgeWirelessUplinkExporter` 通道 | HTTP 是请求-响应模型，跨公网 RTT 234ms，实时性极差；丢包被 TCP 重传掩盖，**看不到真实丢包** |
| 3. 板端主动拉取 | 云端下发「拉流指令」，板端反向隧道连通后云端主动拉 | 需要云端发起连接，仍受入方向限制 |

**方式 2 只适合「留证」，不适合「实时查看」**，因为 TCP 会把丢包转化成延迟，
正好抹掉我们要观测的信号。

留证最终选了**方式 1**（板端主动 HTTPS POST 到 8000 的 `/edge/video-clips`），
而不是改进方式 2 的既有通道：留证不是实时流，请求-响应模型完全够用，而
`EdgeWirelessUplinkExporter` 是遥测专用的（单次 JSON、无分片、无幂等），
把 256 MiB 的码流塞进它会污染遥测链路的失败语义。

### 数据量：这是决定产品形态的硬约束

实测：1640x1232 NV12 裸流 = **54 MiB/s**；编码到 2000 kbps 后：

| 场景 | 数据量 | 产品含义 |
| --- | --- | --- |
| 实时查看（不存） | 只占带宽 | ✅ 可行，但需持续连接 |
| 事件触发留证（异常前后 90s） | 约 22 MB/事件 | ✅ **推荐形态** |
| 7×24 全量录像 | **21.6 GB/天/路** | ❌ 变成 NVR，不是诊断网关 |

**全量录像会让产品滑向 NVR（网络录像机）**，那是完全不同的品类，
也是 `docs/产品定位-工业无线诊断网关.md` 第二节明确要避免的「范围失控」。

推荐形态是**事件触发留证**：`SiteIncident` 已经记录了事故时间点，
视频只需围着那个时间窗保留（如异常前 30 秒 + 后 60 秒）。
这样与现有事故模型天然对齐，且不产生持续存储成本。

### 技术栈：不一定需要 ffmpeg / RTMP

| 需求 | 推荐 | 不推荐 |
| --- | --- | --- |
| 事件留证 | 调 `ffmpeg` **命令行**封装（`-c copy` 不重编码） | 链接 `libavformat`；`gst mp4mux`（实测不可用） |
| 远端实时查看 | WebRTC（首选）或 HLS | **RTMP**（Flash 时代产物，现代浏览器已不原生支持） |
| 测网络 | eBPF | 视频推流 |

板端已有 `x264enc`（gst 插件，实测 `speed-preset=ultrafast` 可达
36.81~42.19 fps，采集侧真实 18.12 fps，约 **2 倍余量**）。

引入 ffmpeg 的成本：Bullseye sysroot 里补 ffmpeg 及全部依赖、
glibc 2.31 硬约束、构建体系分叉。**在 `mp4mux` 能用的情况下没有收益。**

> **订正（2026-11-15，据实测）**：上两段把「引入 ffmpeg」的成本算成了
> **链接**库的成本（sysroot、glibc、构建体系），而实际采用的是调**命令行**——
> 两者完全不同。板端因 `gstreamer1.0-libav` 早已装齐全部 `libav*` 运行时库，
> 装 `ffmpeg` 只多两个包，构建体系一行不用改（二进制里不链接任何 `libav*`）。
>
> 而 `mp4mux` 在这条链路上**做不到**：它硬性要求输入 buffer 带 PTS
> （`Buffer has no PTS`），而硬件编码器吐出的是裸 Annex-B，没有 PTS/DTS。
> `avmux_mp4` 能收，但会把 616 帧全压到同一个时间戳（`duration=0.006s`），
> 产出「文件能打开、内容全错」的结果——比失败更糟。
>
> 实测 `ffmpeg -framerate N/D -i - -c copy` 方案：570 帧产出
> `duration=22.800000`、`avg_frame_rate=25/1`、全量解码 `rc=0`，
> 单次封装约 0.26 s。详见 `openspec/tasks/2026-11-15-mp4-muxing.md`。

## 涉及的工作线：面板与推流是同一件事

**这两个需求不是两条独立的功能，而是同一个「帧分发」能力的两个消费者。**
把它们当成两件事分别实现，会各自去抢 `/dev/video0`（板端实测该节点在 `open()`
层面独占，见下「为什么必须单一所有者」），最后必然有一个失败。

统一后的形态：

```
                     ┌──────────────────┐
   /dev/video0  ───▶ │  V4l2FrameSource │  ← 唯一所有者（独占 open）
   (独占)            └────────┬─────────┘
                              │ pixel_sink 回调（采集线程内，一次拷贝）
                              ▼
                     ┌──────────────────┐
                     │  VideoFrameHub   │  快照槽位 + 租约（fd/slot 分离）
                     └───┬──────────┬───┘
              acquire(fd)│          │acquire(fd)
                         ▼          ▼
                   ┌─────────┐  ┌──────────┐
                   │ Qt 面板 │  │ 编码/推流 │
                   │ 本机显示│  │ RTMP/WebRTC│
                   └─────────┘  └────┬─────┘
                                     │ 推流行为本身
                                     ▼
                              ┌──────────────┐
                              │ 网络场景判定 │
                              └──────────────┘
```

三条由此得出的结论：

1. **面板先落地**（✅ 2026-11-14 已完成）：它是中枢的第一个真实消费者，能在
   不引入编码器/网络的前提下把「采集 → 分发 → 渲染」整条链路验证通。面板通了，
   推流只是换一个消费者。
2. **推流复用同一条 fd 通路**：中枢给的已经是 dma-buf（板端实测
   `backend=dma-heap`），可以零拷贝交给硬件编码器；软件 x264 则需一次读取。
3. **网络场景判定不能靠「推流成功/失败」这种二值信号**：帧率、码率、重传、
   抖动要分开看，且必须与 `FrameStats`（采集侧事实）区分开——否则又会把
   「编码器跟不上」记成「网络差」，与本文档第 28 行那条分层原则冲突。

### 为什么必须单一所有者（板端实测）

`/dev/video0` 在 `open()` 层面独占：A 仅 `open` 成功，B 紧随其后 `open` 得到
`EBUSY`，**只读 `open` 也独占**；而 `video1/4/5` 可同时打开，说明是按节点独占
而非全局。所以面板/编码器**都不能自己打开摄像头**，必须由所有者分发。

### 为什么不能把采集 buffer 的 fd 直接给消费者

看似最零拷贝，但消费者持 fd 时间一长 → 4 个采集 buffer 全被占住 → 驱动无处
入队 → **驱动丢帧** → `FrameStats` 把它记成链路丢帧。

而这条链路的全部意义是**判断链路质量**。把「消费者读得慢」记成「链路劣化」，
等于观测缺陷栽给被观测对象。所以中枢另开一组快照槽位，拷一次（3MB，A55 上
约 1ms），换取采集侧与消费侧生命周期彻底解耦。

### 帧内存布局：任何消费者都必须按事实值读，不能推导

2026-11-14 在板端把 sunxi-vin 的 NV12 布局钉死（1640x1232，`sizeimage=3045504`）：

| 区段 | 范围（字节） | 说明 |
| --- | --- | --- |
| Y 平面 | `[0, 2020480)` | stride = **1640** = width，无行填充 |
| 对齐空洞 | `[2020480, 2030336)` | 9856 字节，实测全零 |
| UV 平面 | `[2030336, 3040576)` | stride = 1640，616 行 |
| 尾部空洞 | `[3040576, 3045504)` | 4928 字节，实测全零 |

两条必须记住的结论：

1. **`bytesperline` 报的 `2460` 是假值**：`2460 × 1232 × 1.5 = 4546080 > 3045504`，
   装不下它自己的 buffer。真实 stride 是 `width`（行间距微扫在 pitch=1640 处取
   尖锐极小值 1.1795，其它偶数 pitch 都是 1.54~1.59）。
2. **UV 偏移不是 `stride × height`**：驱动按 16 对齐分配平面，中间夹着一整段
   空洞。所以 `uv_offset` 必须由生产者算好原样透传，**任何下游都不许推导**。
   若下游按 `stride*height` 去读 UV，读到的是空洞里的 0 → U=V=0 → 严重偏绿。

这条对推流同样成立：交给编码器前必须用事实值描述平面，否则编码器会逐行斜切
（stride 错）或整帧偏色（uv_offset 错）。

## 必须先回答的三个问题

1. **隐私边界**：工业现场画面可能涉密。上云前必须有明确的存储策略
   （加密？保留期？谁能看？）。这不是技术问题，是产品合规问题。
2. **接收端放哪**：云端（真实远端，需新增全套）vs 板内回环
   （只能证明编码能力，**测不到网络**）。两者价值差一个数量级。
3. **是诊断还是产品**：如果只是要「判断网络好不好」，
   eBPF + 合成流量就够了，不需要视频栈；如果要做「能看到画面」，
   才需要上述全套。
