## 一句话摘要

守卫现在能正确判断「采集服务健不健康」，但**它自己挂死时会静默地变成一次无归因的整机复位**，而且**确定性故障下会无限复位、把网关变成每 28 秒重置一次的砖**。本文档记录三项加固：给外部命令加超时、给连续复位加熔断、给磁盘加取证采样。

---

## 动机

### 现状里两个真实的盲区

现行实现的判据链是自洽的：四项判据全部通过才喂狗，任一持续失败即停止喂狗触发硬件复位。问题不在判据，在判据**周边**。

**盲区一：守卫自身会被外部命令焊死。**

`RunCommand()`（改动前位于 `tools/weaknet-health-guard.cpp:285`，现为 `:438`）**当时**用 `popen` / `fread` / `pclose` 执行命令，**没有任何超时**：

```cpp
FILE* fp = popen(cmd, "r");
size_t total = fread(buf, 1, cap - 1, fp);
int rc = pclose(fp);          // ← 子进程不退出，这里永久阻塞
```

两个调用点都在判据路径上：

| 调用点 | 命令 | 挂起条件 |
| :--- | :--- | :--- |
| `CheckSampleNs`（`:622` 调用点） | `busctl --system call ... GetEbpfMonitorHealth` | D-Bus daemon 卡死、服务端派发线程被 SQLite checkpoint 阻塞 |
| `GetMainPid`（`:730`） | `systemctl show -p MainPID --value` | systemd 自身卡住 |

挂起后的完整链条：`pclose` 永久阻塞 → 主循环不再推进 → 不再 `write(fd,"1",1)` → 硬件 16 秒超时 → **整机复位，而 `WriteFailureJson` 根本没被执行到**。

结果是「板子自己重启了，查不到任何原因」。这违反了看门狗的第一原则：**它把自己的故障伪装成了被监控对象的故障**。

顺带暴露两个被低估的问题：

- `fread(buf, 1, cap - 1, fp)` 读满 64 KB 就返回，随后 `pclose` 等子进程退出，而子进程正阻塞在写一个已满的管道上 —— 输出超限时同样死锁，与 hang 无关。
- 一个「慢但没死」的 `busctl`（比如 5 秒）会把实际判定周期从 2 秒悄悄拉长到 7 秒，`kDebounceK = 2` 去抖窗口的时间语义跟着漂移。判据没坏，但它承诺的时间是假的。

**盲区二：没有任何东西记得上一次启动是被守卫打掉的。**

| 机制 | 生命周期 | 复位后 |
| :--- | :--- | :--- |
| `RestartTracker`（`:964`） | 进程内存 | 归零 |
| `kTripFlag`（`:240`） | 跨进程 | **故意作废**（靠 `boot_id` 比对） |

`kTripFlag` 的 `boot_id` 设计是对的 —— 它保证「重启守卫无法撤销一次已判定的复位」。但它同时意味着**没有跨 boot 的记忆**。于是确定性故障下：

```
boot 1 → 判据失败 → 停喂 → 复位
boot 2 → 判据失败 → 停喂 → 复位     ← 一模一样
boot 3 → ...                        ← 无限
```

当根因是「配置写坏 / 数据库损坏 / 一次失败的 OTA」这类**复位解决不了的问题**时，网关变成一块每 ~28 秒重置一次的砖。更糟的是每次只活 28 秒，**远程隧道来不及建连**，人也进不去修 —— 这在产品上等于「必须派人到现场」。

## 初步技术方案

三项独立、可分别提交。风险从低到高排序。

### 一、`RunCommand` 超时（真缺陷修复，语义不变）

**不引入线程。** 外部评审常见的建议是「把判据放到独立线程跑」，这里明确不采纳：

- 线程化只是把阻塞挪走，**判据本身仍然可以永远得不出结论**；而看门狗在「无法判定」时必须按「不健康」处理 —— 那它照样需要一个超时。
- 一旦有了超时，单线程就够了。
- 多线程会引入「守卫卡死但喂狗线程还活着」这个最坏组合：**保护看起来在，判据已经死了**。这比现在更糟。

真正的解耦是「判据不得无限阻塞」，不是「判据换个线程」。

**实现要点**

```cpp
constexpr int kCmdTimeoutMs = 1500;
char* RunCommand(const char* cmd, size_t cap, int timeout_ms, int* out_rc);
```

内部流程：

1. `pipe2(fds, O_CLOEXEC)`；
2. `fork()`；
3. 子进程 `setpgid(0,0)` → `dup2(w, STDOUT_FILENO)` → `execl("/bin/sh","sh","-c",cmd,nullptr)` → `_exit(127)`；
4. 父进程 `setpgid(pid,pid)`（消除 `kill(-pid)` 的竞态）→ `close(w)` → `poll()` 循环，每次用**剩余时间**算 timeout；
5. 读到 EOF 或缓冲满 → 正常 `waitpid`；
6. 超时 → `kill(-pid, SIGKILL)` → `waitpid` 循环吃 `EINTR` → `rc = -ETIMEDOUT`；
7. 缓冲满但子进程还活着：继续 drain 到丢弃用小缓冲，直到 EOF（保住「截断但不死锁」）。

三个必须做对的细节：

| 细节 | 做错的后果 |
| :--- | :--- |
| 子进程 `setpgid` + `kill(-pid)` | 只杀 `sh`，孤儿 `busctl` 泄漏并继续占管道 |
| 父进程也 `setpgid(pid,pid)` | 子进程还没跑到 `setpgid` 就被杀，`kill(-pid)` 打空 |
| 看门狗 fd 已带 `O_CLOEXEC`（`:796` 已满足） | 子进程继承 fd，父进程死了 fd 还开着 → 内核不执行 `release()` → **复位永远不来** |

**超时值的预算推导**

```
kCheckCount(4) × kCmdTimeoutMs + kTickSeconds×1000 < 16000
       4 × 1500      +       2000          = 8000 ms  < 16000   ✅ 余量 50%
```

实际只有 2 个判据起子进程，真实最坏是 `2×1500 + 2000 = 5000 ms`。取 1500 ms 而非更小的 500 ms：板端 `busctl` 实测 25 ms，但 SQLite checkpoint 叠加 12 个 eBPF 程序时 D-Bus 应答可能抖到几百毫秒，1500 ms 是实测值的 60 倍，足够吸收抖动又不吃预算。

**超时后的判据语义**：算失败（`ok=false`，detail 写 `timeout`），交给现有 `kDebounceK = 2` 去抖吸收。单次抖动下一轮即归零；持续挂死约 10 秒后停喂复位，且这次 `WriteFailureJson` 会正常写出来。核心不变式：**无法判定 ≠ 健康**。

### 二、连续复位熔断（新保护层，改变出口集合）

**关键约束：这块板没有 RTC，启动初期系统时间在 1970 附近，NTP 校正会跳变。** 因此任何「最近 N 小时内触发过几次」的时间窗都不可靠。改用**连续启动次数**，不依赖时钟。

**数据结构**：`/var/lib/weaknet/health-guard-trip-history`，纯文本一行一次触发：

```
<boot_id> <reason> <unix_epoch_if_known>
```

- 触发时 append 一行并 `fsync`；
- 只保留最后 `kTripHistoryMax = 5` 行（读-截断-重写，文件几百字节）；
- 用 `boot_id` 去重：同一 boot 内重复触发不重复计数。

**判定**（启动时，必须在 `open()` 之前）：最后 `kTripBreakerThreshold = 3` 行的 `boot_id` 互不相同且都不是当前 boot → 进入熔断。

三个不同 boot 连续以触发收场 = 至少三次「判定不健康 → 复位 → 又判定不健康」。这不是偶发，是确定性故障。

**熔断模式做什么**

| 动作 | 理由 |
| :--- | :--- |
| **不 `open` 看门狗** | open 会 arm 硬件，进程一旦意外退出反而触发复位 |
| 退出码 **98**（新值） | 与 `kExitTripped = 99` 并列；`RestartPreventExitStatus=98 99` |
| 写 `/var/lib/weaknet/health-guard-rescue.json` | 记录进入原因、触发的 boot_id 列表、时间 |
| 每轮 `fprintf(stderr, ...)` | journal 里必须一眼看见「守卫已熔断，无硬件保护」 |
| 照常退出，不 `Restart` | 单元是 `Restart=no`，本来也不会重启 |

**清退方式**：人工删除 history 文件。与 `kTripFlag` 同一哲学 —— 自动机制无权推翻「系统已判定不健康」；同理，自动机制也无权推翻「保护本身正在制造故障」的判断，所以进入熔断后只有人能解除。

**健康复位**：正常运行满 `kTripHistoryResetSec = 30 分钟` 且期间未触发 → 清空 history 文件。一次偶发真实故障（比如内存瞬时耗尽）不会在很久之后的第二次故障上凑成「三次」。

**必须承认的取舍**

熔断模式下**没有硬件看门狗保护**。之后若发生真正的内核挂死，没有任何东西会复位它。

这是刻意的权衡：**「确定性故障下必然砖化的保护」<「偶发挂死时没人兜底的裸奔」**。一个每 28 秒重置的网关等于永久离线；一个能长期在线但少了兜底的网关，至少还能被远程修好。

> **需要产品侧确认**：如果定义是「宁可无限复位也不能失去看门狗」，那第二项只做计数与告警（写 JSON + 日志），不进熔断。技术上两种都成立，取决于这台设备在现网的可达性假设。

**改动清单**

| 文件 | 改动 |
| :--- | :--- |
| `tools/weaknet-health-guard.cpp` | 新增 `kTripHistory*` 常量、`ReadTripHistory()`、`AppendTripHistory()`、`BreakerOpen()`；`RecordTrip()` 内追加一行；`main()` 启动序列最前面插入熔断判定；健康时长达标后清空 history |
| `tools/weaknet-health-guard.service` | `RestartPreventExitStatus=99` → `RestartPreventExitStatus=98 99` |

### 三、磁盘水位：只做取证，不做判定

这一项**推翻了初稿设想**。原本想加第五项判据（磁盘剩余低于阈值即判不健康），重新推演后发现是错的。

**为什么不能当复位判据**

「磁盘满」是一个**复位无法修复的条件**。加进判据 = 磁盘满 → 停喂 → 复位 → 磁盘还是满 → 再停喂 → 复位。这正是第二项熔断要防的那种循环，自己却又造了一个。

更关键的是：**这个洞已经堵上了**。磁盘满导致 SQLite 写不进去 → WAL 的 `mtime` 停止推进 → `CheckWalMtime`（`kWalMaxAgeSec = 12`）失败 → 触发复位。判据 1 已经在覆盖它，只是归因不显式。

逐个核对「以为的漏洞」与实际情况：

| 原本以为的漏洞 | 实际情况 |
| :--- | :--- |
| 磁盘满 → 服务静默不落库 | **不存在**，判据 1 已覆盖（12 秒内发现） |
| 磁盘满 → 采集继续但数据丢 | 同上，会被判据 1 捕获 |
| 磁盘满 → 故障快照写不出来 | **确实存在**，但这是「证据丢失」不是「保护失效」 |

**真正剩下的价值是诊断性的**

`/var/lib/weaknet` 与 `history.db` 可能不在同一个文件系统上。如果根文件系统（放 `health-guard-tripped`、`health-guard-last-failure.json`）写满：

```cpp
void RecordTrip() { if (fd < 0) return; ... }          // 静默失败
void WriteFailureJson(...) { if (fd < 0) return; }     // 静默失败
```

`RecordTrip()` 失败意味着 trip flag 没写下 → 复位后没有任何记忆 → **第二项的熔断器也会跟着失效**。`WriteFailureJson` 失败意味着复位无归因。这是看不见的失效，最糟的一类。

**实现要点**

```cpp
/* 每轮采样，仅用于日志与故障快照，不参与 ok 判定 */
struct DiskWatermark {
    const char* path;
    unsigned long free_pct;      /* free / total × 100 */
    unsigned long avail_mb;
};
void SampleDisk(const char* path, DiskWatermark* out);   /* statvfs(3) */
```

采样两个路径：`/var/lib/weaknet`（证据与标记所在）、`/home/radxa/weaknet/data`（WAL 所在）。两者都写进故障快照：

```json
"disk": {
  "var_lib_free_pct": 41,
  "data_free_pct": 3,
  "warn": true
},
"action": "stopped_petting",
"hardware_timeout_s": 16
```

顺手把现有的 `"reset_expected_in_s": 16` 改名为 `"hardware_timeout_s": 16`。现在这个名字会让人读成「16 秒后板子就回来了」，而实测端到端是 ~28 秒 —— 不是同一条时间线，名字必须改。

日志侧：`free_pct < kDiskWarnPct(10)` 时每轮日志尾部加 `DISK_LOW data=3%`，并在 `RecordTrip()` 前后各采样一次（能看出触发瞬间是不是刚写满）。

**顺带的可见性修复**：`RecordTrip()` 与 `WriteFailureJson()` 现在静默失败，改为 `fprintf(stderr, ...)` 明确喊出「trip flag LOST，breaker will not see this boot」。不改变行为，只改变「故障是否可见」。

## 不做，以及为什么

| 项 | 结论 |
| :--- | :--- |
| 判据换线程 | 治不了「判据永远无结论」，却引入「喂狗活着、判据已死」的更坏组合 |
| pstore / ramoops | 需先取证 `CONFIG_PSTORE` / `ramoops` 是否存在，本次未查，不纳入 |
| pretimeout 预超时中断 | 已核实 `# CONFIG_WATCHDOG_PRETIMEOUT_GOV is not set` + `# CONFIG_WATCHDOG_HRTIMER_PRETIMEOUT is not set`，且 `/usr/src/linux-a733-5.15` 只是 1.4 MB 打包残留，**不可实现**，除非重编内核 |
| 双看门狗纵深 | 板上无外部看门狗芯片，纯硬件问题 |
| 多模块健康投票 | 会破坏「四项全通过才喂狗」的 AND 语义，等于把任何单项故障稀释掉 |
| 远程运维与状态可视化 | 是另一个产品，不是守卫的职责 |
| `fsync` / `O_SYNC` 加固快照 | `WriteFailureJson` **已经调用了 `::fsync(fd)`**；`/dev/sda3` 是 `write back`，`fsync` 只保证「内核 → 设备」，`O_SYNC` 也修不了 |

## 预期业务效果

一句话：**三项加起来，把「守卫自己出错」和「守卫无限正确地出错」这两个盲区都堵掉。**

| 用户可见现象 | 现在 | 三项做完 |
| :--- | :--- | :--- |
| 板子莫名重启，查不到原因 | 会发生（守卫自己卡死） | 不可能 —— 凡是复位必有快照 |
| 网关持续复位，远程进不去 | 会发生（确定性故障） | 3 次后停下，长期在线待修 |
| 复位后知道为什么 | 只有 `reason` + 四项判据 | 再加磁盘水位 + 证据写入是否成功 |
| 现场处置 | 派人 | 远程看一下 JSON |

保护强度没有下降：仍然是「四项判据全通过才喂狗」，仍然只有停喂这一个复位出口，仍然零 ioctl。新增的全部是「守卫自身的可靠性」与「故障的可读性」。

## 实施顺序

1. **第一项（超时）单独一个提交** —— 纯缺陷修复，语义不变，风险最低，且是第二、三项的地基（第二项要在启动阶段写文件，若启动阶段也能挂住，熔断器本身就是新的死锁点）。
2. **第三项（磁盘取证）第二** —— 纯加日志，不改控制流。
3. **第二项（熔断）最后** —— 它改了「允许不喂狗」的出口集合，需要最多讨论与验证。

> **实际实施时的偏差（如实记录）**：三项最终在**同一份源码上一次做完**，没有拆成三个提交。
> 原因是三者共享同一批辅助设施（`RunCommand` 的新签名被熔断器与磁盘采样复用，
> 磁盘采样的两个路径常量又与失败快照共用），拆开会让中间态无法编译或无法验证。
> 但**验证顺序**仍按上面的风险排序：先证明超时（真实进程正反双向），
> 再证明磁盘采样不参与判定，最后证明熔断计数规则。
