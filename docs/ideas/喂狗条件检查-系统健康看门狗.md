# 喂狗条件检查：把看门狗从「进程活着」升级为「系统健康」

> 状态：孵化中（2026-11-14 记录）
> 定位：**产品功能设想**，驱动层介入方式已定：不介入。
> 关联：`kmod/README.md`、`server/src/assurance/observer_attribution.cpp`、`server/src/thermal_monitor.cpp`

## 一句话摘要

让喂狗不再只依赖「喂狗线程还被调度」这个极弱事实，而是先检查采集线程是否还在推进、有没有线程卡死在不可中断睡眠、历史库还写不写得进去，只有全部为真才喂狗。

## 动机：喂狗证明不了系统健康

工业网关部署在无人值守现场，系统挂死必须自动复位，这是保留硬件看门狗的唯一理由。但标准用法存在结构性盲区：

```c
int fd = open("/dev/watchdog", O_WRONLY);   // 启动硬件倒计时
for (;;) {
    write(fd, "x", 1);                       // 喂狗
    sleep(interval);
}
```

喂狗只依赖一个极弱事实：**这个循环所在的线程还在被调度**。多线程程序里这几乎说明不了什么。

本仓库板端实测（2026-11-14）：

```
PID 694  weaknet-dbus-server — 28 条线程，全部 Ssl
历史库 192 MB，最近写入时间与当前时间相差 66 秒
```

28 条线程里任何一条卡死，喂狗循环都不会受影响。可能的失效形态：

| 失效形态 | 喂狗线程 | 系统实际状态 |
| --- | --- | --- |
| 采集线程卡在 `D` 状态等磁盘 I/O | 正常喂 | 遥测已停 |
| D-Bus 派发线程死锁 | 正常喂 | 客户端全部阻塞 |
| 历史落库线程因磁盘满退出 | 正常喂 | 数据不再持久化 |
| 内存耗尽导致线程被 OOM 杀死 | 正常喂 | 部分功能静默失效 |
| 主循环空转、无数据产出 | 正常喂 | 上报恒为旧值 |

**这五种场景硬件看门狗全都不会触发。** 它们的后果恰好是最难诊断的那一类：

> 云端看到「网关在线、心跳正常、但没有新数据」。

这比彻底离线更糟。彻底离线，运维知道要去看；半死不死，运维会以为「现场本来就没异常」。

## 为什么这个痛点在本项目特别成立

产品定位把「观测者自身的可信度」当成一等公民：

- `thermal_monitor.cpp` 判断采集端是否被散热拖慢，输出 `THROTTLED` / `FAN_ANOMALY`
- `observer_attribution.cpp` 判断「eBPF 掉证据是采集端自己忙，还是外部原因」

这两件事都在回答「我们的观测还可信吗」。但它们只影响**归因结果**，不影响系统是否自救。

喂狗条件检查是同一思想往「系统存活」方向的延伸：既然已经承认「采集端自己可能出问题」，就该承认「采集端出问题到一定程度时，系统应该重启」。

| 机制 | 回答的问题 | 后果 |
| --- | --- | --- |
| `observer_attribution` | 这次掉证据是不是我自己忙？ | 降级归因，继续运行 |
| `thermal_monitor` | 是不是我太热了？ | 标记状态，继续运行 |
| **喂狗条件检查** | **我是不是已经废了？** | **不喂狗，硬件复位** |

前两者是诊断，后者是自愈。

## 板端实测事实（2026-11-14）

### watchdog 硬件与驱动

```
$ sudo dmesg | grep -i wdt
[0.294216] sunxi-wdt 2050000.watchdog: Watchdog enabled (timeout=16 sec, nowayout=0)
```

| 项 | 实测值 | 含义 |
| --- | --- | --- |
| 驱动 | `sunxi-wdt`，内建（不在 `lsmod`） | 已绑定，无法 `rmmod` |
| 超时 | **16 秒** | 从 `open()` 到复位只有 16 秒窗口 |
| `nowayout` | `0` | 允许停用，但**前提是写了 magic 字符 `'V'`**（见下方「magic close」） |
| `/dev/watchdog0` | `crw------- root root 246,0` | 权限 0600，只有 root 能开 |
| 当前占用 | **无任何进程持有** | 扫描全部 `/proc/*/fd`，零命中 |
| systemd | `RuntimeWatchdogUSec=0` | PID1 没有使用它 |

**`CONFIG_WATCHDOG_OPEN_TIMEOUT=0` 是一个必须记住的安全事实**：`open()` 立即启动计时，没有宽限期。调试时 `open()` 后异常退出，16 秒后板子就会复位。任何实验都必须先想清楚这一点。

### 喂狗寄存器已查明：`base + 0x0C` 写入魔数 `0x14AF`（2026-11-14 决定性实验）

这是本方案 B 实现前最后一个未知量。结论已由**代码 + 硬件双向证据**钉死。

**证据链一：从运行中的内核直接读出真实指令**

`/proc/kcore` 未开（`# CONFIG_PROC_KCORE is not set`），`/boot/vmlinuz` 与运行内核不是同一份构建（板端内核被 ftrace 打过桩），因此改用 `/dev/mem` 直读物理内存。`CONFIG_STRICT_DEVMEM` 未开，允许用户态读内核物理内存。

先由 `mov w1,#0x14af`（字节 `e1958252`）在物理内存中定位到 `PA=0x40aab0ec`，与 `System.map` 里 `sunxi_wdt_ping = 0xffff8000088ab0d0` 的 `+0x1c` 精确对应，反解出内核物理基址 `_text PA = 0x40200000`。读出 `sunxi_wdt_ping` 的真实字节：

```
ffff8000088ab0d0:  e9031eaa  mov  x9, x21        ; ftrace 桩替换了首条 nop
ffff8000088ab0d4:  1f2003d5  nop
ffff8000088ab0d8:  014c40f9  ldr  x1, [x0, #152]
ffff8000088ab0dc:  3f2303d5  paciasp
ffff8000088ab0e0:  20044ca9  ldp  x0, x1, [x1, #192]   ; x0=base, x1=regs
ffff8000088ab0e4:  bf3203d5  dmb  oshst
ffff8000088ab0e8:  22004039  ldrb w2, [x1]            ; w2 = regs[0]
ffff8000088ab0ec:  e1958252  mov  w1, #0x14af         ; 魔数键
ffff8000088ab0f0:  0000028b  add  x0, x0, x2
ffff8000088ab0f4:  010000b9  str  w1, [x0]            ; *(base + regs[0]) = 0x14AF
ffff8000088ab0f8:  00008052  mov  w0, #0
ffff8000088ab0fc:  bf2303d5  autiasp
ffff8000088ab100:  c0035fd6  ret
```

`sunxi_wdt_restart` 尾段同样执行 `mov w0,#0x14af` 写入同一寄存器后死循环，交叉印证。

**证据链二：运行期 `.rodata` 中的 per-SoC 寄存器表**

在 `PA` 直读的 `.rodata` 段里找到两组 `sunxi_wdt_reg` 结构：

```
VA ffff800008c55348:  0c 10 14 04 03 01 00 00 | 00 00 aa 16 00 00 00 00
VA ffff800008c55378:  10 14 18 04 03 01 00 00 | 00 00 aa 16 00 00 00 00
```

字段语义（由 `start`/`stop`/`ping`/`restart` 的指令交叉推出）：

| 字段 | `0x348` 组 | `0x378` 组 | 用途 |
| --- | --- | --- | --- |
| `regs[0]` | `0x0C` | `0x10` | **`ping` 写魔数的寄存器** |
| `regs[1]` | `0x10` | `0x14` | `start` 写使能位 |
| `regs[2]` | `0x14` | `0x18` | `stop` / `cfg` 寄存器 |
| `regs[3]` | `4` | `4` | timeout 位偏移 |
| `regs[4]` | `3` | `3` | reset mask |
| `regs[5]` | `1` | `1` | reset val |

**本板使用 `0x348` 组**，判定依据是实测：`open()` 后 `+0x14` 由 `0x00` 变 `0xb1`、`close()` 后归 `0x00`，与 `regs[2]=0x14` 的 cfg 语义吻合；而 `+0x10` 恒为 `1`，与 `regs[1]=0x10` 的使能位吻合。

**证据链三：硬件双向验证（一次复位）**

```
Phase1  只写 +0x0C = 0x14AF，每 2 秒一次，持续 24 秒
        结果：存活 24 秒（> 16 秒硬件超时）      ← 喂 → 活
Phase2  停写，静候
        结果：第 15~16 秒复位，boot_id 变更        ← 停喂 → 死
```

第二条是**关键**：它排除了「写入把狗关掉」这一替代解释。只有「喂 → 活」+「停喂 → 死」同时成立，才能证明 Phase1 的存活是喂出来的。

**三个被证伪的错误假设（记录以免重犯）**

| 假设 | 实验 | 结果 | 为何错 |
| --- | --- | --- | --- |
| 喂狗 = 写 `+0x0C = 1` | 每 2 s 写 1，24 s | 16.0 s 复位 | **魔数错**：硬件只认 `0x14AF`，写 `1` 被静默丢弃 |
| 喂狗 = 写 `+0x10 = 1` | 每 2 s 写 1，24 s | 16.0 s 复位 | 偏移错（`+0x10` 是使能位）且魔数错 |
| 喂狗 = 写 `+0x10 = 0x14AF` | 无损，20 ms 内回读 | 回读恒 `1`，写入未落地 | 偏移错：`+0x10` 只读 |
| 喂狗 = 写 `+0x0C = 1` | 无损扫描 | 回读恒 `0` | 魔数错，同上 |

**一个必须记住的判据陷阱**：`+0x0C` 在 `open()` 后出现 `1` 并在 0.2 秒内自清，容易被误认为「喂狗被接受的脉冲指示器」。实测 `open()` 0.3 秒后读数已是 `0`，走 `write(fd,"x")` 的正常 ping 也抓不到脉冲。**它不是可靠指示器，不能用来做无损判定。** 唯一可靠的验证方式就是「喂 24 秒看是否存活 + 停喂看是否复位」。

**地址别名陷阱**：早期曾用 0x400 字节窗口扫描并「发现」`+0x1c4`、`+0x1a0` 等大偏移，全部是假象。硬件只解码低 5 位地址，`+0x190`/`+0x1b0`/`+0x3f0` 等位置的值每 `0x20` 字节完全重复。**DT 声明的 32 字节窗口就是正确孔径，不存在窗口外的寄存器。**

**使能键 `0x16AA0000`：第二个必须知道的坑（同日发现）**

查清 ping 之后仍然不工作：`writel(0x00, base + 0x14)` 想关狗、`writel(0xb1, ...)` 想开狗，回读全是 `0x00`。加上探针自检才看清：

```
cfg before=0x0   plain_write=0x0   keyed_write=0xb1
```

**不带 `0x16AA0000` 的写会被硬件整字丢弃，且不报错。** 这与 `sunxi_wdt_start` 的真实指令一致：

```
ldr w3, [x1, #8]      ; x1=regs, w3 = regs[8] = 0x16AA0000
orr w0, w0, w3        ; 目标值 |= 键
str w0, [x0, #0x10]   ; 写使能寄存器
```

规则：

| 寄存器 | 是否需要使能键 | 依据 |
| --- | --- | --- |
| `+0x0C` ping | **不需要**，裸写 `0x14AF` | `sunxi_wdt_ping` 只做 `str w1,[x0]`，无 `orr` |
| `+0x10` enable | **需要** | `sunxi_wdt_start` 先 `orr` 键再写 |
| `+0x14` cfg | **需要** | `start` 与 `stop` 都带键写 |
| `+0x18` mode | 本模块不触碰 | 恒 `0x1F` |

**为什么 ping 不需要键而配置需要**：这是硬件设计上的防误触——喂狗是高频无害操作，配置错一次可能直接关掉保护。键机制让「误写配置」变成静默丢弃而不是灾难。

**对方案 B 的直接含义**：

- 自注册驱动需要实现三条：ping 裸写 `*(base + 0x0C) = 0x14AF`；enable 与 cfg 写时必须 `|= 0x16AA0000`。无需任何 BSP 依赖。
- 也可不写内核模块，直接在用户态 `mmap` `/dev/mem` 的 `0x02050000`（32 字节）写同一地址——本实验全程就是这么做的，已连续工作 24 秒。
- **驱动里不要做 cfg 自检写**：探测阶段改写配置会在「另一条路径正在喂狗」时打断它，也会把已有超时编码改错。开关只在 `open()`/`close()` 时刻发生。
- `WDIOC_GETBOOTSTATUS` 恒为 `0x0`、`WDIOF_CARDRESET` 位从不置位 ⇒ 驱动未实现 bootstatus，**无法事后从内核判断「上一次复位是否看门狗所致」**，失败 JSON 必须自己写。
- `WDIOC_GETTIMELEFT` 返回 `errno=95`（不支持）⇒ 无法非破坏性地观察倒计时，健康判据不能依赖剩余时间。

## 三条被否掉的路径

### 路径 A：模块包装真实 watchdog（转发喂狗）

模块注册虚拟设备，`.ping` 回调里检查条件，通过后转发给 `sunxi-wdt`。

**否掉的原因**：`watchdog_ping` 未导出，唯一可行的转发方式是 `dev_get_drvdata()` 拿 `sunxi-wdt` 私有结构再直调 `.ops->ping`，跨驱动访问未导出内部结构，内核版本变化即失效。属于「能跑但会被评审打回」。

### 路径 B：走 pretimeout governor

**否掉的原因**：`# CONFIG_WATCHDOG_PRETIMEOUT_GOV is not set`。头文件里 `watchdog_notify_pretimeout()` 在这条配置下退化成 `static inline { pr_alert(...); }`，整个 governor 框架不存在。当前内核上不可用，除非重编。

### 路径 C：重编内核补上配置

| 重编能解决 | 重编解决不了 |
| --- | --- |
| `CONFIG_WATCHDOG_SYSFS` → sysfs 可见属性 | `watchdog_ping` 未导出（源码级） |
| `CONFIG_WATCHDOG_PRETIMEOUT_GOV` → governor 可用 | 需要完整的 `linux-a733-5.15` 源码树 |
| `CONFIG_SOFT_WATCHDOG` → softdog 可用 | 需要维护下游分支 |

**板端 `/usr/src/linux-a733-5.15` 只有 1.4 MB**，是打包残留，不是可编译的完整源码树。手上没有能重编这内核的源码。

而且 `CONFIG_WATCHDOG_SYSFS` 唯一能提供的是几个只读属性，**用 `ioctl(WDIOC_GETTIMEOUT)` 一样能拿到超时值**。为几个 sysfs 属性去维护定制内核，不划算。

## 结论：正确的方案是纯用户态

### 方案：`weaknet-health-guard` 守护进程

```
每 N 秒：
  1. 打开 /dev/watchdog0（一次性，持有到进程退出）
  2. 检查四类健康信号
  3. 全部通过 → write(fd, "x", 1)
     任一不通过 → 不写；连续 K 次不通过 → 记录原因后退出（不写 magic close）
  4. 硬件 16 秒后自然复位
```

### 四项检查（全部用户态可见）

| # | 条件 | 手段 | 说明 |
| --- | --- | --- | --- |
| 1 | 采集线程 CPU 时间在增长 | `/proc/<pid>/task/<tid>/stat` 的 `utime+stime` 差分 | 线程卡死时停止增长 |
| 2 | 无关键线程长期处于 `D` 状态 | 同上，第 3 字段 | `D` 持续超过阈值视为异常 |
| 3 | 历史库可写 | 直接试写一条并 rollback，或查 `-wal` 文件 mtime | 磁盘满、库锁死时失败 |
| 4 | 数据时间戳在推进 | 最新 metrics 的 `sample_ns`，或 `history.db-wal` 的 mtime | 防「线程活着但不产出」 |

**条件 4 最有区分度**：前三条都可能被绕过（线程空转也能让 CPU 时间涨），但「数据时间戳不推进」直接说明业务事实已经停止产出。

### ⚠️ 判据陷阱：数据库是 WAL 模式，主库文件 mtime 不会变

这是写这份文档时实测撞出来的坑，必须记下来。

第一次尝试用 `history.db` 的 mtime 做判据，结果观察到它在 **28 分钟内完全不变**：

```
11:26:20  db=2026-11-14 11:26:18
11:26:26  db=2026-11-14 11:26:18
11:26:32  db=2026-11-14 11:26:18
11:26:38  db=2026-11-14 11:26:18      ← 8 分钟内一动不动
```

**如果按这个写 guard，会造成永久误报**——数据库看起来永远不写，guard 会一直判定「系统已废」，板子进无限复位循环。

换看 `-wal` 文件后真相就出来了：

```
$ ls -lh /home/radxa/weaknet/data/history.db*
-rw-r--r-- 1 radxa radxa 192M Nov 14 11:26  history.db       ← 主库，长时间不变
-rw-r--r-- 1 root  root  32K Nov 14 11:27  history.db-shm
-rw-r--r-- 1 root  root  4.0M Nov 14 11:27  history.db-wal   ← 每 5 秒更新

11:27:56 wal_changed
11:28:01 wal_changed
11:28:06 wal_changed      ← 精确 5 秒，与落库周期一致
```

**正确判据是 `history.db-wal` 的 mtime，不是 `history.db`。** 这与源码一致：

```
server/src/server.cpp:1739  starting history persistence thread (interval=5s)
```

**一条通用教训**：用文件 mtime 判断「某个组件是否还活着」时，必须先确认该组件用的是哪种写入模式。WAL、双缓冲、批量合并刷盘都会让主文件 mtime 长时间静止，而数据其实一刻也没停。

**另一个必须注意的细节**：`-wal` 和 `-shm` 的属主是 `root root`，而 `history.db` 是 `radxa radxa`。这说明服务以 root 身份运行。guard 进程若不以 root 运行，可能读不到 `-wal` 的 mtime——权限问题需要在设计时确认。

### 为什么不做内核模块

| 内核才能拿到的信号 | 在失效场景里的占比 |
| --- | --- |
| 全局 `nr_uninterruptible`（D 状态线程总数） | 低——遍历 `/proc/*/stat` 可近似，虽慢但每分钟一次可接受 |
| 每 CPU 运行队列长度 | 低——`/proc/loadavg` 已提供全局值 |
| 指定 PID 的调度延迟 | 低——需要 tracepoint，但业务半死的主因不是调度延迟 |
| 内核线程卡死 | **极低**——此时用户态 guard 自己也会停，16 秒后真实狗照样复位 |

**最后一行是关键论证**：内核线程卡死到影响用户态时，guard 进程自己也喂不了狗，硬件的 16 秒超时自动兜底。所以这个场景**不需要额外检测**。

结论：写内核模块的边际收益不足以抵消构建风险，而构建风险是真实存在且已经被 LRADC 验证过的。

### 必须遵守的构建边界

若将来确实要加内核侧采集器，**绝不能进 `tools/ci.sh` 的 kmod 构建链**：

- `tools/kmod_cross_build.sh:187` 的 vermagic 校验是 all-or-nothing，任一 `.ko` 不匹配即 `exit 1`
- 随后 `tools/ci.sh:180-187` 会 `rm -rf dist-arm64/kmod`，**连生产观测模块一起删掉**
- LRADC 当年就是这样拖累生产模块的（`kmod/Makefile:28-30` 有记录）

只能走 `kmod/hid_multitouch/` 的模式：独立构建单元、自己的 Makefile、失败只告警（`tools/kmod_cross_build.sh:155-179`），或干脆不接入 `tools/ci.sh`。

## 关键设计决策

### 决策 1：不喂狗 vs 主动 `emergency_restart()`

| 策略 | 效果 | 风险 |
| --- | --- | --- |
| **不喂狗**（推荐） | 等硬件 16 秒自然复位 | 故障期间系统带病运行 16 秒 |
| 主动 `emergency_restart()` | 立刻复位 | 可能在数据落盘中途打断，风险更高 |

**选「不喂狗」**：故障时系统状态本就不确定，主动复位的风险大于收益。而且「不喂」是标准看门狗语义，行为可预测。

### 决策 2：复位前留证据

这是比「怎么复位」更重要的问题。如果看门狗救了系统，运维必须知道：

- 什么时间复位的
- 因为哪条检查不通过

`sunxi-wdt` **不实现 bootstatus**（实测 `WDIOC_GETBOOTSTATUS` 恒返回 `0x0`，`WDIOF_CARDRESET` 位从不置位），加上 `CONFIG_WATCHDOG_SYSFS` 没开连 sysfs 属性也没有。两条路都断了，**没有任何内核侧手段能事后判断「上一次复位是不是看门狗造成的」**。因此必须自己写失败 JSON：

```
/var/lib/weaknet/health-guard-last-failure.json
{
  "detected_at": "...",
  "checks": {"thread_cpu": "ok", "d_state": "FAILED: tid 712 in D for 8s", ...},
  "action": "stopped_petting"
}
```

板端 `/dev/sda3` 是 `write back`，`fsync` 只保证「内核 → 设备」，掉电仍可能丢。**这条记录不保证一定留下来**，但比不写强。这个边界必须写进文档，不能宣称「一定能留下」。

### 决策 3：magic close 与 nowayout（2026-11-15 按内核源码订正）

**先纠正一个流传的错误说法**：`nowayout=0` **不等于**「`close()` 会停掉看门狗」。
`nowayout` 只在 `watchdog_stop()` **内部**生效（令其返回 `-EBUSY`），它管不到「压根不调用 stop」的情况。
「裸 `close()` 要不要停用」由 **`WDIOF_MAGICCLOSE`** 决定。

`drivers/watchdog/watchdog_dev.c` 的 `watchdog_release()`：

```c
if (!watchdog_active(wdd))
	err = 0;
else if (test_and_clear_bit(_WDOG_ALLOW_RELEASE, &wd_data->status) ||
	 !(wdd->info->options & WDIOF_MAGICCLOSE))
	err = watchdog_stop(wdd);          /* ← 只有这两条路会停用 */
/* 没停用时补喂一次，硬件继续倒计时 */
if (err < 0) {
	pr_crit("watchdog%d: watchdog did not stop!\n", wdd->id);
	watchdog_ping(wdd);
}
```

三条结论，直接决定 guard 怎么写：

| 情形 | `WDIOF_MAGICCLOSE` 已设（本模块） | 说明 |
| --- | --- | --- |
| 裸 `close()`，没写过 `'V'` | **不停用**，硬件继续倒计时 → 16 秒后复位 | 这是「判定不健康」要的行为 |
| 写过 `'V'` 再 `close()` | 停用（`nowayout=0` 时成功；`nowayout=1` 时被 `-EBUSY` 拒绝） | 这是「正常停机」要的行为 |
| 驱动**未**设 `WDIOF_MAGICCLOSE` | 裸 `close()` 就停用 | 见下方「未验证的前提」 |

**未验证的前提（2026-11-15 复核发现，必须写清）**

方案 B 选择「接管硬件」而非「直接 `open("/dev/watchdog0")` 按健康判据喂狗」，
技术上唯一成立的理由是：自定义模块设了 `WDIOF_MAGICCLOSE`，因此「判定不健康 → 裸 close →
硬件继续倒计时 → 16 秒复位」这条路成立。

**但 `sunxi_wdt` 自身的 `options` 值从未取证**，本地也没有它的源码或内核镜像：

- 前提文件、`board-assets/`、`~/.cache/weaknet-kmod-headers/` 均无 `sunxi_wdt.c`
- 记录里没有任何实测表明 `sunxi_wdt` 的 close 行为
- 若它**也设了** `MAGICCLOSE`，则「接管硬件」在技术上不是必需的，只是把喂狗权
  从内建驱动挪到可控设备（可与 `/dev/watchdog0` 竞争持有者这一点仍有价值，
  但不足以构成必要的复杂度）

因此：**「必须接管」目前是设计选择，不是被证据强制的结果。** 待板子恢复后需要补的取证：

```
cat /sys/class/watchdog/watchdog0/options      # 位 5 = WDIOF_MAGICCLOSE
```

或从运行中内核取 `sunxi_wdt` 的 `watchdog_info.options`。这句话不能只在文档里写，
必须落成一条可执行的验证项，否则下次又会有人以为这是定论。

**所以本模块绝对不要设 `nowayout=1`**：它会让 `watchdog_stop()` 恒返回 `-EBUSY`，于是
`'V'` 停不掉、`rmmod`（经 `watchdog_stop_on_unregister`）也停不掉，`give-back` 归还时
反而变成一次真复位。

还要确认内核**不会**在设备关闭后自己接管喂狗，否则「停喂」永远等不到复位。
`watchdog_need_worker()` 的第二个条件 `(t && !watchdog_active(wdd) && watchdog_hw_running(wdd))`
看似危险，但裸 close 走的是「不停用」分支 ⇒ `WDOG_ACTIVE` 保持置位 ⇒ 该条件为假 ⇒
`watchdog_update_worker()` 执行 `hrtimer_cancel()`。实测确认（2026-11-15，见
`openspec/tasks/2026-11-14-system-health-watchdog-plan-b.md` 4.11）。

guard 的三条退出路径据此建模：

| 路径 | 动作 | 结果 |
| --- | --- | --- |
| 判据失败 / 崩溃 / 被 `kill -9` | 裸 `close()` 或不 close，`_exit()` | 硬件继续计时 → 16 秒后复位 |
| 正常停机（`SIGTERM`） | 写 `'V'` 再 `close()` | 停用看门狗，不复位 |
| 运维 `stop` 了 guard | `ExecStopPost` 走 `give-back` 归还 | 由 `sunxi_wdt` 重新接管 |

**`give-back` 的门禁必须看 systemd 注入的退出事实，不能只看 trip 标记**（2026-11-15 板端实测修正）。
`tripped_this_boot` 只能覆盖「判定不健康」这一条路径；被 `SIGKILL`/`SIGSEGV`/OOM 杀死、
`open` 或喂狗失败返回 1、以及 `RecordTrip()` 写文件失败时都**来不及写标记**，
而 systemd 在这些情况下**同样执行 `ExecStopPost`** ⇒ `rmmod` → `watchdog_stop_on_unregister`
→ `.stop` → 硬件看门狗被关掉，已排定的复位被静默取消。

板端实测的取值（systemd 247，**与直觉不符，必须按实测写**）：

| 场景 | `SERVICE_RESULT` | `EXIT_CODE` | `EXIT_STATUS` |
| --- | --- | --- | --- |
| `systemctl stop`（优雅 SIGTERM） | `success` | `killed` | `TERM` |
| 捕获 SIGTERM 后 `exit 0` | `success` | `exited` | `0` |
| `kill -9` | `signal` | `killed` | `9` |
| 主进程 `return 99` | `exit-code` | `exited` | `99` |
| `TimeoutStopSec` 超时 | `timeout` | `killed` | `9` |

因此唯一可靠的主判据是 `SERVICE_RESULT`：`success` 允许归还，其余一律拒绝。
**不能**按 `EXIT_STATUS != 0` 判断 —— 正常 stop 时它是 `TERM`，那样每次正常停止服务都会被
拒绝归还，模块与设备永久残留（这是实测抓到的真 bug，不是推演）。

## 深入验证：三件事的实测结论

### 一、线程角色无法靠名字识别（这是设计上的硬约束）

板端实测：

```
$ for t in /proc/694/task/*; do cat $t/comm; done | sort -u
weaknet-dbus-se                    ← 28 条线程，只有一个名字
```

**全部 28 条线程的 `comm` 完全相同**，是进程名被截断到 15 字符（`TASK_COMM_LEN`）的结果。源码侧确认：

```
$ grep -rn "pthread_setname_np|prctl(PR_SET_NAME" server/src/ server/include/
(零命中)
```

**源码里一次线程命名都没有。** 这直接否掉了「按线程名找关键线程」的方案。

再看 `wchan`（线程当前阻塞在哪个内核函数），分布倒是很清楚：

| 阻塞点 | 线程数 | 推断角色 |
| --- | --- | --- |
| `hrtimer_nanosleep` | **23** | 各周期采样线程（`sleep_for` 循环） |
| `futex_wait_queue_me` | 2 | 条件变量等待 |
| `do_epoll_wait` | 1 | D-Bus 派发 |
| `do_select` | 1 | 网络等待 |
| `do_sys_poll` | 1 | 主线程 |

**但 `wchan` 不是稳定标识**：线程在不同瞬间会在 `hrtimer_nanosleep` 和 `futex_wait` 之间来回切换，而且 23 条线程共享同一个 `wchan`，无法区分哪一条是「采集 RSSI」、哪一条是「采集 RTT」。

### 二、结论：判据必须建立在「聚合指标」而非「特定线程」

既然无法定位特定线程，判据设计必须换思路。有三个可选方向：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 进程总 CPU 时间** | `/proc/694/stat` 的 `utime+stime` 差分 | 极稳定、零竞态、一条命令 | 粒度粗，看不出「哪个模块死了」 |
| **B. 按 wchan 分类聚合** | 统计处于 `hrtimer_nanosleep` 的线程数与 CPU 总和 | 能发现「大量采样线程集体停摆」 | `wchan` 读取需要 root，且有采样瞬时性 |
| **C. 数据产出代替线程状态** | 看 `-wal` mtime + metrics 时间戳 | **直接测业务事实**，不受线程模型影响 | 需要确认「无异常时本来就不写」的基线 |

**推荐 C 为主、A 为辅**：

- **C 是端到端判据**：不管内部线程怎么组织，只要「数据还在产出」就说明系统活着。这是唯一不依赖内部实现的判据。
- **A 是兜底判据**：进程总 CPU 时间完全不涨，说明整个进程已经停了。

**B 被排除**：`wchan` 读取在 `CONFIG_KALLSYMS` 未开时会显示地址而非符号名，且需要 `CAP_SYS_ADMIN`，与项目「最小权限」的既有设计取向冲突（`weaknet_cpu_stat.c` 刻意只要 `CAP_PERFMON`）。

### 三、线程 CPU 时间的实测基线（用来定阈值）

5 秒间隔采样：

```
TID   before   after   delta
707    27715   27835    120     ← 主要工作线程
702      577     579      2
727      261     265      4
710      359     360      1
694      273     273      0     ← 主线程，阻塞在 do_sys_poll
732      656     656      0
```

进程级 5 秒增量：

```
52935 → 53078   = +143 ticks（约 1.43 秒 CPU / 5 秒墙钟 = 28.6% 单核占用）
```

**这里有一个必须写进实现的重要事实**：`delta=0` 是**正常现象**，不是故障。28 条线程里绝大多数时间都在 `hrtimer_nanosleep`，CPU 时间本来就不涨。所以：

- ❌ 错误判据：「所有线程 CPU 时间都在涨」
- ❌ 错误判据：「某条线程 CPU 时间不涨就是死了」
- ✅ 正确判据：「**进程总** CPU 时间在 N 秒窗口内增长超过阈值」

`D` 状态基线也很干净：28 条线程全部 `S`，零个 `D`。这说明现场正常时不应出现 `D`，一旦出现且持续超过阈值，确实值得怀疑。

## 最终判据设计（可进实现）

> **前置约束：16 秒硬件超时不可调。** 从最后一次成功喂狗到硬件复位只有 16 秒。
> 所有阈值、窗口、去抖次数都必须在这个预算内收敛，否则判据永远来不及触发。
> 下表已按此约束定稿；更早版本里「30s/60s 阈值 + K=3 + D 状态 45s」的写法已废弃。

### 主判据：数据产出（不看线程）

| 检查 | 手段 | 阈值 | 依据 |
| --- | --- | --- | --- |
| 落库在推进 | `history.db-wal` mtime 距今 | **> 12 秒告警**（落库周期 5 秒，留 2.4 倍余量） | 实测精确 5 秒一次 |
| 采集无长停 | 最新 metrics 的 `sample_ns` 距今 | **> 20 秒告警**（采集周期 10 秒，留 2 倍余量） | 5 秒落库、10 秒采集 |

**为什么不是 30s/60s**：若 20 秒才发现采集停了，再加上去抖与一次重试，已经越过 16 秒，板子先复位了，判据等于没写。阈值必须显著小于 16 秒，才能保证「发现问题 → 停止喂狗 → 硬件复位」这条链路真的走完。

**注意 WAL 陷阱**：主库 `history.db` 的 mtime 长期不变（实测 28 分钟静止），真正在动的是 `history.db-wal`。必须判 WAL 文件，判主库会得到恒定的假告警。

### 辅判据：进程活性（兜底）

| 检查 | 手段 | 阈值 |
| --- | --- | --- |
| 进程总 CPU 在涨 | `/proc/<pid>/stat` 的 `utime+stime` | **6 秒窗口**内增量 < 1 tick 告警 |
| 无长期 `D` 线程 | 遍历 `/proc/<pid>/task/`，每个 tid 读 stat 取第 3 字段 | 任一 `D` 持续 **> 8 秒**告警 |
| 服务进程还在 | `systemctl show -p MainPID` | 缺席超过 **12 秒**容忍窗口才停止喂狗 |

**窗口取值理由**：6 秒 CPU 窗口 + 8 秒 D 状态窗口都落在 16 秒预算内，且各留一次重试空间。更长的窗口在 16 秒约束下没有意义。

**去抖：`K ≤ 2`**。判据周期取 **2 秒**，则 `K=2` 意味着最坏 4 秒确认，加 8 秒 D 阈值是 12 秒，仍在 16 秒内。**不允许 `K=3`**：3 次 × 2 秒 = 6 秒去抖，叠加任何一条主判据的 12~20 秒阈值就会超预算。

**「服务进程不存在」为什么也需要容忍窗口**（实现后订正，原设计是「立即停止喂狗」）：`weaknet-server.service` 是 `RestartSec=5`，一次崩溃自动重启要 5 秒等待 + 2~3 秒启动。若把「进程暂时不在」当成死亡，那么每次服务自动重启、每次 `systemctl restart`、每次 OTA 升级都会把整机打复位。12 秒 = 5 秒重启等待 + 3 秒启动 + 4 秒余量。

**余量不是浪费**：第一版取 8 秒（恰好 5+3，数学上「刚好够」），被 `test_grace_covers_systemd_restart` 断言打回 —— 启动只要比预估慢 1 秒，一次普通的 systemd 自动重启就会变成整机复位。工程上「刚好够」等于「不够」。

**读取 stat 时不能用按空白切分取第 3 字段**（实现后订正）：字段 2 是 `(comm)`，comm 含空格时 `$3` 会落到 comm 内部。必须从最后一个 `)` 之后取。这一点已由 `TestDThreadCounting` 钉死。

## 三个必须在实现前定死的决策

### 决策 4：怎么找到服务进程

不能用 `pgrep -f`（会匹配到 guard 自己或 shell）。三条可选：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **systemd 依赖** | guard 的 unit 里 `BindsTo=weaknet-server.service` + `After=`，用 `systemctl show -p MainPID` 拿 PID | ✅ 推荐，由 systemd 保证顺序与生命周期联动 |
| pidfile | 服务启动时写 `/run/weaknet-server.pid` | 需改服务代码 |
| 扫 `/proc` | 遍历所有进程比对 `exe` 软链 | 有竞态，且重名进程会误判 |

**推荐 systemd 方案**：`After=weaknet-server.service` 保证启动顺序，`BindsTo=` 保证服务停了 guard 也跟着停，`MainPID` 直接给答案。

### 决策 5：启动宽限期

服务刚起来时，数据库可能还没写入第一条，`-wal` 也还没创建。**如果 guard 立刻开始判据，会在启动瞬间误判「系统已废」。**

必须实现：

```
guard 启动后：
  1. 先进入 grace period（建议 90 秒 = 3 个采集周期 + 余量）
  2. 期间正常喂狗，但不做任何健康判定
  3. 宽限期结束后，先采集一次基线，之后才开始判定
```

同理，`systemctl restart weaknet-server` 之后也要重新进宽限期。**怎么感知重启**：监视 `MainPID` 是否变化，变了就重置状态机。

### 决策 6：guard 自己的存活

这是**元问题**：guard 挂了，没人喂狗，16 秒后板子复位。这看起来是「安全失败」，但会造成「guard 本身有 bug → 板子无限重启」的最坏情况。

**规划期的想法（已被推翻）**：`Restart=always` + `RestartSec=3`，让 guard 崩了自动拉起，避免误复位。

**为什么错**：`Restart=always` 会把**最需要复位的那条路径取消掉**。guard 判定不健康 → 停止喂狗并退出 → systemd 立刻拉起新实例 → 新实例 `open(/dev/watchdog1)` 触发 `.start` → **使能并喂狗** → 已经排定的 16 秒复位被静默取消。于是故障还在、保护没了，比不加保护更糟：表面上 `systemctl status` 是个正常的 active 服务。

关键在于：「guard 崩溃」与「guard 主动判定不健康后退出」是两件完全不同的事，而 `Restart=always` 无法区分。

**修正后**（`tools/weaknet-health-guard.service`）：

| 情况 | 期望行为 | 机制 |
| --- | --- | --- |
| 判定不健康 | **不重启**，让 16 秒走完复位 | `Restart=no` + `RestartPreventExitStatus=99` + guard 内部 boot_id 触发标记在 `open()` **之前**拦截（三层纵深） |
| 正常 stop/restart | 写 `'V'` 停用看门狗，不复位 | 默认 `KillSignal=SIGTERM` + `TimeoutStopSec=10` |
| 自己崩溃（段错误/OOM） | 复位（期望行为），但**不要**偷偷续命 | `Restart=no` —— 宁可复位，也不要一个续命的半死守卫 |

`RestartPreventExitStatus=99` 是纵深防御：即使将来有人把 `Restart` 改成 `on-failure`，退出码 99 依然能挡住。guard 自身的 boot_id 标记是第二层，防 systemd 配置漂移。

**「自己崩溃该不该重启」的判断依据**：重启会喂狗续命，把崩溃变成静默故障；不重启则 16 秒后复位，留下可见痕迹。对无人值守设备，「响一声」永远优于「悄悄撑住」。

**没有 `StartLimitBurst` 问题**：`Restart=no` 下不存在重启循环，系统管理器的启动频率限制与本单元无关。

## ✅ 已结案：`rmmod` 路径不存在，但 `unbind` 路径存在（原「可能推翻全部结论的待确认项」）

### 第一层结论：不能 `rmmod`，但这不等于不能接管

上一版假设「如果 `sunxi_wdt` 是模块，就能 `rmmod` 后加载自己的驱动」。
**2026-11-14 板端实测把这个假设否掉了：**

```
$ sudo rmmod sunxi_wdt

```

`lsmod` 零命中、`/lib/modules/$(uname -r)` 下无实体 `.ko`、`/sys/module/sunxi_wdt/`
只有 `uevent` 和 `version`（内建模块的特征：没有 `refcnt`、`sections`、`holders`）。

**但「内建」只阻止 `rmmod`，不阻止 platform driver 的 `unbind`。** 这是本条
待确认项真正的分叉点，上一版没有区分这两件事。

### 第二层结论：`unbind` 实测可逆，但是「设备消失」而非「驱动切换」

板端实测（2026-11-14，全程未 `open()` 看门狗，硬件未启动，零复位风险）：

| 步骤 | 命令 | 结果 |
| --- | --- | --- |
| 基线 | `ls -l /dev/watchdog*` | `watchdog` (10,130) / `watchdog0` (246,0)，均 `0600 root` |
| 基线 | `sudo dmesg \| wc -l` | 1626 行 |
| **unbind** | `echo 2050000.watchdog > .../sunxi-wdt/unbind` | rc=0，driver 软链消失 |
| **观察 1** | `ls /dev/watchdog*` | **两个节点都消失**（`ENOENT`） |
| **观察 2** | `sudo dmesg \| wc -l` | **1626 行（零新增）** |
| **观察 3** | `ls /sys/class/watchdog/` | **空** |
| **bind 回滚** | `echo 2050000.watchdog > .../sunxi-wdt/bind` | rc=0，软链恢复 |
| **恢复验证** | `ls -l /dev/watchdog*` | 节点恢复（inode 变更） |
| **功能验证** | `ioctl(WDIOC_GETTIMEOUT)` | **16 秒**，设备完好 |
| **安全退出** | `write(fd, "V")` + `close()` | 板子未复位 |

**三条必须记住的事实：**

1. **`unbind` 是设备消失，不是驱动切换。** `/dev/watchdog0` 与 `/dev/watchdog`
   同时消失，`/sys/class/watchdog/` 变空。此时任何 `open()` 都是 `ENOENT`，
   连「能不能用看门狗兜底」都判断不了。
2. **`sunxi_wdt_stop()` 完全静默。** 整个 unbind 过程内核日志零新增。这意味着
   生产环境里如果有人 unbind 了没 bind 回来，**日志里什么都不留**——与本文档
   开头批判的「半死不死」是同一种故障形态。
3. **可逆性成立，且不持久。** `bind` 能干净恢复，功能实测完好。更重要的是：
   重启后内建驱动会重新 probe，**故障会自愈**，不会出现「永久接管失败」的死局。
   这让方案 B 的风险从「无限复位」降级为「有限窗口内裸奔」。

### 第三层结论：方案 B（unbind + 自注册驱动）可选，但必须带安全网

用户已明确选择**方案 B**。它的技术形态与风险边界如下：

**驱动可接管性已确认：**

| 项 | 实测值 |
| --- | --- |
| 设备树节点 | `/proc/device-tree/soc@3000000/watchdog@2050000` |
| `compatible` | `allwinner,wdt-v103` |
| `reg` | `0x02050000`，长度 `0x20`（32 字节寄存器窗口） |
| `interrupts` | SPI 106 (`0x6a`)，高电平触发（类型 4） |
| 驱动符号 | `sunxi_wdt_ops` / `sunxi_wdt_dt_ids` 在 `System.map` 可见 |
| `watchdog_ping` 导出 | ❌ 未导出（`__ksymtab` 零命中，`Module.symvers` 无） |
| 板端构建环境 | ✅ `gcc` / `make` / 完整 `Module.symvers`（14797 符号）/ `.config` |

**必须先确认的构建边界：** 板端 `/lib/modules/5.15.147-99btf1-a733/build` 是
`/usr/src/linux-headers-...`，**有 `Module.symvers` 与 `.config`，但没有
`drivers/watchdog/` 源码目录**（headers-only）。因此 `sunxi_wdt` 的寄存器位定义
**拿不到源码**，必须从 `System.map` 地址反汇编 `sunxi_wdt_start` / `sunxi_wdt_ping`
推出，或参考上游 `sunxi_wdt.c` 的通用实现。

**安全网（不可省略）：**

```
  1. modprobe weaknet_wdt           ← 先加载，probe 失败就此打住
  2. 检查 /dev/weaknet_wdt 存在      ← 不存在则 exit 1，绝不 unbind
  3. unbind sunxi_wdt               ← 只有上一步确认成功才撤保护
  4. 任一失败 → 立刻 bind 回来
```

**顺序不可颠倒。** 先撤保护再加载新驱动，中间就是无设备、无日志、无保护的真空期。

**方案 B 的两个设计错位（必须正视，不能靠实现技巧绕开）：**

1. **`.ping` 由用户态 `write()` 触发，内核在那一刻看不到业务语义。** 在 `.ping`
   里做健康检查意味着「喂狗时刻同步阻塞地查一堆东西」，检查本身若卡住（等锁、
   读用户态内存），`write()` 就卡住，喂狗变成挂死。
   → **结论：健康判定必须留在用户态，内核侧只做采集/转发。**

2. **驱动 `probe` 早于业务启动。** 它无法知道「采集线程是否在推进」，只能在
   被调用时现查。这与方案 C 的内核采集器面临同一个约束。

**因此方案 B 的推荐形态是「接管硬件 + 保持薄内核层」：**

```
weaknet_wdt.ko（接管 0x2050000）
  ├─ .ping  → 直接写硬件寄存器（等价 sunxi_wdt_ping），零附加逻辑
  └─ 导出 /dev/weaknet_wdt 供用户态 open/write 喂狗

weaknet-health-guard（用户态，root）
  ├─ 判据（落库 mtime / metrics 时间戳 / CPU 增量 / D 状态）
  ├─ 去抖
  └─ 全部通过 → write /dev/weaknet_wdt；任一失败 → 不写，16s 后硬件复位
```

## 详细技术计划（方案 B，2026-11-14 定稿）

### 判据出口已实测确认（这一步以前是空的，现在不是了）

三项主判据都有现成的只读出口，且都已板端验证：

| 判据 | 出口 | 实测 | 开销 |
| --- | --- | --- | --- |
| 落库推进 | `stat("/home/radxa/weaknet/data/history.db-wal").st_mtime` | 每 6 秒前进 6 秒 | 一次 `stat` |
| 采集推进 | `busctl --system call com.example.WeakNet /com/example/WeakNet com.example.WeakNet GetEbpfMonitorHealth` | `last_successful_sample_ns` 持续推进 | **25 ms** |
| 进程存在 | systemd `MainPID` | 可用 | 一次 `systemctl show` |

**必须注意的事实**：`GetEbpfMonitorHealth` 返回的 8 个监控器里有 2 个 `last_successful_sample_ns = 0`（按需启用、当前未运行）。判据**不能要求全部推进**，否则恒假告警。正确做法是**统计非零项的数量**，要求「非零项中至少 2/3 在 6 秒内有推进」。

`busctl` 以 **radxa 身份**即可调用（无需 sudo），但 guard 本身仍以 root 运行——因为 `/dev/watchdog0` 是 `0600 root`。

### 关键简化：内核模块可以写得很薄

喂狗寄存器查明后，`weaknet_wdt.ko` 的硬件部分只剩三条写：

```c
writel(0x14AF,             base + 0x0C);              /* 喂狗 */
writel(0xB1 | 0x16AA0000,  base + 0x14);              /* 开狗 + 16s */
writel(0x00 | 0x16AA0000,  base + 0x14);              /* 关狗 */
```

`base` 由 `ioremap(0x02050000, 0x20)` 得到。**不需要任何 BSP 依赖、不需要 `watchdog_ping` 导出、不需要 `sunxi_wdt` 源码。**

注意「三条」而不是「一条」：ping 裸写，开/关必须带使能键 `0x16AA0000`。少一个键，驱动会「open 成功、write 成功、硬件毫无反应」——这正是第一版的现象。

保留模块而不是纯 `/dev/mem` 的理由是**权限与唯一性**，不是能力：

| | 纯 `/dev/mem` 写魔数 | `weaknet_wdt.ko` |
| --- | --- | --- |
| 谁能喂狗 | **任何 root 进程**都能静默关掉保护 | 只有持有 `/dev/weaknet_wdt` 的进程 |
| 误写风险 | 无隔离 | 设备节点 `0600` + 单一持有者 |
| 与 `sunxi_wdt` 共存 | 两套东西同时存在，谁生效说不清 | `unbind` 后唯一主人 |
| 语义 | 「有人在敲一个魔数」 | 「watchdog 设备被喂了」 |

### `weaknet_wdt.ko` 规格

**不匹配 DT 节点。** 不复用 `allwinner,wdt-v103`，而是手工创建 platform device，直接 `ioremap` 已知物理地址：

```c
static struct platform_device *wn_pdev;

static int __init weaknet_wdt_init(void)
{
    wn_pdev = platform_device_register_simple("weaknet-wdt", -1, NULL, 0);
    /* probe 里 ioremap(0x02050000, 0x20) */
}
```

物理地址写死是可接受的，因为这是 A733 专用模块而非通用驱动；但必须在源码顶部注释里显式声明这条假设。

寄存器操作（全部来自实测）：

```c
#define REG_PING    0x0C   /* 写 0x14AF 喂狗，裸写不带键 */
#define REG_ENABLE  0x10   /* 使能位，带键写，回读 1 */
#define REG_CFG     0x14   /* 使能 0xB1 / 关闭 0x00，带键写 */
#define REG_MODE    0x18   /* 恒 0x1F，本模块不动 */

#define ENABLE_KEY  0x16AA0000  /* 写 enable/cfg 必须或上，否则被丢弃 */

static inline void wn_ping(void)   { wmb(); writel(0x14AF, base + REG_PING); }
static inline void wn_enable(void) { writel(0xB1 | ENABLE_KEY, base + REG_CFG); }
static inline void wn_disable(void){ writel(0x00 | ENABLE_KEY, base + REG_CFG); }
```

**`ENABLE_KEY` 不是可选项**：第一版驱动没带键，`writel(0xB1, ...)` 回读仍是 `0x00`，看门狗从没真正使能过。表现是「open 成功、write 成功、什么也没发生」。实际实现里 `enable` 与 `cfg` 走读-改-写以保留 `reset mask` 之外的位，细节见 `kmod/weaknet_wdt.c`。

回调：

| 回调 | 实现 |
| --- | --- |
| `.start` | `wn_enable(); wn_ping();` |
| `.stop` | `wn_disable();` |
| `.ping` | `wn_ping();` |
| `.set_timeout` | 只接受 16，其余返回 `-EINVAL`（与 `sunxi_wdt` 行为一致） |
| restart handler | `wn_enable(); wn_ping(); mdelay(100);` |

`sunxi_wdt_ping` 在写之前执行 `dmb oshst`，`writel()` 内部已有 `__iowmb()`，但要在实现里显式确认写屏障，避免极端情况下写被乱序。

### 安全网顺序（不可颠倒）

```
1. insmod weaknet_wdt.ko
2. 检查 /dev/watchdog1 存在        ← 不存在则 exit 1，绝不 unbind
3. echo 2050000.watchdog > /sys/bus/platform/drivers/sunxi-wdt/unbind
4. 任一失败 → 立刻 bind 回来
```

**必须先验证的假设**：`weaknet_wdt` 注册后设备名应为 `watchdog1`（`watchdog0` 已被 `sunxi_wdt` 占用）。`unbind` 后 `watchdog0` 消失，但**我们的设备编号不会自动变成 `watchdog0`**。因此 guard 必须按固定路径打开，不能按「编号最小的那个」找。这条要用实测确认，不能靠推断。

### `weaknet-health-guard` 规格

**主循环（周期 2 秒）**：

```
1. 维护标记有效？ → 只喂狗，不判定（30 分钟自动过期）
2. systemd 拿 MainPID
3. 拿不到 → OTA 在推进？ → 继续喂
              否则缺席超过 12 秒？ → 不喂狗，写 JSON，退出 99
4. 拿到 → 新 PID 的 12 秒豁免期内？ → 只喂狗，不判定
5. 执行 4 项检查
6. 每项独立累计失败次数；通过则清零
7. 任一检查连续失败 ≥ K(=2) → 不喂狗，写 JSON，退出 99
8. 全部通过 → write(fd, "1")
```

**实现时新增的四条放行路径**（都不是"放宽"，是防止把正常运维判成故障）：

| 情形 | 处理 | 不加会怎样 |
| --- | --- | --- |
| 人工维护标记 | 只喂狗不判定，30 分钟过期 | 停服务排障 = 板子复位，现场消失 |
| OTA 回执 `IN_PROGRESS` + mtime 新鲜（< 300 s） | 只喂狗不判定 | 云端升级中途被复位，可能落在指针已翻、release 未转正处 |
| OTA 回执停在 `IN_PROGRESS` 但 mtime 陈旧 | **恢复正常判定** | 一次崩死的升级会永久关掉保护 |
| 换 PID 后 12 秒内 | 只喂狗不判定 | 新进程继承停机期间陈旧的 WAL mtime，一起就被判死 |
| 20 分钟内重启 > 6 次 | **取消豁免，正常判定** | 崩溃循环被反复豁免，看门狗永久喂活 |

**阈值与去抖（受 16 秒约束）**：

| 检查 | 阈值 | 去抖 |
| --- | --- | --- |
| WAL mtime 距今 | > 12 秒 | K=2 |
| sample_ns 距今 | > 20 秒 | K=2 |
| 进程总 CPU 6 秒增量 | < 1 tick | K=2 |
| 任一 `D` 状态持续 | > 8 秒 | K=2 |
| 服务进程缺席 | — | **12 秒容忍窗口**后生效 |

周期 2 秒 + K=2 = 最坏 4 秒确认，叠加 8 秒 D 窗口是 12 秒，仍在 16 秒内。**不允许 K=3**。

**为什么"进程缺席"不能免去抖**：初版设计写的是"免去抖立即生效"，实现后必须推翻。`weaknet-server` 是 `RestartSec=5`，一次自动重启 = 5 秒等待 + 3~5 秒启动；若缺席即断喂，每一次自动重启都会把整机打复位（`ci.sh` 部署、OTA 升级、手工 restart 全部命中）。改成 12 秒容忍窗口：`RestartSec(5) + 启动(3) + 4 秒余量`。

最初取 8 秒（恰好 5+3），被测试 `test_grace_covers_systemd_restart` 拦下——数学上刚好够，工程上是错的：启动慢 1 秒就误复位。余量不是浪费。

**三条退出路径必须显式区分**：

| 场景 | 行为 | 结果 |
| --- | --- | --- |
| 判据失败 | 不写 `V`，直接 `close()` | **16 秒后硬件复位** |
| 正常停机（`systemctl stop`） | `write(fd,"V")` + `close()` | 停用看门狗，不复位 |
| guard 自己崩溃 | 没机会写 `V` | **16 秒后复位（期望行为）** |

第三条是设计意图：guard 无法稳定运行，就该让硬件重启系统。

{

  "uptime_s": 765.35,
  "boot_id": "689d34f3-...",

`reason` 必须区分三种责任（实现时补的，初版只有一个 `"action"` 字段，等于放弃事后归因）：

| reason | 含义 | 运维处置 |
| --- | --- | --- |
| `criteria_unhealthy` | 进程活着，但判据挂了 | 查 `detail`，看是哪一项；这才是有价值的故障现场 |
| `service_absent` | 服务真的没了（超过 12 秒容忍 + 非 OTA 过渡） | 查 `journalctl -u weaknet-server` |
| `feed_write_failed` | 连喂狗都写不进去了 | 查设备与内核日志，通常是驱动/权限问题 |

`detail` 字段写的是**当时的实测值**而不是布尔结论，因为复位之后唯一的现场就是这份 JSON。

**边界**：`/dev/sda3` 是 `write back`，`fsync` 只保证「内核 → 设备」，复位瞬间仍在缓存里的数据块可能丢。这条 JSON **不保证一定留下来**。

```ini

ExecStopPost=/home/radxa/weaknet/current/tools/weaknet-wdt-takeover.sh give-back
Restart=no
RestartPreventExitStatus=99
KillSignal=SIGTERM
TimeoutStopSec=10
StateDirectory=weaknet
```

**四处与初版设计相反的修正，每一条都是实现时才看清的**：

| 初版设计 | 为什么错 | 修正 |
| --- | --- | --- |
| `Restart=always` + `RestartSec=3` | guard 判定不健康后停止喂狗并退出；systemd 立刻把它拉起来，新实例 `open()` 设备 → 内核调 `.start` → **使能并喂狗，复位被静默取消**。故障还在、保护没了，比不加保护更糟 | `Restart=no`；guard 自己另有 boot_id 触发标记在做 `open()` 之前拦截，形成双层 |
| `BindsTo=weaknet-server.service` | 服务不在时守卫跟着不启动 ⇒ 没人喂狗也**没人使能**看门狗，系统静默退化成零保护。而「服务该在却没在」恰恰是守卫最该出手的场景 | 改 `Wants=` |
| 只有 `ExecStart`，没有归还步骤 | guard 正常退出会写 `'V'` 停用硬件看门狗，而 `sunxi_wdt` 仍是 unbind 状态 ⇒ `systemctl stop` 之后整机**既无健康看门狗也无原生看门狗**，`status` 却一切正常 | `ExecStopPost` 归还（用 Post 而非 Stop：后者在「主进程自己退出/启动失败」时不执行） |
| `StartLimitBurst=0` | 同上，根源是 `Restart=always` 这个前提本身错了 | 随 `Restart=no` 一并取消 |

**为什么用 `ExecStopPost` 而不是 `ExecStop`**：`ExecStop` 只在 `systemctl stop/restart` 时执行，主进程自己退出或启动失败时**不执行**。而 `ExecStartPre` 已经把 `sunxi_wdt` unbind 了——那种情况下若没有 `ExecStopPost`，整机就同时失去两套看门狗。

**`RestartPreventExitStatus=99`** 是纵深防御：`Restart=no` 已经排除自动重启，这条防的是将来有人把 `Restart` 改成 `on-failure`。

### ⚠️ 16 秒硬约束对所有方案成立

| 约束 | 数值 |
| --- | --- |
| 硬件超时 | **16 秒**（不可调） |
| 落库周期 | 5 秒 |
| 采集周期 | 10 秒 |
| 板子完整重启 | **33.8 秒**（kernel 5.84s + userspace 27.95s） |

**16 秒窗口内最多看到 1~3 个业务周期。** 这是硬件事实，任何软件方案都改不了。
因此判据必须压到 **3~5 秒量级**，去抖 `K` 最多 2，否则去抖窗口本身就把 16 秒吃光。

「`D` 持续 > 45 秒」这类超过硬超时的值已全部删除。
