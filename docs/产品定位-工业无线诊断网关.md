# 产品定位：工业现场无线信号检测与诊断网关

> **文档状态**：产品基线（v1，2026-09-30）
> **适用项目**：AI-powered-Network-Diagnostics / WeakNet
>
> 本文是**产品语义的唯一权威来源**。任何新功能（无论是否走 OpenSpec change）
> 都必须能回答"它改善的是设备层、链路层还是区域层"，否则退回重新定义。
>
> **为什么需要这份文档**：项目早期实现了 `a2dp_media` / `audio_quality` 等音频
> 观测能力，导致后续讨论反复把产品理解成"蓝牙音频诊断"。那些实现只是历史遗留的
> 专项能力，**不定义产品**。本文把定位钉死，避免再次被既有代码带偏。

## 一、产品是什么

**WeakNet 是面向工业现场的无线信号检测与诊断网关。**

持续观测现场 Wi-Fi、Bluetooth 等无线链路及周边设备状态，识别单设备异常和区域性
无线环境异常，并通过历史数据、链路事件和跨设备关联帮助运维人员判断：

- 哪里出了问题
- 什么时候开始
- 影响了哪些设备
- 可能是什么原因

产品负责**观测、检测、诊断、追溯**。

## 二、产品不做什么

| 不做 | 原因 |
| ---- | ---- |
| 设备管理（配对、自动重连、音频路由、设备控制） | 一旦开始就会从 diagnostics 滑向 management platform，范围失控 |
| 替代厂商管理平台 | 我们回答"现场无线环境怎么了"，不回答"如何远程配置这台设备" |
| 音频 QoE 诊断 | `a2dp_media`/`audio_quality` 是 legacy 专项能力，保留兼容但不作为主线 |
| 多网关聚合（当前阶段） | 见第五节的边界说明 |

**一句话**：不控制、不管理，只做观测与诊断。

## 三、用户是谁

**工业现场运维人员**。他们面对的真实问题是：

> "昨天凌晨 3 点产线出过一次问题，现在恢复了，帮我查当时发生了什么。"

这个场景实时监控页面完全帮不上忙——所以**历史追溯是产品支柱之一，不是
"诊断完顺手存库"**。

## 四、核心领域对象

```
Site（现场）
 └── Gateway（网关）
      └── WirelessDevice（被网关直接观测并持续维护身份状态的无线实体）
           ├── DeviceObservation（原始观测：时间点的信号/状态快照）
           └── DeviceEvent（规范化业务事件：发生了什么）
                └── SiteIncident（区域级事件：一组 DeviceEvent 的持续解释）
                     └── DiagnosisEvidence（诊断证据，含从事实到推断的链路）
```

| 对象 | 语义 | 关键约束 |
| ---- | ---- | -------- |
| `Gateway` | 部署在现场的采集节点（一块开发板 = 一台网关） | 当前 1 Gateway = 1 Site，但 `gateway_id`/`site_id` 从第一天就进 schema |
| `WirelessDevice` | 被直接观测、且身份被持续维护的无线实体 | 当前只实例化 Bluetooth；`protocol` 预留 wifi/zigbee/other 为 **reserved**（枚举存在 ≠ 已支持） |
| `DeviceObservation` | 一次原始观测 | 未采集必须表达为 NULL，**不用 0 冒充** |
| `DeviceEvent` | 规范化后的业务事件（Canonical Device Event） | WHAT 与 WHY 分离；原始事实无损；事实与推断永不合并 |
| `SiteIncident` | 区域异常事件，有生命周期 | Event 是不可变事实，Incident 是持续解释，两者生命周期不同，**必须分开建模** |
| `DiagnosisEvidence` | 支撑诊断结论的证据 | 必须可追溯到具体来源（哪个 hook / 哪次观测） |

### 事实与推断必须分开

这是贯穿全项目的原则，在 schema 层就体现：

- `reason_code`（事实：内核给出）≠ `suspected_cause`（推断：诊断器产出）
- `affected_devices`（事实：几台设备同时异常）≠ `suspected_interference`（推断：疑似干扰）

**采集层永远不产出推断。** 违反这条会让用户不再信任整个诊断系统——
一次"因为没有证据就断言是 Wi-Fi 干扰"的误判，足以毁掉长期可信度。

## 五、三层模型与当前边界

| 层 | 回答的问题 | 当前状态 |
| -- | ---------- | -------- |
| **设备层** | 这台设备现在是否正常？ | Phase 1 部分实现（蓝牙设备事件） |
| **链路层** | 这台设备为什么出现通信异常？ | Phase 1 实现断连原因；Phase 2 做 RSSI 基线与劣化 |
| **区域层** | 是一台设备坏了，还是这一片无线环境出了问题？ | Phase 3a 已实现：时空关联产出 `SiteIncident`，回答"影响了哪些设备、哪几条证据"；**"可能是什么原因"仍为空白**（`suspected_cause` 恒 NULL，属 Phase 4+ 诊断器） |

### Wi-Fi 与蓝牙的关系（当前阶段）

- **Bluetooth 是当前唯一被实例化的 `WirelessDevice` 协议**（Bluetooth-first）。
- **Wi-Fi 当前扮演 Environment Evidence Provider**：提供信道、频段、噪声、RF
  健康度等**环境证据**，而不是设备身份。Wi-Fi station 的身份问题（MAC 随机化、
  漫游、STA/AP/BSSID 关联变化）尚无产品依据，不在当前范围。
- 两者在**区域层**才相遇：做多设备时空关联时，Wi-Fi 异常作为环境证据参与，
  不强行合并成统一"设备模型"。

### 目标 vs 当前（多网关）

- **产品长期目标**：支持多网关组网（一个车间/仓库不会只有一个采集点）。
- **当前运行模型**：1 Gateway = 1 Site。
- **schema 从第一天保留** `site_id` / `gateway_id`——它们是**事件来源身份**
  （"这个事件是哪台探针看到的"），不是多网关功能。
- 多网关引入时改变的是 `site_id → 多个 gateway_id` 的关系，不必重改历史数据结构。

## 六、四个产品支柱

| 支柱 | 含义 |
| ---- | ---- |
| **实时观测** | 持续采集现场无线链路与设备状态 |
| **异常检测** | 从观测中识别设备级与区域级异常 |
| **根因诊断** | 给出可解释的结论：症状 → 证据 → 判断 → 建议 |
| **历史追溯** | 事后能回答"当时发生了什么"，是独立支柱而非附属功能 |

产品最终对用户输出的应该是：

```
症状（蓝牙音频不稳定）
  ↓
证据（10 分钟内 4 次链路异常，3 次 Connection Timeout，同期 RSSI 下降）
  ↓
判断（更可能是无线干扰或距离过远）
  ↓
建议（Wi-Fi 切至 5GHz / 缩短距离 / 检查设备电量）
```

而不是把 `RSSI -81 / effective_ratio 0.72 / gap 180ms` 直接甩给用户。
**把一堆数据变成结论，才是产品价值。**

## 七、边缘与云端职责

| 位置 | 职责 |
| ---- | ---- |
| **边缘网关** | 采集、状态维护、实时异常检测、低延迟事件生成 |
| **云端** | 跨时间、跨设备（以及未来跨网关）的聚合分析、可视化、知识辅助诊断 |

### 数据分级上传（避免把原始时序全量上云）

工业网关的原始观测数据量极大，必须分级：

```
Raw Observation          → 边缘短期保存
       ↓
Downsampled Time Series  → 云端趋势分析
       ↓
Event / Incident         → 必须可靠上云
```

## 八、当前实现状态（截至 2026-09-30）

| 能力 | 状态 |
| ---- | ---- |
| 蓝牙断连事件（`bt_events` eBPF → Canonical Device Event → `device_events` 表） | ✅ 真机端到端验证通过 |
| 蓝牙设备状态（BlueZ D-Bus：设备列表 / 连接态 / RSSI） | ✅ 已有 |
| Wi-Fi 环境证据（RSSI / 频段 / 丢包归因） | ✅ 已有（作为环境证据，非设备身份） |
| 网络质量评价体系（SLE / Assurance v2） | ✅ 已有（IP 网络域） |
| 事件查询出口（D-Bus `QueryDeviceEvents` / `weaknet-cli events` / `history_query_tool --events`） | ✅ phase1b 已实现 |
| RSSI 基线与 `LinkDegraded`（链路层） | ✅ Phase 2 已实现 |
| 区域级 `SiteIncident` 与多设备关联（区域层） | ⬜ **Phase 3a 已实现关联与查询**：设备事件 → `SiteIncidentCorrelator` → `site_incidents` + 证据回链；查询出口 D-Bus `QuerySiteIncidents` / `weaknet-cli incidents` / `history_query_tool --incidents`。**`suspected_cause` 恒为 NULL**——根因推断属 Phase 4+ 诊断器 |
| 事件上云与云端诊断 | ⬜ Phase 4 |

> **Phase 1 / 1b 的准确表述**：技术闭环 = `真实断连 → canonical event → 持久化 → 系统查询出口`
> （D-Bus / CLI / 查询工具三条路径，均只读）；诊断推断（`suspected_cause`）仍未开始。
