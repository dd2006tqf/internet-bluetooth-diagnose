# 架构设计：五层权责契约 v1

> **文档状态**：v1 架构权威文档（2026-10-03 定稿）
> **权威关系**：本文是产品分层权责与层间契约的唯一权威来源；领域对象语义仍以
> `docs/产品定位-工业无线诊断网关.md` 为唯一权威来源，两者互补不冲突。
> **适用范围**：后续所有 Prediction（预测）、Network Operations Council（决策）、
> Web（呈现与交互）改动，均以本文契约为验收依据；违背本文分层的提案，应被
> Code Review 直接驳回。

---

## 总则（一句话原则）

> **事实只由 L1 产生；诊断只由 L2 产生；预测只由 L3 产生；动作权限只在 L4 收口；
> L5 只执行已批准动作。执行结果只能作为新的 L1 事实回流。
> Web 不推断、不裁决、不直接执行，只承载展示与人工审批。**

这句话是本文档的最高条款。后续任何人提出"让 Council 顺便判断根因""前端按钮直接调
`pending_actions`""预测模型顺便修改板端告警阈值"之类的建议，均以此句作答：
**不属于这一层的权力。**

## 二、五层职责与禁止项

| 层 | 可以做 | 绝对不可以做 |
|---|---|---|
| **L1 Observation** | 采数据、记事件、算基线、聚合区域事故、接收 L5 执行结果作为新事实 | 不猜原因、不做预测、不下发动作 |
| **L2 Diagnosis** | 解释现象、产出 `Pattern + Hypothesis + Confidence` | 不控制设备、不预测未来、不改写历史事实 |
| **L3 Prediction** | 基于时序趋势产出 `RiskWindow` | 不改变 L2 的诊断结论、不引用未观测指标当事实、不承诺未校准的 TTF |
| **L4 Decision** | 消费契约 B/C/D 输入、提出动作建议（**建议权**）；Policy 产出准入决定（**准入权**）；人工产出批准（**批准权**） | Council 不发现新事实、不创造新根因；Policy 不篡改事实与历史；任何环节不越过 Approval 直接触达 L5 |
| **L5 Execution** | 只执行 `ApprovedAction`，并把执行结果作为新事实回流 L1 | 不接受未经批准的动作、不自行判断动作是否合理 |

**权力四分立（L4 内部，防止任何单一 LLM 跨权）**：

```text
Council    —— 建议权（recommended_action + rationale）
Policy     —— 准入权（allowed / risk / preconditions / approval_required）
Human      —— 批准权（approved_by / approved_at）
Execution  —— 执行权（generation / nonce / claim_token 防重放）
```

没有任何一个 LLM 能独立跨完这四层。

### L1/L2 边界：状态归约 vs 根因假设

端侧 SLE / Assurance 引擎到底属于 L1 还是 L2，按以下判断标准拍死：

> **L1 可以做确定性的状态归约和异常维度定位，但不得产生物理根因 Hypothesis。**

具体而言：

- `AssessmentSnapshot` 可以属于 L1。`reliability = BAD` / `state = DEGRADED` /
  `packet_loss = 4.2%` 这类输出不是传感器原始值，但它们是**确定性规则对事实状态的
  归约**，仍是 factual assessment：
  ```text
  Raw Observation → Deterministic Assessment → L1 factual state
  ```
- `primary_issue` 必须按语义切分：
  - `PRIMARY_ISSUE = PACKET_LOSS`（哪个已测指标导致状态门禁失败）→ 属于 L1；
  - `PRIMARY_ISSUE = RF_INTERFERENCE` / `GATEWAY_STACK_STALL`（回答"为什么坏"）→
    属于 L2。

归属示例表：

| 归属 | 示例 |
|---|---|
| **L1** | `GOOD / DEGRADED / BAD`、`packet_loss_violation`、`latency_violation`、`LinkDegraded` |
| **L2** | `COEXISTENCE_RF_INTERFERENCE`、`HOST_STALL`、`DISTANCE_OR_SHADOWING` |

此边界固化后，端侧 SLE 与 Phase 4b 永远不会"抢解释权"。

## 三、层间契约

### 契约 A：L1 → L2/L3（事实下行，只读）

复用已建成的 `IncidentEvidenceBundle`（`network_assurance/wireless_contracts.py`）：

```text
incident (SiteIncidentView)
+ qualifying_events (WirelessEventView[])
+ baselines (BaselineView{})
+ environment (EnvironmentWindowView)
```

- 来源表：`network_wireless_events` / `network_site_incidents` /
  `network_device_baselines` / `network_env_windows`（四张权威事实表）；
- **约束**：L2/L3 只读，永不回写四张事实表。Phase 3a 固化的不变量
  （`site_incidents.suspected_cause` 恒 NULL）即本契约的既有实例。
- **权威事实源不变量（正式定义）**：

  > L1 内部对象可以依据自己的领域生命周期合法演进；下游 L2/L3/L4/L5
  > 不得为了适配诊断、预测或决策结果反向修改 L1。

  各对象的合法演进形态：
  - `WirelessDeviceEvent` —— 近似 immutable（一旦落库不再变更）；
  - `SiteIncident` —— 按 `OPEN → ONGOING → RESOLVED` 生命周期演化；
  - `DeviceBaseline` —— 随新观测持续更新（含追加式变更历史）；
  - `EnvironmentWindow` —— 滑动窗口式更新；
  - `NetworkActionOutcome`（迁移 `0094`）—— **append-only 执行事实**：一次
    L5 执行实例的终态回执（`APPLIED/REJECTED/ROLLBACK`）在同一事务里
    投影为 L1 行。它记录"网关上被报告发生了什么"，不判断动作是否正确、
    安全或有效（`APPLIED` ≠ 故障已修复）。

### 契约 B：L2 → L4（当前诊断）

复用 `CanonicalDiagnosis`（Phase 4b 已实现，不变）：

```text
observed_pattern + hypothesis + confidence(HIGH/MEDIUM/LOW/INSUFFICIENT)
+ evidence_ids + deterministic_reasons + device_findings
```

- 纯确定性规则先决裁，LLM 只润色 `DiagnosisPresentation`，W1~W6 护栏把关。

### 契约 C：L3 → L4（未来风险 PredictionResult）【v1 修订：结构化 + 三态语义】

`PredictionResult` 是联合类型，**不是单一模型**。三态互不混淆：

```text
PredictionResult = RiskWindow | InsufficientPrediction
```

```text
RiskWindow {
    subject_type: DEVICE | SITE       # v1 只支持 DEVICE；SITE 保留枚举但返回 Unsupported
    subject_id

    risk_level: LOW | MEDIUM | HIGH   # 注意：不含 INSUFFICIENT/UNKNOWN

    window_estimation_status: AVAILABLE | UNAVAILABLE
    window_earliest_hours: int | null # 仅 AVAILABLE 时非空（机器可读，禁止 "24-72h" 字符串）
    window_latest_hours: int | null   # 仅 AVAILABLE 时非空
    forecast_horizon_hours: int       # 预测视野，恒为 168

    prediction_confidence: LOW | MEDIUM | HIGH    # 与 risk_level 必须分离
    data_sufficiency: PARTIAL | SUFFICIENT        # INSUFFICIENT 走 InsufficientPrediction

    drivers: [{
        metric,
        contribution_pct,            # 产品文案一律称"风险驱动贡献度"
        direction,                   # DETERIORATING | STABLE
        evidence_ids
    }]

    trend_evidence: [...]            # 事实性趋势证据（如基线连续下降）

    failure_criterion_id             # 失效判据的标识
    failure_criterion_version        # 判据版本（判据演化可追溯）
    model_version                    # 含参数指纹（阈值变化必使指纹变化）
    generated_at
}

InsufficientPrediction {
    subject_type, subject_id

    data_sufficiency: INSUFFICIENT   # 无风险判断产生
    missing_requirements: [...]      # 具体缺什么（哪项指标、哪项资格条件）
    available_evidence_ids: [...]

    model_version
    generated_at
}
```

**三态判定（互不混淆）**：

| 情形 | 产出 |
|---|---|
| 风险无法判断 | `InsufficientPrediction`（**系统没有产生风险判断**） |
| 风险可判断，但时间速度不可估 | `RiskWindow`（`risk_level` 有值，`window_estimation_status = UNAVAILABLE`，窗口为 null） |
| 风险与时间均可估 | `RiskWindow`（`window_estimation_status = AVAILABLE`） |

> **"没有风险判断"与"有风险判断但不知何时越界"是两件事，绝不合并。**
> "证据不足"不是第四种风险等级。

**契约 C 的七条纪律**：

1. **`risk_level` 与 `prediction_confidence` 必须分开**：可能出现"风险 HIGH、置信度
   LOW"（单一指标恶化 + 历史数据不足）。此思想与 L2 的 `Hypothesis + Confidence`
   一脉相承。
2. **第一版不承诺 TTF**：只交付"风险窗口"（`window_earliest_hours ~ window_latest_hours`）。
   严禁输出 `预计 48 小时后断连` / `RUL = 51.3h` 这类确定性倒计时。
3. **失效判据 = 相对退化 + 业务影响**，与 Phase 2 纯相对基线原则一致：
   绝对值（如 RSSI ≤ -90）只能作为 feature 之一，禁止作为全系统统一 failure truth
   （基线 -45 与 -82 的设备，绝对值语义完全不同）。判据本身以
   `failure_criterion_id + version` 显式声明、可演进，并**实际驱动窗口估计**：
   按判据各必需组件分别外推 crossing 时间，再按 AND（取 max）/ OR（取 min）聚合；
   单个 feature 达 1.0 **不等于** failure。任一必需组件无法可靠外推 →
   `window_estimation_status = UNAVAILABLE`，不得改用最坏 driver 兜底。
4. **`contribution_pct` 的产品文案固定为"风险驱动贡献度 / 模型贡献度"**，
   严禁写成"原因占比"——它只表示对模型输出的贡献，不表示现实故障的因果配比。
   v1 确定性算法：`raw_i = weight_i × normalized_degradation_i × trend_strength_i`，
   仅对实际存在且有效的指标归一化（Σ = 100% ± 1%）；**缺失指标不进分母、不当 0**。
5. **`HI_link` 健康指数降级为模型内部变量**：可参与拟合，但不是产品主指标；
   Web 主指标必须是 `risk_level + drivers`（可解释），不得以 `0.43` 这类裸分数作答。
6. **L3 的双基线域**：`operational_baseline`（Phase 2 自适应中位数）只服务 L1/L2
   状态判定；L3 观察的是 `prediction_reference`（窗口起点时**有效的成熟 baseline**）
   与其后的 `baseline_trajectory`。**绝不用 `current_rssi − current_baseline` 宣称
   发现慢性衰退**——自适应基线会把 -60→-64 的漂移吃掉，差值恒为 -1/-2dB。
7. **参数指纹不可省**：slope 阈值、最小样本数、窗口尺寸、连续窗口数、权重、判据参数
   等**任何会改变输出的参数**都必须进入 `model_version` 指纹；否则 threshold 从 0.3
   改到 0.5 却仍声称同一版本，历史结果无法复现。

### 契约 D：CouncilInput（L2 + L3 + 运维约束 → L4）【v1 修订：增加 DecisionEvidenceContext】

```text
CouncilInput {
    canonical_diagnosis                 # 契约 B
    risk_window                         # 契约 C

    evidence_context {                  # DecisionEvidenceContext（只读事实上下文）
        diagnosis_evidence_ids
        prediction_evidence_ids

        rf_facts        # 来自 L1 的空口事实（Wi-Fi 丢包、频段冲突警告、RSSI 基线…）
        kernel_facts    # 来自 L1 的内核事实（进程画像 Top N、skb_drop 归因…）
        device_facts    # 来自 L1 的设备事实（断连原因、事件时序…）
    }

    operational_constraints {           # 资产桥 + 生产约束
        affected_assets
        production_critical
        action_registry_whitelist       # 板端 ActionRegistry 白名单（技术可执行域）
        config_whitelist                # 板端可调参数白名单
    }

    knowledge_context                   # RAG，可选，只作参考
}
```

**`knowledge_context` 的定位（与 evidence 的硬边界）**：

```text
knowledge_context ≠ evidence ≠ source of truth
```

- RAG 检索到的既往案例可帮助专家"解释得更好、建议得更好"，但**绝不混入
  `evidence_context` / `source_bindings`，也绝不进入 W1~W6 护栏认可的 Evidence ID 集合**；
- 历史案例不能让当前事故被直接判成同类原因——历史是参考书，不是证据。

**为什么需要 `evidence_context`（防止三个专家失去存在价值，同时防止 Council 演变为第二套诊断系统）**：

- 若 RF/Kernel 专家只能读已总结好的 Diagnosis，则无"专家会商"可言；
  若任其自由读取一切原始指标并自行解读，则 Council 又变成第二套 Diagnosis。
- 折中解：**Council 可以引用、比较、权衡 L1 已存在的事实，但不能生成新的
  `ObservedPattern` / `Hypothesis`**。
  - 允许的表述（引用事实作判断依据）：
    > "内核事实 K12 显示 Gateway 协议栈未见异常，因此重启 Gateway 的收益依据不足。"
  - 禁止的表述（创造新根因）：
    > "新的根因是 USB controller crash。" ← 除非 L2 已形成该 hypothesis。

所有 `*_facts` 必须来自 L1 已落库事实，带 `evidence_ids` 可回溯。

### 契约 E：L4 内部与 L4 → L5【v1 修订：拆分为 E1 / E2】

#### E1：Council → Policy（只有建议权）

```text
ActionProposal {                      # Council（LLM 群体）的全部输出
    action_id | (config_key, config_value)   # 必须命中板端白名单
    rationale                           # 为什么建议
    proposed_preconditions              # 专家认为的执行前提（仅建议）
    source_bindings                     # 绑定的 diagnosis_evidence_ids / prediction 窗口
}
```

Council **只说"我建议做什么、为什么"**。它**不产出** `risk`、不产出
`approval_required`——那属于策略域，LLM 无权决定。

#### Policy：Action Policy Validator + Risk Policy（准入权）

```text
ActionDecision {
    normalized_action
    allowed: bool
    risk: LOW | MEDIUM | HIGH              # 由 Risk Policy 计算，非 LLM 给出
    required_preconditions
    approval_required: bool                # 由 Risk Policy 计算
    block_reason                           # 不允许时必填
}
```

固定管线：

```text
ActionProposal
    → Action Policy Validator（白名单 + Schema 校验）
    → Risk Policy（情境规则，如 production_critical && affected_devices>10
                   → 强制 approval_required=true）
    → ActionDecision
```

职责切分：**`ActionRegistry` 只回答"技术上可执行什么"；
Risk Policy 回答"当前情境允许不允许"。**

#### E2：L4 → L5（唯一合法的执行入口）

```text
ApprovedAction {                         # 人工批准后才生成
    normalized_action
    decision_id                           # 溯源至 ActionDecision

    risk
    satisfied_preconditions

    approved_by
    approved_at

    generation                            # 板端防重放高水位
    nonce
    claim_token
}
```

**只有 `ApprovedAction` 才允许进入 L5（`pending_actions` 队列）。**
板端现有安全链（generation 门禁 / claim_token 绑定 / 终态不可变回执）原样生效。

## 四、Presentation & Human Interaction Plane（原 L0 重命名）

不再称为 "L0 Presentation"，因为它是**横跨 L1~L4 的展示与人工交互平面**，
不是数据处理层。

**权限定义（修正版，替代"Web 永远只读"这一矛盾表述）**：

> **Web 无推断权、无策略裁决权、无直接执行权；
> Web 只展示各层产物，并作为人工意图与审批的交互入口。**

```text
Web
 ├─ READ L1（事实）
 ├─ READ L2（诊断）
 ├─ READ L3（预测）
 ├─ READ L4（提案 / 决策）
 │
 └─ Human approval intent（人工审批意图）
              ↓
        L4 Approval Service
              ↓
        ApprovedAction（契约 E2）
              ↓
           L5 执行
```

**绝对禁止的捷径**：`Web → pending_actions`。
所有执行必须走 `Web → L4 Approval → ApprovedAction → L5`。

**信息呈现顺序（工业运维 UI 铁律）**：

```text
事实（WHAT） → 影响范围 → 确定性模式（PATTERN） → 推断假说（HYPOTHESIS）
→ 证据（EVIDENCE） → AI 解释 → 建议动作（ACTION） → 未来风险（FUTURE RISK）
```

现场人员第一眼必须看到"7 台设备异常，持续 42 秒"，而不是"综合分析表明……"。
AI 报告永远排在事实与证据之后，不得占据页面首屏主位。

### ⑥ 补充：2026-10-08 真机排练复核（真实数据 + 真实模型）

在真实板端 incident 上重跑了一遍链路，结论按「真实可得 / 人工注入」分开记：

- **真实跑通的上游段**：板端真实 BLE 断连事件（2 台设备亚秒级同步 `CONNECTION_TIMEOUT`）
  → `SiteIncident` → 规范化诊断（`HIGH` / `COEXISTENCE_RF_INTERFERENCE`，`llm_used=true`，
  guardrail `ALLOWED`）→ 真实模型会商（attempt 2、3 成功）→ 2 条 `ACTION_ID` 提案
  → Policy 裁决（`LOW` / `MANUAL_RUNBOOK`）→ 审批（`APPROVED` / `REJECTED`）。
- **真实触发的安全边界**（非 fixture）：SoD 自批 403 `separation_of_duties`；
  `REJECTED` / `SUPERSEDED` 审批被 409 `approval_conflict` 拒；MANUAL 走 `/execute`
  409 `manual_execution_not_allowed`；runbook 恒 `execution_status=NOT_EXECUTED`；
  旧 attempt 审批被新 attempt 置 `SUPERSEDED`；异幂等键 409 `idempotency_conflict`、
  同键重放 `idempotent_replay=true` 不产生第二条 pending action；陈旧 `If-Match`
  409；未知 `proposal_id` 404。
- **远端腿（CONFIG_CHANGE → REMOTE_PENDING_ACTION）在本 incident 上不可得**：
  `action_policy` 把 `CONFIG_CHANGE` 写死映射为 REMOTE、`ACTION_ID` 写死映射为 MANUAL，
  而超时类 incident 的真实模型只产出 `ACTION_ID`（三次会商均如此）。
  故当前库中唯一的 REMOTE 链是**人工注入 fixture**
  （`proposal_id='ncouncil-10d3ed70cf6749b1-remote-config'`，`proposal_index=10`，
  digest 为占位串，不在 council 落库的 `proposals_json` 内）——
  **它不构成真实 Council 闭环证据**，远端腿需可控 fixture 另行设计。
- **会商脆弱性**：`recommendation_direction` 上限 1000 字符虽已写入 system prompt，
  模型仍偶发超长导致 `COUNCIL_SCHEMA_PARSE_FAILED` + fail-closed 409
  （10-07 五次会商中四次失败）；`?force=true` 重跑通常可成功。

各阶段验收均以本文契约字段为对账清单；阶段间不得跳序（未完成 ⑤ 前，
不得出现任何 `ActionProposal` 直达 L5 的通路）。
