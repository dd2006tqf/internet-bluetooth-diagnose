## 一、系统架构总览

本项目是一个 **基于 D-Bus 的 Linux 网络诊断与弱网监控系统**，采用 C/S 架构：

- **服务端**：常驻后台的监控守护进程，持续采集网络状态
- **客户端**：通信代理，封装 D-Bus 复杂性，提供 C API 供第三方集成
- **AI 分析模块**：基于 RAG 的网络问题智能分析（Python）

## 四、eBPF 程序清单（当前 6 个）

| eBPF 程序 | 挂点 | 功能 | 所属监控器 | server.cpp 线程 |
|-----------|------|------|-----------|----------------|
| `flow_rate.bpf.c` | `kprobe/tcp_retransmit_skb` + `kprobe/ip_queue_xmit` + `kprobe/udp_sendmsg` | 每进程 TCP/UDP 流量 + 重传统计 | `ProcessNetProfiler` | `start_process_net_profiler_thread` |
| `tcp_retransmit.bpf.c` | `kprobe/tcp_retransmit_skb` + `kprobe/tcp_sendmsg` | TCP 连接级丢包率 | `TcpLossMonitor` + `TcpRetransmitMonitor` | `start_tcp_loss_monitor_thread` |
| `dns_monitor.bpf.c` | `kprobe/udp_sendmsg` + `kprobe/udp_recvmsg` | DNS 解析延迟/超时 | `DnsMonitor` | `start_dns_monitor_thread` |
| `wifi_packet_loss.bpf.c` | `tracepoint/net/netif_receive_skb` + `net_dev_queue` + `net_dev_xmit` | Wi-Fi 收发丢包归因 | `WifiPacketLossMonitor` | `start_wifi_loss_monitor_thread` |
| `http_latency.bpf.c` | `kprobe/tcp_sendmsg` + `kprobe/tcp_recvmsg` | HTTP 请求级 TTFB 延迟 | `HttpLatencyMonitor` | `start_http_latency_monitor_thread` |
| `a2dp_media.bpf.c` | `kprobe/l2cap_sock_sendmsg` + `kprobe/__sock_sendmsg` | 蓝牙 A2DP 音频流量/卡顿 | `BtAudioAnalyzer`（经 BtMonitor） | `start_bt_monitor_thread`（Phase 2） |

### 同探针多消费者（架构决策）

`tcp_retransmit_skb` 探针被 **两个 eBPF 程序**分别挂载：
- `tcp_retransmit.bpf.c` → 按连接聚合算丢包率（`TcpLossMonitor`）
- `flow_rate.bpf.c` → 按 PID+连接聚合算每进程流量（`ProcessNetProfiler`）

两者账本结构、聚合键、消费者不同，**不做技术合并**，各自独立加载，但 init 都绑定到同一 `ServerContext` 生命周期（`server.cpp`）。这是显式的架构债。

## 五、服务端职责

### 核心职责：**数据采集 + 状态监控 + D-Bus 服务导出**

### 1. 监控线程矩阵（server.cpp 启动的 13 个线程）

| 监控项 | 采集方式 | 周期 | 输出 |
|--------|---------|------|------|
| **网卡列表** | 读取系统网络接口 | 10s | 接口名称、状态、IP、MTU、流量 |
| **当前上网网卡** | 路由表分析 | 10s | 正在上网的网卡名称 |
| **RTT 延迟** | ping 223.5.5.5 | 10s | 延迟毫秒数 |
| **Jitter 抖动** | 基于 RTT 标准差 | 2s | 抖动值 |
| **Wi-Fi 信号强度** | wpa_supplicant SIGNAL_POLL | 10s | RSSI dBm |
| **TCP 丢包率** | eBPF `tcp_retransmit.bpf.o` | 10s | 丢包率百分比 |
| **流量分析** | 读取 /proc/net/dev + eBPF | 10s | 带宽、活跃流数、包率 |
| **网络质量** | 综合评估 | 15s | 质量等级 |
| **蓝牙** | BlueZ D-Bus API | 3s | 设备列表、连接状态、RSSI |
| **DNS** | eBPF `dns_monitor.bpf.o` | 10s | 解析延迟/超时 |
| **Wi-Fi 丢包** | eBPF `wifi_packet_loss.bpf.o` | 10s | 收发丢包归因 |
| **HTTP 延迟** | eBPF `http_latency.bpf.o` | 10s | TTFB 分位数 |
| **进程画像** | eBPF `flow_rate.bpf.o` | 15s | 每进程带宽/重传 |

### 2. 生命周期管理（`ServerContext`）

`server.hpp` 的 `ServerContext` 结构体是服务端生命周期中枢，持有：
- 所有监控线程对象
- 所有 eBPF 监控器指针（`dns_monitor`、`wifi_loss_monitor`、`http_latency_monitor`、`process_net_profiler` 等）
- WeakNetMgr / BtMonitor / DbusService 指针

`start_server()` 按依赖顺序启动全部线程，`Looper::run()` 退出后逆序 `stop()` 释放 BPF 资源。

### 3. D-Bus 服务导出

#### 服务标识

```cpp
服务名:    com.example.WeakNet
对象路径:  /com/example/WeakNet
接口名:    com.example.WeakNet
```

#### 提供的方法

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `Get` | 无 | 字符串 | 示例方法 |
| `GetInterfaces` | 无 | 字符串数组 | 返回所有网卡列表 |
| `HealthCheck` | 无 | 字符串(JSON) | 网络健康检查结果 |
| `Ping` | 主机名 | 字符串 | Ping 结果（含延迟） |
| `GetBluetoothDevices` | 无 | 字符串数组 | 蓝牙设备列表 |
| `GetBluetoothAdapter` | 无 | 字符串 | 适配器状态信息 |

| 信号 | 触发条件 | 参数 |
|------|---------|------|
| `Changed` | 通用状态变化 | message, counter |

**EventManager**（全局单例）负责：
- 注册各类事件的回调函数
- 统一事件分发（invokeCallbacks）
- 通过 DbusService 发射对应的 D-Bus 信号

## 六、客户端职责

### 核心职责：**消费服务端数据 + 提供 C API 供第三方集成**

客户端是一个**通信代理**，把 D-Bus 的复杂性封装起来，让其他程序用简单的 C API 就能获取网络诊断数据。编译为 `libweaknet.so`。

### 1. 方法调用（主动查询）

```cpp
weaknet_get_interfaces()    → 获取网卡列表
weaknet_health_check()      → 获取网络健康检查
weaknet_ping_host(hostname) → 发起 Ping 请求
weaknet_get_bluetooth_devices() → 获取蓝牙设备列表
weaknet_get_bluetooth_adapter() → 获取适配器信息
```

### 2. 信号订阅（被动接收）

```cpp
weaknet_subscribe_event(type, callback)   → 订阅指定事件
weaknet_subscribe_bluetooth_events(cb)    → 订阅蓝牙事件
weaknet_subscribe_network_quality(cb)     → 订阅网络质量事件
```

### 3. 非阻塞检查（轮询模式）

```cpp
weaknet_check_events()          → 检查是否有新事件
weaknet_check_network_quality() → 检查网络质量变化
```

## 八、关键设计决策

### 1. 为什么使用 D-Bus？
- **Linux 原生 IPC**，无需额外依赖
- **支持信号推送**，无需轮询
- **多客户端支持**，同一信号多订阅

### 2. 为什么蓝牙用系统总线？
- BlueZ 运行在系统总线上
- 服务端运行在会话总线上，互不干扰

### 3. 为什么 Wi-Fi RSSI 不走 D-Bus？
- wpa_supplicant 提供 UNIX DGRAM socket（ctrl_interface）
- 直接通信比 D-Bus 更高效

### 4. 为什么 eBPF 监控？
- 内核级探针精确捕获，零开销
- 6 类指标（TCP 丢包、DNS、Wi-Fi 丢包、HTTP 延迟、进程流量、蓝牙音频）全部走 eBPF

### 5. 为什么 `server.cpp` 统一管理监控器生命周期？
之前多个 eBPF 监控器编译进二进制但未启动（孤儿）。`ServerContext` 统一持有并启动，确保每个加载的 BPF 程序都有消费者和数据出口。

## 十一、重要注意事项

1. **`ServerContext` 生命周期中枢**：任何新监控器必须纳入 `server.cpp` 的 `start_server()` 启动链，不能成为孤儿。
2. **同探针多消费者**：`tcp_retransmit_skb` 被 TcpLossMonitor 和 ProcessNetProfiler 共用，各自独立加载不合并。
3. **eBPF 编译环境**：必须用 ARM64 容器 + 预置 vmlinux.h，不能在 x86 裸编译。
4. **蓝牙事件路由**：所有蓝牙事件通过 `EventManager::emitBluetoothDeviceChanged()` 统一分发。
5. **编译产物不提交**：`bin/`, `build/`, `*.o`, `*.so`, `vmlinux.h`, `dist-arm64/` 已在 `.gitignore` 排除。
6. **工作流铁律**：项目使用 OpenSpec/AutoAI harness（见 `CLAUDE.md` 和 `docs/ai/`），planning/implementation/evaluation 三阶段分开。
