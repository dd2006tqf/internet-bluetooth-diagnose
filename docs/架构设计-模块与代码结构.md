## 一、系统架构总览

本项目是一个 **面向工业现场的无线信号检测与诊断网关**（产品定位见 `docs/产品定位-工业无线诊断网关.md`），采用 C/S 架构：

- **服务端**：常驻后台的监控守护进程，持续采集网络状态
- **客户端**：通信代理，封装 D-Bus 复杂性，提供 C API 供第三方集成
- **AI 分析模块**：基于 RAG 的网络问题智能分析（Python）

### 同探针多消费者（架构决策）

`tcp_retransmit_skb` 探针被 **两个 eBPF 程序**分别挂载：
- `tcp_retransmit.bpf.c` → 按连接聚合算丢包率（`TcpLossMonitor`）
- `flow_rate.bpf.c` → 按 PID+连接聚合算每进程流量（`ProcessNetProfiler`）

两者账本结构、聚合键、消费者不同，**不做技术合并**，各自独立加载，但 init 都绑定到同一 `ServerContext` 生命周期（`server.cpp`）。这是显式的架构债。

## 五、服务端职责

### 核心职责：**数据采集 + 状态监控 + D-Bus 服务导出**

### 1. 监控线程矩阵（17 个监控器插件 + 3 个非插件常驻线程）

| 监控项 | 采集方式 | 周期 | 输出 |
|--------|---------|------|------|
| **网卡列表** | 读取系统网络接口 | 10s | 接口名称、状态、IP、MTU、流量 |
| **当前上网网卡** | 路由表分析 | 10s | 正在上网的网卡名称 |
| **RTT 延迟（含 Jitter 衍生）** | ping 223.5.5.5；Jitter 由同一次采样做滑动窗口标准差（`rtt.window_size`） | 10s | 延迟毫秒数、抖动值 |
| **Wi-Fi 信号强度** | wpa_supplicant SIGNAL_POLL | 10s | RSSI dBm |
| **TCP 丢包率** | NETLINK_SOCK_DIAG / `tcp_info` | 10s | 丢包率百分比 |
| **TCP 重传统计** | eBPF `tcp_retransmit.bpf.o` | 10s | 连接级重传率与重传次数 |
| **流量分析** | 读取 /proc/net/dev + eBPF | 10s | 带宽、活跃流数、包率 |
| **网络质量** | 综合评估 | 15s | 质量等级 |
| **蓝牙** | BlueZ D-Bus API | 3s | 设备列表、连接状态、RSSI |
| **DNS** | eBPF `dns_monitor.bpf.o`（raw_syscall 捕获 → Tracker） | 10s（perf 排空 100ms） | 事务终态 + 解析延迟/超时 + 观测质量 |
| **Wi-Fi 丢包** | eBPF `wifi_packet_loss.bpf.o` | 10s | 收发丢包归因 |
| **HTTP 延迟** | eBPF `http_latency.bpf.o` | 10s | TTFB 分位数 |
| **进程画像** | eBPF `flow_rate.bpf.o` | 15s | 每进程带宽/重传 |
| **TCP 连接** | eBPF `tcp_conn_stats.bpf.o` | 10s | 入向连接生命周期与耗时直方图 |
| **Socket 丢包归因** | eBPF `skb_drop.bpf.o` | 10s | 内核协议栈丢包原因分类直方图 |
| **TCP 建连耗时** | eBPF `tcp_connect.bpf.o` | 10s | 出向 TCP 建连握手耗时分布 |
| **蓝牙设备事件** | eBPF `bt_events.bpf.o`（kprobe → ringbuf → 归一化） | 事件驱动（消费线程 200ms poll） | 断连事件 + 原因（`device_events` 表） |

**非插件常驻线程**（不占插件位）：
- **区域级异常关联**：消费 `device_events` 事件流 → SiteIncident（`site_incidents` 表 + `site_incident_events` 证据回链）
- **历史持久化**：5s 周期批量落盘
- **主动连通性探测**：`active_probe` 配置，默认关闭

### 2. 生命周期管理（`ServerContext`）

`server.hpp` 的 `ServerContext` 结构体是服务端生命周期中枢，持有：
- 所有监控线程对象
- 所有 eBPF 监控器指针（`dns_monitor`、`wifi_loss_monitor`、`http_latency_monitor`、`process_net_profiler` 等）
- WeakNetMgr / BtMonitor / DbusService 指针

`start_server()` 按依赖顺序启动全部线程，`Looper::run()` 退出后逆序 `stop()` 释放 BPF 资源。

#### D-Bus 派发层的三条硬约束（2026-11-01 实测确立）

`Looper::run()` 的主循环曾因一条错误注释埋下 P99 抖动缺陷（方法调用最坏 25s），
修复后形成三条必须保持的约束，回归测试见
`server/test/unit/test_looper_dispatch_gtest.cpp`：

| 约束 | 原因（实测证据） |
|---|---|
| **派发必须循环** | `dbus_connection_read_write_dispatch()` 一次只派发**一条**消息。积压 8 条时调用一次，回调只 +1，`dispatch_status` 仍为 `DATA_REMAINS`。 |
| **不能只看 POLLIN** | 内部队列有积压、socket 已读空时，`poll()` **不再**报告可读（实测 300ms 超时返回 0）。只在 POLLIN 分支派发会让积压等到下一条 socket 数据。 |
| **必须有轮次上限** | 无界 `while` 在持续有内部消息时饿死 self-pipe 的停止信号，SIGTERM/SIGINT 失效（systemd 停服要等 `TimeoutStopSec` 后 SIGKILL）。上限 `kMaxDispatchRounds = 64`。 |

修复后板端实测（Radxa Cubie A7A）：复用连接的服务端处理延迟
P99 从 21ms 级降到 **1.3ms**（空载）/ **6.1ms**（干扰负载），
systemd 停服 2.07s 正常完成、未触发 SIGKILL。

> **测量陷阱**：用 `dbus-send` 子进程逐次调用测延迟，会混入每次
> `fork+exec+总线认证` 的固定 11~13ms 开销，从而把健康服务误判为超标。
> 评估服务端延迟必须复用单条连接（`tools/interference_test.py` 已改为该方式）。

逐 key 差分（驱逐可见性）能力**不受信号停发影响**：启用了差分追踪的监控器

`keyStatsSnapshot()` 汇入 `GetEbpfMonitorHealth` 等查询方法，把「eBPF Map
是否被 LRU 驱逐限制观测」这一事实暴露出去：


同一个信封会让"哪一条失败、该重发什么"的语义互相耦合。

云端落四张租户事实表（`network_wireless_events` / `network_site_incidents` /
`network_device_baselines` / `network_env_windows`），供因果诊断装配证据包。

```
C++ 上报器                中心平台 (Large-Model-Application)
EdgeTelemetryExporter      /api/v1/network/edge/*
  │
  │ ① 上行：Ed25519 签名覆盖原始字节
  │ POST /api/v1/network/edge/telemetry
  │ X-Edge-{Key-Id,Token,Tenant,Signature}
  │ ─────────────────────────────────────────→ 验签 → 幂等入库
  │ ←───────────────────────────────────────── 200
  │   {accepted, duplicates, pending_actions[]}
  │
  │ ② 就地执行下发的配置
  │    setMonitorParam()  ← 复用白名单/类型/范围校验，不 shell out
  │
  │ ③ 下行结果回执（与上行同一轮循环内发出）
  │ POST /api/v1/network/edge/action-results
  │ {"schema_version":"network.edge.action-results.v1",
  │  "device_id":..., "results":[{action_id,status,detail,reported_at}]}
  │ ─────────────────────────────────────────→ 204，云端置 APPLIED/REJECTED
```

两个不变式：

- **签名覆盖发送字节**：序列化一次、对这段字节签名、原样发送，中途不重新序列化。跨语言（C++ 生产 / Python 校验）下任何"各自规范化再签名"都会因数字格式、键序差异而静默失配。
- **幂等键是 `(tenant, device, network_epoch, sequence_id)`**。`sequence_id` 是进程内计数器、每次重启从 1 重来，因此 `network_epoch` **必须跨重启推进**才能避免重启后的数据与历史键重合而被判重复。代次由 `data/network-epoch` 持久化（`NetworkEpochStore`），启动时 +1；状态损坏时从 `1000000` 重新起算而非回落 1。

## 八、关键设计决策

### 1. 为什么使用 D-Bus？
- **Linux 原生 IPC**，无需额外依赖
- **多客户端支持**，多路并发查询
- 信号推送能力曾被列出，但从未被任何生产订阅者消费——发射端在 O3-B
  停发后，当前实际用法是"方法调用 + 服务端落库/上行"，见第五章说明

### 2. 为什么统一使用系统总线（System Bus）？
- 服务端以 root 系统服务运行（eBPF 需要 CAP_BPF/CAP_SYS_ADMIN），用户会话总线（session bus）的生命周期与桌面/SSH 会话绑定，且实测不允许 root 连接
- 系统总线随系统启动、常驻运行、多用户可达，与服务端运行形态一致
- 蓝牙监控（BlueZ）本就运行在系统总线上，统一后无需跨总线中转
- 访问策略由 `/etc/dbus-1/system.d/com.example.WeakNet.conf` 放行本地用户

#### 服务单元的能力集合（含一处易漏项）

`tools/weaknet-server.service` 用 `CapabilityBoundingSet` / `AmbientCapabilities` 收窄特权，当前为：

```
CAP_NET_RAW CAP_NET_ADMIN CAP_BPF CAP_PERFMON CAP_DAC_OVERRIDE
```

`CAP_DAC_OVERRIDE` **不是可选加固项，删掉会静默破坏持久化**。原因是服务虽以 `User=root` 运行，但 `data/` 目录属于 `radxa:radxa` 且权限位不含 other 写位；内核的能力检查在 DAC 检查之前生效，`CapabilityBoundingSet` 一旦剔除了 `CAP_DAC_OVERRIDE`，root 就既不是属主、也不在属组、又失去了越权能力，只能以 "other" 身份被拒绝。后果包括：

- `history.db` 打不开 → 本地历史持久化整体失效（日志仅一行 `DatabaseManager: failed to open`，其余功能看起来完全正常）；
- `data/network-epoch` 写不进去 → 上行遥测的幂等代次无法跨重启推进，数据被服务端当重复丢弃。

两处失败都**不产生持续错误日志**，排查成本极高。判断方法：

```bash
# 目录属主与权限位
sudo ls -ld /home/radxa/weaknet/data
# 用与服务单元相同的属性集复现权限判定
sudo systemd-run --property=User=root --property=Group=root \
  --property="CapabilityBoundingSet=CAP_NET_RAW CAP_NET_ADMIN CAP_BPF CAP_PERFMON" \
  --wait --collect --pipe /bin/sh -c 'touch /home/radxa/weaknet/data/probe && echo OK && rm -f /home/radxa/weaknet/data/probe'
```

### 3. 为什么 Wi-Fi RSSI 不走 D-Bus？
- wpa_supplicant 提供 UNIX DGRAM socket（ctrl_interface）
- 直接通信比 D-Bus 更高效

### 4. 为什么 eBPF 监控？
- 内核级探针精确捕获，零开销
- 6 类指标（TCP 丢包、DNS、Wi-Fi 丢包、HTTP 延迟、进程流量、蓝牙音频）全部走 eBPF

### 5. 为什么 `server.cpp` 统一管理监控器生命周期？
之前多个 eBPF 监控器编译进二进制但未启动（孤儿）。`ServerContext` 统一持有并启动，确保每个加载的 BPF 程序都有消费者和数据出口。

## 十二、端侧智能诊断架构（Auditable & Resource-Aware Edge Intelligence）

> **引入时间**：2026-09-21
> **核心原则**：WeakNet 负责“判定事实与决定动作”，AI 负责“提供可读解释与操作辅导”。AI 解释属于顾问性质，机器诊断属于权威事实。

### 12.1 三层核心设计不变量

1. **决策权绝对属于确定性引擎**：
   * `fault_domain`、`primary_issue`、`secondary_issues`、`confidence`、`evidence_refs` 以及 `actions` 全部由确定性 C++ `DiagnosisEngine` 闭环决断；
   * LLM 无权推测网络故障，无权选择、增删或重新排序动作。
2. **AI Explanation 纯顾问与可随时丢弃（Advisory & Replaceable）**：
   * 若 LLM 超时、输出格式损坏或未通过 Contract Validator 契约校验，系统立即丢弃 AI 输出，自动回退到规则预置的 **Deterministic Fallback** 模板，绝不阻断核心网络诊断与处置。
3. **两阶段呈现（Progressive Display）**：
   * **Phase A（瞬时呈现，SLO: P99 < 5ms）**：提取系统权威不可变快照，立即向终端输出权威事实骨架；
   * **Phase B（受约束 JSON 生成与校验）**：LLM 完整生成受约束 JSON，通过 Validator 严格验证动作全等映射后补充呈现白话解释。

### 12.2 核心模块组成

```
┌────────────────────────────────────────────────────────────────────────┐
│                        WeakNet Core (C++ / eBPF)                       │
│  • 9 大 eBPF 探针内核级单一来源捕获                                    │
│  • 权威不可变快照: 带跨重启稳定 ID 的 AssessmentSnapshot                │
└───────────────────────────────────┬────────────────────────────────────┘

                                    ▼
┌────────────────────────────────────────────────────────────────────────┐

│  • PredicateEngine: 严格守住 Missing != false 的三态求值原则           │
│  • CausalResolver: 因果抑制剪枝 (网关故障抑制DNS) 与多故障共存判定     │

│  • 2. 强类型安全执行: safeExec 严禁经由 shell, 仅走 posix_spawn 参数   │
```

### 12.3 D-Bus 接口装配与闭环执行（消解孤儿接口）

为杜绝内部算法沦为仅单测调用的孤儿代码，系统在 `com.example.WeakNet` 系统总线上正式装配了如下生产接口：
* **`GetDiagnosis()` $\rightarrow$ `s` (JSON)**：
  * 直接读取当前 `AssessmentSnapshotStore` 不可变快照，由 `DiagnosisEngine` 结合 `EvidenceIdGenerator` 输出完整的 `DiagnosisFacts` JSON；
  * 被离线客户端 `weaknet-offline-diag` 直接消费作为 Phase A 事实源。
* **`ExecuteAction(action_id, param_key, param_val)` $\rightarrow$ `s` (JSON)**：
  * 将 `ActionRegistry::safeExec` 接入生产执行总线；
  * 执行前强校验参数白名单与 IPv4 格式，底层通过 `posix_spawn` 参数数组调用目标执行体，彻底隔绝 Shell 注入攻击面。

### 12.4 物理资源防争用与基准实测

* **硬件拓扑**：Radxa Cubie A7A（2× A76 大核 + 6× A55 小核，8GB LPDDR5）；
* **计算硬隔离**：两个服务都通过 systemd 限制各自的资源上限——`weaknet-server.service` 由 `LimitNOFILE=65536` 与 capabilities 集合收窄；`llama-server.service` 由 `MemoryMax=4.5G` + `CPUAffinity=0 1`（把推理钉在固定两颗核上）限制推理占用。
  > 注：单元文件的唯一权威来源是仓库 `tools/llama-server.service`（2026-11-01 单源化；此前仓库副本、文档 heredoc、板上实例三处各有一份，彼此漂移）。核对方式：
  > `ssh "$BOARD" 'systemctl show llama-server -p MemoryMax -p CPUAffinity -p CPUQuotaPerSecUSec'`。
  > 板端实测 `/proc/cpuinfo` 为 8× Cortex-A55（无 A76 大核），故 `CPUAffinity=0 1` 的含义是"固定两颗核、其余留给弱网服务与系统"，而非早期所称的"绑定 A76 大核"。
* **板载实测基准 (Qwen2.5-0.5B-Instruct-Q4_K_M)**：
  * 权重大小：469 MB，空闲内存 79 MB，推理峰值内存 ~380 MB；
  * 平均首字时延 (TTFT)：8442.42 ms；
  * 平均解码速率：3.49 tok/s；
  * 稳态满载温度：45.0 ℃（无降频，远低于 75 ℃ 门限）；
  * 满载推理干扰下 `weaknet-server` RSS 内存波动仅 0.96 MB（预算 < 5.0 MB）。

## 十三、重要注意事项

1. **`MonitorManager` 生命周期中枢**：任何新监控器必须注册为 `IMonitorPlugin` 并由 `MonitorManager` 协调，不能成为孤儿。
2. **同探针多消费者**：`tcp_retransmit_skb` 被 TcpLossMonitor 和 ProcessNetProfiler 共用，各自独立加载不合并。
3. **eBPF 编译环境**：必须用 ARM64 容器 + 预置 vmlinux.h，不能在 x86 裸编译。
4. **蓝牙事件路由**：所有蓝牙事件通过 `EventManager::emitBluetoothDeviceChanged()` 统一分发。
5. **编译产物不提交**：`bin/`, `build/`, `*.o`, `*.so`, `dist-arm64/` 已在 `.gitignore` 排除。`vmlinux.h` 只忽略 bpftool 自动生成到仓库根与 `server/` 下的副本；**`board-assets/vmlinux.h` 是预置构建输入，随仓库提交**（CI 依赖它编译 eBPF）。
6. **工作流铁律**：项目使用 OpenSpec/AutoAI harness（见 `CLAUDE.md` 和 `docs/ai/`），planning/implementation/evaluation 三阶段分开。
