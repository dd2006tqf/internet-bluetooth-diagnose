> **更新日期**：2026-09-22

## 一、项目概述

这是一个基于 eBPF + D-Bus 的 Linux 网络诊断与弱网监控系统，核心功能是实时监测网络状态、蓝牙设备、Wi-Fi 信号强度、TCP 丢包率、DNS 延迟、HTTP 请求延迟、每进程流量、网络流量等指标，并通过 D-Bus 将变化通知给客户端。同时包含 Python RAG 智能诊断模块，结合 LangChain + FAISS 实现自然语言故障诊断。

### 技术栈

| 技术 | 用途 |
|------|------|
| C++17 | 服务端核心语言 |

| 纯 C API 封装 | 客户端动态库对外接口 |
| **clang -target bpf (CO-RE)** | eBPF 程序编译 |

| 组件 | 职责 |

| `WeakNetMgr` | 弱网管理器：收集/管理网卡信息 |

| `Network Assurance Engine` | **网络体验保障引擎（MetricsRegistry + 4 大 SLE 纯函数评估 + OverallPolicy 负面优先决策 + StateStabilizer 防抖）** |

## 五、详细不足分析

### 1. D-Bus 实现过于底层

**问题**：直接使用 libdbus-1 C API 而非 GDBus/sdbus-c++

**影响**：代码冗长（`bt_monitor.cpp` 1000+ 行）、容易出错、维护成本高

**建议**：引入 `sdbus-c++`，代码量可减少 50%+

---

### 2. ~~事件路由混乱~~ (已修复)

**历史问题**：蓝牙事件曾错误使用 `InterfaceChanged` 信号；蓝牙 RSSI 曾混入 Wi-Fi `RssiChanged` 通道

**当前状态**：✅ 已修复，EventManager 统一路由，蓝牙事件正确使用 `BluetoothDeviceChanged` 信号

---

### 3. 序列化协议待完善

**问题**：D-Bus 信号只传一个字符串 + 计数器

**影响**：客户端需自己解析文本而非结构化 JSON/Protobuf

---

### 4. 缺少 D-Bus Introspection XML

**问题**：没有提供 D-Bus 接口描述文件，客户端无法自动生成绑定

---

### 5. ~~无单元测试~~ (已解决)

**当前状态**：✅ 已建立完整测试框架（250+ 用例，`ci.sh` 自动化入口）

---

### 6. 配置文件支持

**问题**：目标 IP、轮询周期等硬编码

---

### 7. eBPF 监控器的**信号**出口仍不完整

**问题**：各监控器的数据已可通过查询类 D-Bus 方法取出（`GetDnsStats`、`GetWifiLossStats`、
`GetHttpLatencyStats`、`GetProcessProfiling`、`GetSkbDropStats`、`GetEbpfMonitorHealth`），
但**主动推送**的信号只有 `Changed`/`InterfaceChanged`/`ConnectionModeChanged`/
`NetworkQualityChanged`/`BluetoothDeviceChanged`/`MonitorStateChanged` 六种，没有按监控器细分的信号。

**影响**：客户端要拿到 DNS/HTTP/进程画像的变化，只能轮询查询方法，无法订阅。

**建议**：为每进程流量、HTTP 延迟等新增细粒度信号（需同步扩展客户端的信号过滤表）

---

### 8. 错误处理不一致

**问题**：有些地方 `return false`，有些地方直接继续执行

## 六、监控线程一览

| 线程（插件名） | 周期 | eBPF |
|------|------|------|
| 网卡列表（`iface`） | 事件驱动 | 否 |
| 当前上网网卡（`using_iface`） | 事件驱动 | 否 |
| RTT 延迟（`rtt`，含 Jitter 衍生） | 10s | 否 |
| RSSI 信号强度（`rssi`） | 10s | 否 |
| TCP 丢包率（`tcp_loss`） | 10s | 否（netlink） |
| 流量分析（`traffic`） | 10s | `flow_rate.bpf.o` |
| 网络质量评估（`quality`） | 15s | 否 |
| 蓝牙（`bluetooth`） | 3s | `a2dp_media.bpf.o` |
| DNS（`dns`） | 10s | `dns_monitor.bpf.o` |
| Wi-Fi 丢包（`wifi_loss`） | 10s | `wifi_packet_loss.bpf.o` |
| HTTP 延迟（`http_latency`） | 10s | `http_latency.bpf.o` |
| 进程画像（`process_profiler`） | 15s | `flow_rate.bpf.o` |
| TCP 重传（`tcp_retrans`） | 10s | `tcp_retransmit.bpf.o` |
| TCP 连接生命周期（`tcp_conn`） | 10s | `tcp_conn_stats.bpf.o` |
| Socket 丢包归因（`skb_drop`） | 5s | `skb_drop.bpf.o` |

> 以上为 `MonitorManager` 管理的 16 个插件（8 传统 + 8 eBPF）。另有 2 个非插件线程由 `ServerContext` 单独管理：受控主动探测 `active_probe`（30s，默认关闭）与历史持久化（5s）。

## 七、总结

**优势**：
- **9 个 eBPF 程序**组成完整的内核级网络监控矩阵
- `MonitorManager` 生命周期统一管理 16 个插件
- 同探针多消费者解耦，架构债明确声明
- 工程化程度高：OpenSpec/AutoAI 工作流、ARM64 交叉编译容器、自动化测试

**待改进**：
- D-Bus 实现迁移到 sdbus-c++ 提升代码质量
- 增加配置文件支持
- 序列化协议完善（JSON/Protobuf）
- eBPF 监控器数据结构化出口

**定位**：中上水平的个人项目，技术深度和工程化程度较高，具备生产环境部署潜力。
