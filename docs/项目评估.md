# AI-powered Network Diagnostics 项目评估报告

> **更新日期**：2026-08-05
> 报告已按当前代码库现状更新：6 个 eBPF 程序、13 个监控线程、`ServerContext` 生命周期统一管理、ARM64 交叉编译容器。

## 一、项目概述

这是一个基于 eBPF + D-Bus 的 Linux 网络诊断与弱网监控系统，核心功能是实时监测网络状态、蓝牙设备、Wi-Fi 信号强度、TCP 丢包率、DNS 延迟、HTTP 请求延迟、每进程流量、网络流量等指标，并通过 D-Bus 将变化通知给客户端。同时包含 Python RAG 智能诊断模块，结合 LangChain + FAISS 实现自然语言故障诊断。

## 二、技术栈与核心组件

### 技术栈

| 技术 | 用途 |
|------|------|
| C++17 | 服务端核心语言 |
| libdbus-1 | D-Bus IPC 通信（C API） |
| BlueZ D-Bus API | 蓝牙设备监测（系统总线） |
| wpa_supplicant ctrl_interface | Wi-Fi RSSI 获取（UNIX DGRAM） |
| **eBPF + libbpf** | **6 类内核级网络监控（丢包/DNS/Wi-Fi/HTTP/进程流量/蓝牙）** |
| glog | 日志系统 |
| 纯 C API 封装 | 客户端动态库对外接口 |
| **clang -target bpf (CO-RE)** | eBPF 程序编译 |

### 核心组件

| 组件 | 职责 |
|------|------|
| `ServerContext` | **生命周期中枢，统一持有所有监控线程与 eBPF 监控器指针** |
| `DbusService` | D-Bus 服务端：方法调用 + 信号发射 |
| `WeakNetMgr` | 弱网管理器：收集/管理网卡信息 |
| `NetInfo` | 网卡信息模型（RTT/RSSI/TCP丢包/流量） |
| `BtMonitor` + `BtAudioAnalyzer` | 蓝牙监测 + eBPF 音频融合评估 |
| `EventManager` | 全局事件管理器：回调注册 + 信号分发 |
| `NetworkQualityAssessor` | 网络质量综合评估器 |
| `DnsMonitor`/`HttpLatencyMonitor`/`WifiPacketLossMonitor`/`ProcessNetProfiler` | 新增 eBPF 监控器 |
| `WeakNetClient` | 客户端：D-Bus 通信 + C API 封装 |

## 五、详细不足分析

### 1. D-Bus 实现过于底层

**问题**：直接使用 libdbus-1 C API 而非 GDBus/sdbus-c++

**影响**：代码冗长（`bt_monitor.cpp` 1000+ 行）、容易出错、维护成本高

**建议**：引入 `sdbus-c++`，代码量可减少 50%+

---

### 2. ~~事件路由混乱~~ (已修复)

**历史问题**：蓝牙事件曾错误使用 `InterfaceChanged` 信号；蓝牙 RSSI 曾混入 Wi-Fi `RssiChanged` 通道

**当前状态**：✅ 已修复，EventManager 统一路由，蓝牙事件正确使用 `BluetoothDeviceChanged` 信号

---

### 3. 序列化协议待完善

**问题**：D-Bus 信号只传一个字符串 + 计数器

**影响**：客户端需自己解析文本而非结构化 JSON/Protobuf

---

### 4. 缺少 D-Bus Introspection XML

**问题**：没有提供 D-Bus 接口描述文件，客户端无法自动生成绑定

---

### 5. ~~无单元测试~~ (已解决)

**当前状态**：✅ 已建立完整测试框架（250+ 用例，`run_all_tests.sh`）

---

### 6. 配置文件支持

**问题**：目标 IP、轮询周期等硬编码

---

### 7. eBPF 监控器数据出口待完善

**问题**：`ProcessNetProfiler`（进程画像）等新监控器的数据通过日志输出，尚未接入完整的结构化 D-Bus 信号出口

**建议**：为每进程流量/HTTP 延迟等新增 D-Bus 细化信号

---

### 8. 错误处理不一致

**问题**：有些地方 `return false`，有些地方直接继续执行

## 七、总结

**优势**：
- **6 个 eBPF 程序**组成完整的内核级网络监控矩阵
- `ServerContext` 生命周期统一管理 13 个线程 + 6 个监控器
- 同探针多消费者解耦，架构债明确声明
- 工程化程度高：OpenSpec/AutoAI 工作流、ARM64 交叉编译容器、自动化测试

**待改进**：
- D-Bus 实现迁移到 sdbus-c++ 提升代码质量
- 增加配置文件支持
- 序列化协议完善（JSON/Protobuf）
- eBPF 监控器数据结构化出口

**定位**：中上水平的个人项目，技术深度和工程化程度较高，具备生产环境部署潜力。
