# 多网关空口空间拓扑融合设计（Phase 5+）

> **状态**：设计文档（**只出设计，不写实现**）
> **编制**：2026-10-03
> **前置**：第 3 项（物理拓扑元数据）与第 4 项 M1/M2（身份解耦与现场聚合视图）已落地。
> **定位依据**：`docs/产品定位-工业无线诊断网关.md` 第五节"三层模型与当前边界"。

---

## 一、这份文档要回答什么

产品长期目标是**多网关组网**（一个车间/仓库不会只有一个采集点）。M1/M2 已经把
"身份能表达多网关"做出来了，但**空间语义**仍是空白。本文件回答四个问题：

1. 多网关对同一 AP 的观测如何合并（BSSID 空间图）；
2. 同一设备被多台网关先后观测如何形成轨迹（设备空间轨迹）；
3. 同一现场多台网关各起一起事故，是否算同一物理事件（区域事故归并）；
4. 上述推断在什么情况下**必须放弃**（不确定性边界）。

**本文件不预决实现方案**，只定义问题边界、必需的数据模型与判据纪律。

## 三、问题一：BSSID 空间图

### 输入

第 3 项已在遥测快照里上行 `ap_bssid` / `ap_ssid` / `link_type`（含精确频段）。
每台网关各自知道自己关联的是哪个 AP。

### 关键洞察

同一车间里，多台网关**听到同一个 AP 的 BSSID** 是常态（AP 覆盖重叠）。
BSSID 是 IEEE 分配、全球唯一且**不随机化**的（与设备 MAC 不同），因此它是
唯一可靠的"固定锚点"。

### 由此可以做什么

- **锚点图**：把 `BSSID → {gateway_id, RSSI, 时间}` 聚合成"哪几台网关能听到哪个 AP"；
  这给出了**网关之间的相对位置约束**（能同时听到同一 AP 的网关必然地理接近）。
- **环境证据**：AP 数量与信道分布在 site 内是稳定事实，可作为区域级环境基线。

### 需要的新数据

| 项 | 说明 |
|---|---|
| `network_gateway_deployments` | 每个 gateway 的物理坐标 `(x, y, z)`、天线朝向、有效观测半径、标定时间。**当前不存在**，需要现场勘测填入 |
| AP 锚点聚合视图 | 从 `network_wireless_events` 之外的遥测快照抽取 `ap_bssid` 按 gateway 聚合。**注意**：`ap_bssid` 目前只在遥测快照（`network_snapshots.experience_json`）里，不在无线事实表里，聚合需要读 JSON 列或另建投影 |

## 四、问题二：设备空间轨迹

### 输入

`device_baselines` 的复合主键是
`(site_id, gateway_id, hci_index, protocol, address_type, device_address)`
——**同一 MAC 在不同网关下天然是两条独立画像**。这正是轨迹的前提。

### 可做什么

把同一 `(site_id, address_type, device_address)` 在不同 `gateway_id` 下的
画像按时间排列，得到"这台设备先后被哪几台网关看到"的**漫游序列**。

### 判据纪律（重要）

- **同 MAC ≠ 同物理设备**：`BtAddressType::LeRandom` 的地址会周期性重生成。
  因此轨迹只在 **address_type 一致 + 时间连续** 时才成立；一旦观察到
  `LeRandom` 地址消失又出现，必须当成新的观测身份，**不得**判定为"设备移动回来"。
- **不得由轨迹反推距离**：轨迹只回答"先后被谁看到"，距离必须由 RSSI 模型给出
  （问题三），两者不可互相替代。

## 五、问题三：区域事故的空间归并

### 现状

M1 之后，同 site 的两台网关会各自产出独立的 `incident_id`（含 gateway 段）。
这是**刻意的**——两起独立事故不能被静默合并。但它们**可能**是同一物理事件
（一次区域干扰被两台探针同时观测到）。

### 需要回答的问题

> 同一 site 内、时间窗重叠的两起 `SiteIncident`，何时应当被判定为**同一物理事件**？

### 候选判据（需评审，本文件不预决）

| 判据 | 依据 | 风险 |
|---|---|---|
| 时间窗重叠 | 两台网关在 `correlation_window` 内各自达标 | 时间重叠是相关不是因果 |
| 设备集合重叠 | 同一批设备地址被两台网关同时观测到 | MAC 随机化会误判 |
| 空间接近 | 两台网关的物理距离 < 阈值（需 deployments 坐标） | 依赖现场勘测质量 |
| 环境证据一致 | 两台网关的 `wifi_anomaly` 同时为真 | 环境窗口当前粗粒度 |

### 存储形态（二选一，待评审）

- **A. 新增 `site_incident_groups`**：把同物理事件的多条 incident 归到一个 group，
  group 不改写 incident 本体（事实与解释继续分离）。
- **B. 不加新表**：云端在查询/展示时按上述判据动态聚合，不落库。

**倾向 A**：与"Event 不可变 / Incident 是解释"的既有分层一致——group 是**更高一层的解释**，
且可独立演进其判据而不动底层事实。

### 与诊断的关系

归并是**关联层**行为（回答"这是不是一起事故"），**不是诊断层**行为（回答"为什么"）。
`wireless_rules.py` 的 `ObservedPattern` 若要新增空间类模式（如
`AREA_WIDE_INTERFERENCE_ZONE`），必须先进 `HYPOTHESIS_MAX_CONFIDENCE` 上限表，
并按既有纪律由护栏校验证据 ID。

## 六、问题四：不确定性边界（必须写进实现）

| 情形 | 必须降级为 | 理由 |
|---|---|---|
| 网关无物理坐标 | 不做任何空间推断 | 没有坐标就没有空间 |
| 网关坐标未标定或标定过期 | 空间推断标记为 `uncertain` | 坐标是人的输入，会失效 |
| 时序无法对齐（时钟偏差 > 归并窗） | 不做跨网关时序归并 | 错误的时序对齐比不做更危险 |
| 设备地址类型为 `LeRandom` 且中途变化 | 视为不同观测身份 | 随机化使身份不可续 |
| 只有一台网关能观测到某设备 | 不做定位（欠定） | 单点无法三边测量 |

**一条总纪律**：空间推断**永远不写入事实表**。`device_events` /
`site_incidents` 是不可变事实；坐标、位置估计、盲区评分都是**派生解释**，
落在独立的投影表或视图里，可随时重算。

---

## 七、必需的数据模型（清单，实现时逐项立项）

| 名称 | 用途 | 依赖 |
|---|---|---|
| `network_gateway_deployments` | 网关物理坐标与射频参数（含标定元数据） | 现场勘测 |
| `network_sightings`（投影） | 跨网关观测归并（同一设备被哪些网关在什么时间看到） | M2 已有的事实表 + 时钟对齐 |
| `network_propagation_models` | 按 site 标定的路径损耗参数（`n`、参考损耗、阴影衰落） | 现场标定 |
| `network_position_estimates`（投影） | 多点 RSSI → 设备位置估计 + 协方差 | deployments + propagation |
| `network_site_coverage_grid`（投影） | 网格覆盖/盲区评分 | deployments + sightings |

**上行契约**：若需要携带板端时钟偏差用于跨网关对齐，应作为
`WirelessEventUplinkBatch` 的**可选**字段加入（旧 payload 不带即走单网关路径，
与既有 `env_window` 缺省处理一致）。

## 八、建议的推进顺序

| 阶段 | 内容 | 前置 |
|---|---|---|
| N1 | `network_gateway_deployments` + 标定工作流（人的输入） | 现场勘测 |
| N2 | 时钟偏差字段上云 + `network_sightings` 投影 | N1 无关，可并行 |
| N3 | `network_propagation_models` 标定 | N1 |
| N4 | 多点定位 `spatial_fusion` + `network_position_estimates` | N1+N3 |
| N5 | 区域事故归并（§五，需先定 A/B 方案） | N1 |
| N6 | 盲区判定 `network_site_coverage_grid` | N4 |

**强烈建议先做 N1**：没有物理坐标，后面全部无从谈起；而坐标只能由人填。
在 N1 落地前，空间类能力应当保持**诚实不可用**（返回 `UNKNOWN` 而非猜测）。

---

## 九、明确不做（当前阶段）

- 不做 ASN / 运营商级定位；
- 不做 Wi-Fi station 身份模型（MAC 随机化、漫游、STA/AP/BSSID 关联语义尚无产品依据）；
- 不做跨 site 聚合（当前 1 Gateway = 1 Site 的运行模型不变，多 site 是另一层扩展）；
- 不在事实表里写入任何推断字段。
