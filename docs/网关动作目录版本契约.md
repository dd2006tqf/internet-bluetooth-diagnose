# 网关动作目录版本契约（跨端执行前置条件）

> 状态：2026-10-08 实施中
> 关联：路线图 ⑤（Action Policy）的 fail-closed 防线；⑥ 的真机排练复核

## 一、问题（为什么需要这份契约）

路线图 ⑤ 的 Policy 有一条 fail-closed 防线：

```text
云端审阅目录 != 目标网关宣称目录 → allowed=False（catalog_version_mismatch）
```

`action_policy.py:202` 实现正确、单测覆盖充分（`test_action_policy.py:118` 等
`gateway_catalog_version="cat-old"`）。**但真实运行中这条防线永不触发**：

- `build_request_from_tables()` 从不设置 `gateway_catalog_version`，恒取默认值
  `TOP_LEVEL_CATALOG_VERSION`（`network_council_service.py:150`）；
- 板端从不上报任何目录版本（上行报文只有 `schema_version`）；
- 全仓所有非默认值 **100% 出现在 `tests/` 里**。

结论：这不是"缺陷"，是**未接线**——云端与网关各自持有目录，但**没有任何一侧
对比过**。本契约把这条比较接上，让 ⑤ 已有的防线真正具备输入源。

## 二、契约

### 2.1 指纹算法（两端必须逐位一致，否则真机全量误判漂移）

指纹 = SHA-256（12 位十六进制前缀），输入是**规范 JSON**：

```json
{"actions":{"<action_id>":{"params":[{"allowed":[...],"name":..,"required":..,"type":..}]}},
 "config_keys":["<key>",...]}
```

规范化要求（与云端 `_canonical_payload()` 完全一致）：
- 顶层键顺序固定：`actions` 在前、`config_keys` 在后；
- `actions` 的键**按 action_id 升序**；
- 每个 action 只有一个 `params` 键；param 字段顺序固定为
  `allowed, name, required, type`；
- `config_keys` **按字典序升序**；
- 无空白（separators `("," ":")`）。

`allowed` 为空时须序列化为空数组——两端必须**同样输出** `"allowed":[]`。

金标向量（两端必须都得到此值）：

```text
bdb093ac5310
```

### 2.2 传输

| 项 | 决定 |
|---|---|
| 通道 | 复用既有 `/api/v1/network/edge/wireless-events`（**不新增端点**） |
| 字段 | 顶层 `catalog_version: str \| None`，可选，1–64 字符 |
| 语义 | 设备**自述**其 L5 可执行目录指纹；服务端只做事实记录与对比，不据此授权 |

### 2.3 缺失语义（关键：决定会不会把现有真机全线阻断）

| 情形 | 行为 | 理由 |
|---|---|---|
| 设备上报版本 == 云端 | 记录；Policy 放行 | 正常 |
| 设备上报版本 != 云端 | 记录为漂移事实；Policy 依 ⑤ 原语义 fail-closed | 本契约要接通的正是这条 |
| 设备**未上报**（`None`） | **不阻断**：回落既有"无漂移事实"语义 | 缺数据不等于漂移。若把缺失当漂移，所有旧固件与排练环境会被全线 403，而它们并没有被证明跑在漂移目录上 |

「缺失 = 不阻断」是**刻意的保守选择**：本契约的目标是让"已声称的漂移"可被发现并
拒绝，而不是把未申报变成新的拒绝理由。把缺失升级为阻断需要固件版本门禁等更强
前提，属于后续独立议题。

## 三、实现落点

### 3.0 既有防线（实现前必须知道）

`Large-Model-Application/tests/test_edge_action_catalog.py` **已经**是一条跨端
一致性防线：它解析 `action_registry.hpp` 的 `registerAction({...})` 块与
`weaknet_config.cpp` 的 `trialable = {...}` 列表，与云端镜像逐字段比对。
因此本契约**不需要**再新建"两端是否同源"的机制，只需要：

1. 让指纹本身两端可比（下表）；
2. 在两个测试套件里各钉同一金标值。

**坑（已踩过一次）**：该解析器用正则匹配 ``trialable\s*=\s*\{(.*?)\};``——
若把白名单改成 lambda 初始化（`= [] { ... }()`）以图排序方便，正则失配、
解析器抛错，这条防线会**静默失效**（当时确实打断了
`test_config_keys_cover_edge_trialable_whitelist`）。因此原始声明必须保持
花括号字面量形态；排序只能作用于其副本。

## 四、验收

1. **金标对照**：C++ 与 Python 各自算出 `bdb093ac5310`，且 C++ 输出与
   `_canonical_payload()` 逐字节相同。
2. **单测**：新增/扩充覆盖——两端一致（无漂移）、漂移（fail-closed）、缺失（不阻断）。
3. **真机**：板端上行的 `catalog_version` 落库；真机排练的会商输入携带真实网关版本，
   且**当前无漂移**（板端与云端同源）；
4. **不回归**：既有 259 项非 live 测试保持全绿。

## 五、2026-10-08 验收记录（真实运行）

### 5.1 通过项

| 项 | 证据 |
|---|---|
| 金标对照 | 两端载荷逐字节相同，版本均为 `bdb093ac5310` |
| 跨架构 | ARM64（QEMU）与 x86 指纹一致——SHA-256 不依赖架构 |
| 单测 | C++ `ctest 48/48`；Python `269 passed`（改前 259） |
| 真机正常路径 | 板端 ARM64 二进制自述 `bdb093ac5310` → 落库 → `build_request_from_tables` 读入，与云端一致，**无误判漂移** |
| 迁移 | PG 上应用成功，模型/迁移逐列对齐（6 列、主键一致） |

### 5.2 漂移防线真机演示（P2-B）

做法：暂停板端上行（否则每 10s 重报会覆盖演示值）→ 手工把落库值改为
`deadbeef0000` → 在真实 incident 上触发真实模型会商 → 观察 Policy 裁决。

结果（`ncouncil-49e352cdb3fc4d87`，真实模型产出 3 条 `ACTION_ID` 提案）：

```text
proposal                      allowed  block_reason
ncprop-49e352cdb3fc4d87-a2-0  False    catalog_version_mismatch: cloud=bdb093ac5310 gateway=deadbeef0000
ncprop-49e352cdb3fc4d87-a2-1  False    catalog_version_mismatch: cloud=bdb093ac5310 gateway=deadbeef0000
ncprop-49e352cdb3fc4d87-a2-2  False    catalog_version_mismatch: cloud=bdb093ac5310 gateway=deadbeef0000
```

不变量链完整成立：

- 该会商 **3 条提案落库可审计**，但 **0 条审批行**；
- 审批视图里三条的 `decision.allowed=False`、`approval=None`；
- 对被拦提案调 `/decision` 返回 **404 `proposal_not_found`**——是"审批对象根本
  不存在"，而不是"存在但被策略拒绝"。这条区分正是 ⑤ 的 P0-2 语义。

**这是本契约价值的直接证明**：改动前该 `block_reason` 永不出现（`gateway_catalog_version`
恒为默认值，比较恒等）。演示后已恢复板端上行，真实版本自动重报覆盖演示值——
漂移是瞬态的，会被正确值自动纠正。

### 5.3 遗留

- 板端仍需**旧固件**才能自然产生真实漂移：当前演示用的是手工注入值。
  真实场景需要"网关目录 != 云端目录"（例如网关降级到旧版本、或云端先行更新）。
- 会商本身仍受上游模型脆弱性影响（本次 3 次触发中 1 次 `COUNCIL_MODEL_FAILED`、
  1 次失败重试），与漂移无关，见 `PLATFORM_OPERATION_GUIDE.md` 遗留事项。
