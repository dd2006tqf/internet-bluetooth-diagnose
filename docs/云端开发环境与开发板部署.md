# 云端开发环境与开发板部署

本文档描述把日常开发从本地 x86 电脑迁移到**公网轻量云服务器**后的拓扑与操作方式。
本地电脑不再需要长期开机；ARM64 交叉编译、部署与真机测试全部在云端完成。

> 前提阅读：`docs/交叉编译与开发板部署.md`（ARM64 容器构建原理与日常循环）。
> 本文只描述**拓扑变化**：构建机从本地电脑换成云端服务器，以及由此引入的反向隧道。

---

## 一、拓扑

```
┌──────────────────────────────────────────────┐
│  云端开发服务器 (Ubuntu 24.04 x86_64, 4C/4G)  │
│  81.71.76.133                                 │
│                                              │
│  ~/个人学习/AI-powered-Network-Diagnostics/            │
│    ├── build-x86/    x86 快速编译 + 单元测试   │
│    ├── build-arm64/  ARM64 增量编译（QEMU）    │
│    ├── dist-arm64/   部署产物                 │
│    └── weaknet-arm64-dev (常驻 ARM64 容器)    │
│                                              │
│  127.0.0.1:2222  ──┐ 反向隧道落点             │
└────────────────────┼─────────────────────────┘
                     │ ssh -R 2222:localhost:22
                     │ （由开发板主动发起）
┌────────────────────┼─────────────────────────┐
│  开发板 (Radxa Cubie A7A, ARM64)              │
│  家庭局域网 wlan0, 无公网地址                  │
│  /home/radxa/weaknet/                         │
│  cloud-tunnel.service  ← 维持隧道并自动重连    │
└──────────────────────────────────────────────┘
```

**为什么需要反向隧道**：开发板在家庭 NAT 后没有公网地址，云端无法主动连它；
但开发板有正常出网能力，因此由**板子主动拨号**到云端建立 `-R` 隧道，
云端便可通过 `127.0.0.1:2222` 访问板子的 22 端口。

隧道只绑定在云端回环地址（sshd `GatewayPorts no`），不对公网暴露。

## 二、一次性配置（已完成，此处仅记录）

### 2.1 云端

| 项目 | 内容 |
|------|------|
| SSH 免密 | 本地电脑公钥已加入云端 `~/.ssh/authorized_keys`（别名 `cloud-dev`） |
| 构建依赖 | `build-essential cmake pkg-config ccache libdbus-1-dev libgoogle-glog-dev libsqlite3-dev libgtest-dev libssl-dev libcurl4-openssl-dev libnl-3-dev libnl-genl-3-dev clang llvm libelf-dev libbpf-dev ripgrep` |
| ARM64 容器 | 镜像 `weaknet-builder:bullseye-arm64` 与 `weaknet-arm64-dev-running:latest` 由本地 `docker save | zstd` 流式导入；容器名 `weaknet-arm64-dev` |
| vmlinux.h | `board-assets/vmlinux.h` 从本地传入（被 .gitignore 忽略，clone 不含） |
| 板子侧密钥 | `~/.ssh/id_board`（云端用它登板子） |
| 隧道别名 | `~/.ssh/config` 中 `Host board`（127.0.0.1:2222, User radxa） |
| 主机名 | `/etc/hosts` 增 `127.0.0.1 board`（满足 `ci.sh` 的 ping 可达性检查） |
| 默认目标板 | `~/.bashrc` 中 `export BOARD=radxa@board` |

### 2.2 开发板

| 项目 | 内容 |
|------|------|
| 隧道密钥 | `~/.ssh/id_cloud_tunnel`（板子用它登云端） |
| 隧道服务 | `/etc/systemd/system/cloud-tunnel.service`，`enable` + `Restart=always` |
| 云端公钥 | 云端 `id_board.pub` 已加入板端 `~/.ssh/authorized_keys` |

`cloud-tunnel.service` 内容：

```ini
[Unit]
Description=Reverse SSH tunnel to cloud dev server (cloud-dev:2222 -> board:22)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=radxa
ExecStart=/usr/bin/ssh -o BatchMode=yes -o StrictHostKeyChecking=no \
    -i /home/radxa/.ssh/id_cloud_tunnel \
    -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes -o TCPKeepAlive=yes \
    -N -R 2222:localhost:22 ubuntu@81.71.76.133
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

## 三、日常循环（云端）

```bash
ssh cloud-dev                       # 本地电脑拨入云端
cd ~/个人学习/AI-powered-Network-Diagnostics

# x86 快速验证
cmake -B build-x86 -DCMAKE_BUILD_TYPE=Debug -DBUILD_EBPF=OFF
cmake --build build-x86 -j4
ctest --test-dir build-x86/server --output-on-failure

# ARM64 编译 + 打包 + 部署到板子 + 真机冒烟（唯一入口）
./tools/ci.sh                       # BOARD 默认已是 radxa@board
```

`ci.sh` 会自动完成：容器内 ARM64 增量编译 → 打包 `dist-arm64/` →
`rsync` 经隧道同步到板端 → 重装 systemd 单元与 D-Bus 策略 → 重启服务 → 跑板端冒烟套件。

只编译不部署：`./tools/ci.sh --local-only`。

> **注意 `BOARD` 的两种写法**：`~/.bashrc` 的 `export BOARD=radxa@board` 与
> `~/.ssh/config` 的 `Host board`（已含 `User radxa`）等价，因此 `BOARD=board`
> 也合法——`ssh` 会把 `User` 补上。但 `ci.sh` 开头的 `ping ${BOARD#*@}` 依赖
> `/etc/hosts` 里 `127.0.0.1 board` 这条记录，不能写成 `.local` 主机名：
> 云端与开发板不在同一广播域，mDNS 不可达，`radxa-cubie-a7a.local` 在这里永远
> 解析失败。若换一台没有 `.bashrc`/`/etc/hosts` 配置的云端机器，部署前要补
> `export BOARD=radxa@board`（或 `BOARD=board`）。

### 手动 ARM64 编译

```bash
docker exec weaknet-arm64-dev bash -c 'cd /src && cmake --build build-arm64 -j1'
```

`-j1` 是硬约束（QEMU 模拟下高并行度会 segfault）。

## 四、隧道运维

```bash
# 云端：看隧道端口
sudo ss -tlnp | grep 2222

# 云端：直连板子
ssh board
ssh board 'uname -m'

# 板端：隧道服务状态
ssh board 'systemctl status cloud-tunnel.service'
ssh board 'sudo systemctl restart cloud-tunnel.service'
```

隧道断开时按序排查：

1. 板子是否在线（本地同网段时 `ssh board`）；
2. 板子出网是否正常：`ssh board` 不通时先在板端 `curl -s -o /dev/null -w "%{http_code}" http://81.71.76.133`；
3. 板端服务是否在跑：`systemctl is-active cloud-tunnel.service`；
4. 云端 `authorized_keys` 是否仍含 `board-to-cloud` 公钥。

隧道由开发板侧 `Restart=always` 守护，板子重启后约 10 秒自动恢复，无需人工干预。

## 五、与本地部署的关系

本地电脑与开发板同网段时，原有直连方式仍然可用：

```bash
BOARD=radxa@board ./tools/ci.sh
```

注意 `radxa-cubie-a7a.local` 是 mDNS 链路本地名称，**只在同一广播域内可解析**，
云端与板子跨网段，因此云端一律使用 `board`（隧道别名），不要写 `.local`。

## 六、首次部署的清理前置

板端若残留 root 创建的旧目录（如 `server/server/`、`logs/`），
`rsync --delete` 会因属主不匹配报 exit 23。部署前先清：

```bash
ssh board 'sudo rm -rf /home/radxa/weaknet/server/server /home/radxa/weaknet/logs'
```

`ci.sh` 已内置部分清理，但历史残留需手工处理一次。

## 七、成本与限制

| 项 | 现状 | 说明 |
|----|------|------|
| 磁盘 | 40G，已用约 21G | 增量编译保留 `build-arm64/`，不要清目录全量重编 |
| 内存 | 4G（+1.9G swap） | ARM64 容器编译峰值较高，避免与其他重负载并存 |
| 带宽 | 3 Mbps | rsync 只传差异产物，日常部署几 MB~几百 KB；全量镜像导入需数分钟 |
| 无 KVM | 纯 QEMU 模拟 | 全量 ARM64 编译约 10+ 分钟，增量编译秒级 |
